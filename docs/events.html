Kafka Event Streams

Event Logs Have a Different Contract from Job Queues

Rustee exposes Kafka's topic, key, partition, consumer-group, offset, retry, DLQ, and replay meaning instead of disguising it as a background job API.

Enable the Kafka Adapter

The broker-backed publisher, consumer, and delayed-retry adapters are opt-in. Kafka configuration rejects blank, NUL-containing, or oversized bootstrap-server values before native client construction. Keep configuration types available for shared setup without a native client, then enable rdkafka only in the application that connects to Kafka. Rustee builds the opt-in native client from source, so local Kafka builds require CMake plus a working C and C++ toolchain; Linux CI verifies that feature lane. 

[dependencies]
rustee-events-kafka = { version = "0.1", features = ["rdkafka"] }

# Add only for PostgreSQL-backed durable delayed retry.
rustee-events-kafka-sqlx = { version = "0.1", features = ["rdkafka"] }

Event Contract

  • rustee-events defines versioned envelopes with a 1 MiB framework byte limit, a NUL-free 255-byte provider-visible event type, a separately bounded 1 MiB partition key, and 255-byte correlation and causation identifiers. It retains an explicit topic and partition key, provider-neutral handler/context/dispatch, strict current-version decode, explicit old-version upcasters, and content-free envelope, upcast, and provider diagnostics with trusted sources for application handling.
  • Producers acknowledge a broker result; consumers use serial manual commit. A source offset is committed only after the intended success, retry, or DLQ action is broker-acknowledged.
  • rustee-events-opentelemetry captures a bounded W3C carrier and makes a valid source context the event-handler parent without delegating handler diagnostics. Trace export, sampling, and retention stay application-owned.
  • Consumer observers collect bounded provider/outcome/in-flight/global-duration data. They retain at most fifteen direct provider labels plus other. Topic, partition, offset, key, payload, endpoint, and raw error do not become exporter labels.

Kafka Processing Rules

  • Use explicit keys, consumer groups, acks=all, enable.auto.commit=false, and enable.auto.offset.store=false to preserve the settlement contract.
  • A handler or strict decode failure routes to an immediate retry topic while the attempt budget remains, then to the DLQ. Source, retry, and DLQ topics must be distinct. Retry and DLQ records retain the original envelope and sanitized failure/origin metadata.
  • A worker crash after failure-route acknowledgement but before source commit can duplicate the retry or DLQ record. Consumers and DLQ projections must be idempotent.
  • Malformed, duplicate, or partial retry and origin headers terminate the worker without committing the source record. Topic ACLs must match producer and worker identities.
  • Native librdkafka options are explicit, bounded configuration input. Their names and values stay out of Rustee debug output; typed delivery, commit, and topic-provisioning invariants override conflicting native settings.
  • Source, retry, and DLQ topic names are non-blank, free from NUL and whitespace, and bounded to 249 UTF-8 bytes before client construction.
  • Framework-created Kafka clients force allow.auto.create.topics=false; deployment automation creates topics first. Their readiness checks each configured source, retry, or DLQ topic with a bounded, read-only call. Injected native clients retain their caller-owned setting and use full metadata before checking configured topics. Readiness does not prove group assignment, lag, downstream effects, or handler health.
  • Shutdown stops new polls, drains active handlers, and commits only safely settled offsets. Lag snapshots default to at most 128 assigned partitions; larger assignments require an explicit KafkaLagSnapshotLimit before broker watermark calls begin. The real-broker suite covers success commit, failure redelivery, drains, rebalances, and lag diagnostics.

Durable Delayed Retry

Kafka topics are not delay queues. rustee-events-kafka-sqlx stages a retryable failure in PostgreSQL before committing the source offset, admitting a non-empty payload and optional partition key independently up to the 1 MiB framework record bound. The relay repeats payload/key, retry/origin topic, partition, offset, and attempt checks before publishing a due row. Its stored retry and lease delays are positive whole milliseconds. A database-clock, SKIP LOCKED relay publishes only due rows to the stored retry topic and confirms after Kafka acknowledgement.

  • Unique source-topic/partition/offset plus next-attempt keys prevent duplicate staging during commit retries.
  • Within one SKIP LOCKED lease, due unlocked rows publish in available_at, created_at, then row-ID order. This local ordering does not remove the at-least-once duplicate boundary.
  • Kafka acknowledgement and database confirmation are not atomic, so the relay can duplicate publish. Event consumers must tolerate it.
  • Relay readiness checks the retry table and retry/DLQ topic metadata only. Migration, topic creation, delay policy, supervision, alerts, and graceful shutdown remain deployment-owned.
  • Generic outbox event delays do not replace source-offset and retry-header semantics. Follow the Kafka delayed retry runbook for approved replay.

Schema Compatibility

  • Strict decode is the default. Use compatible decoding only where an older producer contract is intentionally supported.
  • Current consumers reject newer versions rather than guessing forward compatibility. Producer-first rollout requires a separate deployment rule or consumer version.
  • rustee-events-schema binds typed event type and version to a bounded top-level JSON Schema artifact, exact source fingerprint, and stable subject/version catalog.
  • rustee-events-schema-confluent performs bounded, redacted HTTPS or loopback registry checks with a per-response byte limit for effective policy, exact lookup, absent-artifact registration, and exact relookup. It does not infer semantic compatibility, publish Kafka records, create topics, or move offsets.
  • Registry publication does not replace upcaster tests, rollback windows, retention/replay policy, or consumer-first rollouts. Follow the event schema runbook.

Outbox and Replay

  • Stage OutboxMessage::event with the business mutation in PostgreSQL and let an application-owned relay publish a leased destination row.
  • Use PostgresInbox with a stable consumer scope and event ID to suppress committed duplicate database effects. External side effects require their own idempotency evidence.
  • Before replay, record topic/partition/offset or timestamp scope, intent, expected count, approver, executor, and stop condition. Never use a production consumer group for first replay execution.
  • Create an explicit replay group and inspect admin-tool dry-run output before resetting offsets. Rustee does not wrap or execute Kafka administrative commands.
  • Monitor replay lag, throughput, failures, retry/DLQ backlog, oldest age, and downstream rate limits. Compare reconciled results before closing the incident.

Provisioning Boundary

Topic creation, partitions, replication, retention, ACLs, encryption, registry credentials, compatibility policy, and consumer-first rollout are deployment provisioning. Rustee does not automatically create topics or change partition counts at application startup.
