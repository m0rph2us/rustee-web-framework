Authentication and Authorization

Verify Identity, Decide Permission Separately

Rustee normalizes verified request identity into a provider-neutral Principal. Authentication proves who made the request; authorization independently decides which action that principal may perform.

Decision Summary

Request Processing Model

request
  -> bearer, API-key, session, or OIDC authentication layer
  -> verified Principal request extension
  -> tenant resolution and tenant-match guard
  -> permission or role-policy layer
  -> handler and repository-specific authorization

A handler receives a verified Principal, not raw credentials. Authentication layers reject malformed or unverifiable credentials without including a token, authorization header, session ID, key fingerprint, or provider endpoint in the response.

Principal and Bearer Boundaries

The validated Principal model is maintained separately from credential extraction, provider verification, and authorization middleware. The provider-neutral bearer verifier contract is also separate from the HTTP layer, which accepts exactly one bounded RFC 6750 b64token value before a provider is invoked. The stable rustee_auth::Principal, rustee_auth::BearerAuthenticator, and rustee_auth::AuthError paths remain the public facade; new adapters must depend on those contracts rather than a raw header or a particular middleware implementation. Local static bearer-token and API-key mappings reject duplicate credentials rather than letting registration order replace a principal. Principal subjects, issuers, and tenants are limited to 1 KiB; each scope, role, or permission is limited to 256 bytes and each distinct set to 64 values. Builder methods, serde restoration, and the verified-claim normalization helper enforce the same contract before a principal reaches a request, session, or durable API-key record. The PostgreSQL API-key store also limits the serialized durable principal to 512 KiB and fails closed before an oversized legacy row reaches authentication deserialization. Principal and authorization policy Debug output retains only safe aggregate counts; subjects, tenants, scopes, roles, and permission values are never rendered.

Implemented Authentication Paths

  • Static-key JWT: rustee-auth-jwt bounds trusted issuer, audience, leeway, and static-key configuration before verifying the selected algorithm, signature, issuer, audience, and time claims. HMAC secrets must meet the selected JWA algorithm's minimum key length. The adapter then normalizes verified roles and permissions. Validation diagnostics retain only algorithm, leeway, and issuer/audience presence; parsed claim diagnostics report only claim presence.
  • JWKS JWT: rustee-auth-oidc bounds trusted issuer, audience, HTTPS JWKS endpoint, and clock-skew configuration before strict asymmetric verification, bounded JSON-media-type retrieval, caching, rotation, and a fail-closed unavailable-provider response. Parsed access-token and ID-token diagnostics report claim presence only.
  • Opaque access tokens: the OIDC adapter bounds trusted issuer, audience, HTTPS endpoint, client credentials, and clock-skew configuration before active, identity, time, and fingerprint-cache checks. When enabled, cache failures fail closed before remote introspection is attempted; a zero cache TTL or entry limit bypasses cache state entirely.
  • OIDC browser login: bounded browser configuration, confidential-client credentials, discovery, token exchange, and final authorization redirects; authorization-code plus PKCE; callback-state validation before transaction-store access; bounded callback code and provider diagnostics before token exchange; bounded ID-token admission before nonce-checked verification; and an opaque session bridge are supported. One-time transaction TTLs are whole seconds between one second and one hour because the durable expiry is Unix-second based. The local transaction store retains at most 1,024 unexpired transactions, removes expired entries, and rejects a live duplicate state rather than replacing its nonce or verifier; rustee-auth-oidc-redis uses the same atomic create-only behavior for multi-instance deployment. Its default diagnostics are content-free and retain trusted sources for application handling.
  • Server-side sessions: rustee-auth-session uses one canonical opaque UUID v4 session-ID cookie and server-side state. Duplicate Cookie or CSRF headers are rejected rather than choosing one value. Place SessionLayer outside CsrfLayer, for example SessionLayer::new(store, cookie).layer(CsrfLayer.layer(app)): CSRF then checks unsafe requests only after a valid session context has been restored, while public and bearer-authenticated endpoints without session context proceed to their own authentication or handler policy. Its local in-memory store retains at most 1,024 unexpired sessions and prunes expired entries while saving or loading; rustee-auth-session-redis supplies an optional Redis store for multi-instance deployment. Redis persistence reads at most 512 KiB per session record, revalidates the persisted session ID, CSRF capability, key-to-record binding, and expiry before restoration. It exposes content-free failure categories by default, preserves trusted sources for application handling, and remains fail-closed at the HTTP boundary. Cookie-policy diagnostics retain only TTL, secure, and SameSite settings; cookie names, session IDs, and CSRF capabilities are never rendered.
  • API keys: rustee-auth exposes an explicit header-only API-key layer. Key validation, fingerprint derivation, bounded pepper rotation, and header handling remain one internal module; bearer middleware and authorization policies stay separate. rustee-auth-sqlx provides PostgreSQL keyed fingerprint records, no-overlap rotation metadata, revocation/expiry, and successful-auth audit. Its storage failure display and debug output are content-free while trusted driver sources remain available to application handling.

Authorization and Tenant Boundaries

  • RequirePermissionsLayer requires direct permissions or permissions granted to the principal's roles by an application-configured RolePolicy. A role string alone never proves resource ownership.
  • Verified token or provider claims may supply roles and permissions, but deployment policy decides what a role actually grants.
  • TenantResolutionLayer runs only after authentication. A TenantResolver must produce a trusted context, and principal tenant claims must match it before TenantContext reaches a handler.
  • The default HostTenantResolver uses a configured exact authority map. Host routing scope is not authorization. Unknown, malformed, or duplicate hosts return a tenant-detail-free 404; mismatch returns 403; resolver outage returns sanitized 503.
  • TenantContext is a trusted, non-blank, NUL-free identifier bounded to 1 KiB and shared by security and storage integrations. Route authorization alone does not isolate data: PostgreSQL uses application-owned RLS and MongoDB requires its own verified query and credential policy.

Failure and Browser Rules

  • Authorization-transaction, session-store, JWKS, and introspection outages fail closed. Rustee does not fall back to an anonymous request or identity cookie.
  • Rotate or revoke a session ID after login, privilege change, and logout.
  • Apply CSRF validation to callbacks and state-changing cookie requests. Configure credentialed CORS origins explicitly.
  • Do not log raw tokens, authorization headers, session IDs, credentials, identity claims, tenant IDs, host mappings, provider endpoints, redirect URLs, one-time authorization values, authorization-policy values, or authentication error bodies. Debug output must retain only safe state summaries.
  • Advanced OAuth client authentication, delegated authorization, mTLS, DPoP, and production identity-provider qualification require separate release gates.
