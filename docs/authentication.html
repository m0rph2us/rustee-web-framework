Authentication and Authorization

정체성을 확인하고, 권한은 별도로 판단합니다

Rustee는 특정 identity provider나 사용자 DB를 소유하지 않습니다. 대신 OIDC/OAuth login, bearer token, browser session을 하나의 Principal로 정규화하고, permission, role, scope, tenant에 따른 권한 부여를 명시적으로 적용합니다.

결정 요약

Stage 8은 rustee-auth, rustee-auth-jwt, rustee-auth-oidc, rustee-auth-session을 선택적 crate로 분리합니다. 현재 static-key JWT와 HTTPS JWKS 기반 API resource-server, server-side browser session 경로가 구현됐습니다. browser application의 OIDC Authorization Code + PKCE(S256), discovery, nonce-bound ID token과 session bridge, HTTPS opaque access-token introspection도 구현됐습니다.

인증은 Authenticator가 request credential을 검증해 Principal을 만드는 과정입니다. 권한 부여는 route 또는 handler가 Principal과 resource context를 사용해 permission을 검사하는 별도 과정입니다. rustee-core는 이 타입이나 provider에 의존하지 않습니다.

bearer verifier가 token을 거부하면 rustee-auth는 401과 WWW-Authenticate: Bearer를 반환합니다. JWKS, introspection 같은 필수 provider infrastructure가 안전하게 응답하지 못하면 verifier는 raw detail 없이 ProviderUnavailable을 반환하고 layer는 fail-closed 503으로 정규화합니다.

Authorization scope, permission, role, tenant, resource ownership를 확인합니다. 인증되었지만 허용되지 않은 요청은 403으로 분류합니다.
Handler 검증된 AuthUser 또는 Principal과 도메인 resource를 사용해 use case를 수행합니다. 인증 관련 내부 오류나 raw token은 HTTP response와 log에 노출하지 않습니다.

use jsonwebtoken::Algorithm;
use rustee_auth::AuthLayer;
use rustee_auth_jwt::{JwtAuthenticator, JwtConfig};

let jwt_verifier = JwtAuthenticator::from_hmac_secret(
    JwtConfig::new(Algorithm::HS256, "https://issuer.example", "rustee-api")?,
    std::env::var("JWT_HMAC_SECRET")?,
)?;

let protected = App::new()
    .get("/me", current_user)
    .layer(AuthLayer::bearer(jwt_verifier));

let app = App::new()
    .get("/health", health)
    .nest("/api", protected);

async fn current_user(AuthUser(principal): AuthUser) -> Json<Profile> {
    Json(Profile::from(principal))
}

App::nest는 /api를 제거한 request URI와 query를 protected service에 넘기므로 inner route는 계속 /me로 선언합니다. nested route의 observability template은 외부 /api/me로 유지하고, prefix 아래의 auth rejection과 fallback은 child service가 소유합니다. rustee-auth는 provider-neutral Principal, AuthUser extractor, bearer AuthLayer, scope/role/permission/tenant policy layer를 구현합니다. rustee-auth-jwt는 위 경로의 static-key verifier를 구현합니다. Principal은 subject, issuer, tenant, 검증된 scope, role, direct permission을 표현하지만 raw token을 보관하거나 재노출하지 않습니다.

현재 JWT resource-server 경로

JwtConfig는 issuer, audience, 허용 algorithm 하나와 선택적 clock-skew leeway를 명시적으로 받습니다. 기본 leeway는 0초이며, verifier는 signature와 sub, iss, aud, exp, nbf를 모두 필수로 검증합니다. HMAC, RSA/PS, EC, EdDSA key constructor는 algorithm family가 맞지 않으면 시작 시 거부합니다.

성공한 token만 Principal로 변환합니다. tenant claim은 tenant context가 되고, scope는 OAuth의 공백 구분 문자열 또는 문자열 배열로 받아 scope policy에 전달합니다. 검증 실패는 token이나 key 세부 정보를 노출하지 않는 단일 bearer rejection으로 정규화합니다.

이 crate는 local/static verification key 용도입니다. key ID에 따른 JWKS refresh와 rotation, issuer discovery, browser redirect/login, opaque token introspection은 별도 rustee-auth-oidc 경로로 제공합니다. static key로 그 경로를 대체하거나 algorithm 검증을 완화해서는 안 됩니다.

현재 JWKS resource-server 경로

rustee-auth-oidc는 configured HTTPS endpoint만 사용하고, 하나의 asymmetric algorithm, token header의 필수 kid, signature, sub, iss, aud, exp, nbf를 함께 검증합니다. remote JWK는 같은 algorithm을 명시하고 signature verification 용도로 허용된 경우에만 cache에 들어갑니다. duplicate kid는 임의 key를 고르지 않고 제외합니다. 

use std::time::Duration;

use jsonwebtoken::Algorithm;
use rustee_auth::AuthLayer;
use rustee_auth_oidc::{HttpJwksFetcher, JwksAuthenticator, OidcResourceServerConfig};
use url::Url;

let jwks_url = Url::parse("https://login.example.com/keys")?;
let config = OidcResourceServerConfig::new(
    Algorithm::RS256,
    "https://login.example.com/",
    "rustee-api",
    jwks_url.clone(),
)?;
let verifier = JwksAuthenticator::new(
    config,
    HttpJwksFetcher::new(jwks_url, Duration::from_secs(3))?,
);
let protected = AuthLayer::bearer(verifier).layer(App::new());

successful JWKS는 기본 5분 동안 사용합니다. unknown kid 또는 만료된 cache는 refresh를 시도하며, 기본 30초의 minimum refresh interval이 임의 kid 입력으로 인한 fetch storm을 제한합니다. JWKS transport/HTTP failure는 raw error를 노출하지 않고 ProviderUnavailable과 fail-closed 503으로 정규화합니다. 애플리케이션은 startup readiness가 provider reachability를 요구할 때에만 명시적으로 refresh()를 호출합니다.

이 resource-server API와 browser ID token API는 서로 다른 claim requirement를 가집니다. bearer JWT는 nbf를 필수로 요구하지만, OIDC ID token은 exp, iat, nonce를 필수로 하고 nbf가 있으면 검증합니다. opaque access token은 아래의 remote introspection 경로로 검증하며 JWT처럼 decode해서는 안 됩니다.

현재 opaque access-token 경로

OpaqueTokenAuthenticator는 configured HTTPS introspection endpoint에만 credential을 전송합니다. HTTP 200만으로 인증하지 않고 active=true, non-blank sub, configured iss와 aud, 공급된 exp/nbf 시간 경계를 확인한 뒤에만 Principal을 만듭니다. provider가 exp를 주지 않는다면 credential은 매 요청 remote 확인을 거치며 cache하지 않습니다. 

use std::time::Duration;

use rustee_auth::AuthLayer;
use rustee_auth_oidc::{
    HttpOpaqueTokenIntrospector, OidcClientAuthentication, OidcClientSecret,
    OpaqueIntrospectionConfig, OpaqueTokenAuthenticator,
};
use url::Url;

let config = OpaqueIntrospectionConfig::new(
    "https://login.example.com/",
    "rustee-api",
    Url::parse("https://login.example.com/oauth2/introspect")?,
    "rustee-resource-server",
    OidcClientAuthentication::ClientSecretBasic(
        OidcClientSecret::new(std::env::var("OIDC_INTROSPECTION_SECRET")?)?,
    ),
)?;
let verifier = OpaqueTokenAuthenticator::new(
    config,
    HttpOpaqueTokenIntrospector::new(Duration::from_secs(3))?,
);
let protected = AuthLayer::bearer(verifier).layer(App::new());

HTTP adapter는 form body의 token, token_type_hint=access_token과 configured client authentication을 전송합니다. ClientSecretBasic, ClientSecretPost, 명시적인 None을 지원하지만 production resource server는 provider가 허용하는 confidential authentication을 선택합니다. endpoint transport, HTTP status, JSON decoding failure는 raw detail 없이 ProviderUnavailable과 fail-closed 503으로 정규화합니다.

successful response cache의 기본 TTL은 60초, 기본 최대 항목 수는 1,024개입니다. cache key는 raw token이 아닌 SHA-256 fingerprint이며, entry lifetime은 provider exp를 넘지 않습니다. inactive, invalid, 만료 response는 cache하지 않습니다. 즉시 revocation이 필요한 deployment는 with_cache_ttl(Duration::ZERO) 또는 0-entry cache를 명시합니다.

현재 OIDC browser login 경로

OidcBrowserLogin은 discovery document의 issuer, authorization endpoint, token endpoint, JWKS URI를 configured HTTPS provider와 비교한 뒤에만 redirect를 만듭니다. authorization request에는 response_type=code, exact redirect URI, openid, S256 code challenge, server-side state, nonce가 들어갑니다. callback은 state record를 먼저 atomic하게 consume하므로 replay, provider error, code exchange retry가 같은 transaction을 재사용할 수 없습니다. 

async fn login_start(State(app): State<AppState>)
    -> Result<AuthorizationRedirect, OidcLoginError> {
    app.oidc_login.begin().await
}

async fn login_callback(
    State(app): State<AppState>,
    Query(callback): Query<AuthorizationCallback>,
) -> Result<Response, OidcLoginError> {
    let issued = app.oidc_login
        .complete_session(callback, &app.sessions)
        .await?;
    let mut response = redirect_to("/app");
    issued.apply_to(&mut response);
    Ok(response)
}

token endpoint 응답에서 ID token만 검증에 사용하며 raw authorization code, PKCE verifier, client secret, ID/access token은 Debug이나 HTTP response에 노출하지 않습니다. ID token은 signature, issuer, audience, exp, iat, multi-audience의 azp, nonce를 검증해 Principal로 바꾼 뒤 SessionManager::establish에 전달합니다. application은 callback이 만든 임의 redirect URL을 신뢰하지 않고 server-side success location을 선택합니다.

InMemoryAuthorizationTransactionStore는 local/test 전용입니다. production browser login은 rustee-auth-oidc-redis의 RedisAuthorizationTransactionStore를 사용합니다. 기본 namespace는 rustee:oidc:transaction:v1이며 state record는 남은 transaction TTL로 저장되고 Redis GETDEL로 atomic하게 소비됩니다. Redis failure는 in-memory fallback 없이 login failure로 정규화합니다.

현재 browser session 경로

rustee-auth-session은 cookie에 random opaque session ID만 두고 Principal, expiration, CSRF token은 SessionStore에 유지합니다. SessionManager는 login/privilege change에서 새 ID를 만들고 기존 ID를 삭제하는 rotation, logout invalidation, Set-Cookie 발급을 제공합니다. 기본 cookie는 Secure, HttpOnly, SameSite=Lax이며 local development에서만 insecure cookie를 명시적으로 허용할 수 있습니다.

SessionLayer는 유효한 store record만 request extension에 넣고, SessionUser extractor는 검증된 principal과 opaque ID만 제공합니다. CsrfLayer는 POST/PUT/PATCH/DELETE 등 unsafe method에 X-CSRF-Token을 요구합니다. session store 장애는 fail-closed 503으로 정규화하며, 만료/없는 session은 anonymous 요청으로 처리합니다.

InMemorySessionStore는 local/test 전용입니다. production에는 rustee-auth-session-redis의 RedisSessionStore를 사용합니다. 기본 namespace는 rustee:session:v1이며 각 write는 남은 session TTL을 Redis expiry로 설정합니다. Redis read/write/delete failure는 SessionLayer에서 fail-closed 503으로 정규화합니다. OIDC callback은 verified Principal으로 새 session을 발급합니다. cookie value나 CSRF token을 log/trace에 기록하지 않습니다.

API key service 경로

ApiKeyLayer::header는 configured HTTP field name 하나에서만 API key를 읽습니다. missing, duplicate, non-ASCII, blank, whitespace 또는 4 KiB 초과 값은 provider 호출 전에 401로 거부하고, provider outage는 credential detail 없이 503으로 fail-closed 합니다. layer는 validated Principal만 extension에 넣으며 raw key, configured header name, lookup detail을 response, handler 또는 Debug output에 넣지 않습니다. 

use rustee_auth::{ApiKeyAuthenticator, ApiKeyLayer, Principal};

// The provider owns hashed lookup, rotation, tenant mapping, and audit policy.
let protected = ApiKeyLayer::header("X-API-Key", api_key_authenticator)?
    .layer(App::new().get("/service", handler));

StaticApiKeyAuthenticator는 test/local example만을 위한 raw in-memory mapping입니다. production에는 keyed hash, constant-time comparison 또는 provider-native secret lookup과 revocation/rotation runbook을 가진 application provider를 사용합니다. query parameter와 cookie API key, automatic OpenAPI-to-middleware wiring, database schema, rate-limit key derivation은 이 layer의 scope가 아닙니다.

권한과 tenant 경계

  • Principal의 identity와 route의 authentication requirement는 permission 판단과 분리합니다.
  • RequirePermissionsLayer는 direct permission 또는 RolePolicy가 해당 principal role에 grant한 모든 permission을 요구합니다. 단순 role 문자열만으로 resource ownership을 판단하지 않습니다.
  • JWT/JWKS/ID token/introspection verifier는 signature 또는 provider response를 검증한 뒤 roles와 permissions claim을 정규화할 수 있습니다. role이 실제로 부여하는 permission은 token claim이 아니라 deployment의 RolePolicy가 결정합니다.
  • TenantResolutionLayer는 verified principal을 받은 뒤 TenantResolver가 만든 context를 비교하고, 일치할 때만 TenantContext extractor를 handler에 넣습니다. 기본 HostTenantResolver는 configured exact authority map을 case-insensitive로 매칭합니다. Host는 routing scope일 뿐 권한이 아니므로 principal tenant가 다시 일치해야 합니다.
  • unknown, malformed 또는 duplicate Host는 tenant detail을 주지 않는 404, tenant mismatch는 403, resolver outage는 sanitized 503입니다. custom resolver는 trusted proxy context, server-side routing 또는 session lookup을 사용할 수 있지만 임의 client header를 tenant authority로 쓰지 않습니다.
  • TenantContext는 provider-neutral rustee-tenant crate가 소유하고 rustee-auth가 호환 경로로 re-export합니다. PostgreSQL에서는 rustee-sqlx::begin_tenant_transaction이 transaction-local setting을 설정해 application-owned RLS policy가 read/write를 막도록 합니다. route authorization만으로 데이터 격리를 보장하지 않으며, MongoDB와 다른 repository는 해당 provider의 별도 tenant query/credential 정책을 명시해야 합니다.
  • 정책 engine, delegated authorization, ABAC/ReBAC는 Stage 10에서 별도 extension과 ADR로 검토합니다.
use rustee_auth::{
    AuthLayer, HostTenantResolver, RequirePermissionsLayer, RolePolicy, TenantContext,
    TenantResolutionLayer,
};

let mut roles = RolePolicy::new();
roles.grant("project-editor", ["project:read", "project:write"])?;

let policy = RequirePermissionsLayer::new(["project:write"], roles)?;
let tenants = HostTenantResolver::new([(
    "acme.example.test",
    TenantContext::new("acme")?,
)])?;
let tenant_scoped = TenantResolutionLayer::new(tenants).layer(
    policy.layer(App::new().get("/projects", list_projects)),
);
let protected = AuthLayer::bearer(authenticator).layer(tenant_scoped);

// `list_projects(TenantContext, ...)` must constrain every read and write by the tenant.

세션과 실패 정책

  • browser session은 signed session ID cookie와 server-side state를 기본 모델로 합니다. identity data 전체를 암호화 cookie에 기본 저장하지 않습니다.
  • 로그인, privilege 변경, logout 시 session ID를 rotation 또는 폐기합니다.
  • SessionLayer는 session store outage를 fail-closed 503으로 처리합니다. Rustee 기본 middleware에는 identity cookie 또는 anonymous request로의 fail-open fallback이 없습니다.
  • JWKS와 opaque introspection adapter의 실제 loopback transport outage는 authentication_unavailable 503으로 fail-closed되며, response에는 raw token이나 provider endpoint를 넣지 않습니다. key refresh와 issuer 장애도 metrics와 trace에 남기되 token, authorization header, session ID를 기록하지 않습니다.
  • callback과 state-changing cookie request에는 CSRF 검증을 적용하고, CORS 허용 origin을 credential 사용과 함께 명시합니다.

구현 순서

  1. Stage 4에서 request extension, extractor, error mapping을 안정화합니다.
  2. Stage 6에서 Redis state-store와 failure policy를 구현해 session adapter의 기반을 만들었습니다.
  3. Stage 8에서 rustee-auth의 Principal, authorization policy와 JWT resource-server flow를 구현합니다. provider-neutral principal, bearer layer, explicit header-only API-key layer, scope policy, static-key JWT 검증, JWKS cache/rotation verifier, OIDC Code + PKCE browser/session flow와 opaque introspection은 구현됐습니다.
  4. 같은 단계에서 role-to-permission policy, tenant-match request guard, configured host-map TenantResolutionLayer, JWKS/opaque introspection의 real loopback transport-outage security contract를 구현했습니다. repository-level tenant query verification과 실제 external IdP revocation integration test가 남았습니다.
  5. Stage 10에서 advanced OAuth client authentication, delegated policy, mTLS/DPoP 같은 요구를 실제 deployment와 함께 독립 release gate로 확장합니다.
