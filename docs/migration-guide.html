Migration Guide

Compatibility Changes Include the Operating Procedure

A Rustee migration explains code, configuration, schema, provider, and deployment changes together with verification and rollback. A diff alone is not a migration plan.

Initial Baseline: v0.1.0

The first public baseline establishes the documented core HTTP, optional integration, and support boundaries recorded in the release inventory and release notes. Consumers should pin the supported MSRV and use explicit feature flags for optional adapters.

Redis Streams Retry-Key Format

Redis Streams workers derive provider-private delayed-retry keys from a versioned, length-delimited stream and consumer-group namespace. This prevents delimiter-containing identifiers from making separate worker routes share retry storage.

For an existing deployment that used the earlier delimiter-only form, reconcile all scheduled retries before replacing workers. The adapter intentionally does not infer old retry ownership because a colliding legacy key cannot be attributed safely to one source route.

  1. Stop workers for each affected route after its active handlers have drained.
  2. Inspect the earlier {stream}:rustee:jobs:{group}:retry:* schedule and hashes; allow known records to run, replay them intentionally, or remove them using the deployment's incident procedure.
  3. Deploy the versioned-key worker and verify that its new retry storage starts empty or contains only retries scheduled by the new workers.

MCP OAuth Redis Record-Key Format

Encrypted MCP OAuth transaction and token records use versioned, length-delimited namespace/state and namespace/token-slot keys. This prevents a delimiter-containing callback state or tenant/user/connection slot from colliding with another configured Redis namespace.

Do not automatically read or copy a legacy delimiter-only record. Its full legacy Redis key is authenticated encryption data, and a colliding key cannot establish which transaction or token subject should own the ciphertext. After deployment, restart any uncompleted OAuth authorization flow, reauthorize each affected token slot, and retire legacy entries with the deployment's credential-handling procedure.

Tenant Identifier Admission

TenantContext now rejects NUL-containing values when it is constructed. This keeps a tenant identity representable in both MongoDB BSON data and PostgreSQL's transaction-local RLS setting instead of failing after a database transaction begins.

Before upgrading, audit trusted identity and tenant-resolver mappings for NUL-containing values. Correct those source values rather than lossy-normalizing them: a request with such a tenant now fails at context construction, and no database migration is required.

Required Information for Future Releases

  • Changed public APIs, feature flags, defaults, configuration keys, environment inputs, and minimum Rust version.
  • Database, outbox, scheduler, checkpoint, or ledger migrations including order, preconditions, forward compatibility, backfill, rollback, and owner.
  • Provider/client version, credential, TLS, topology, topic/queue/schema, cache, identity, or edge-delivery changes.
  • Behavioral changes to authentication, authorization, tenant isolation, retry, acknowledgement, replay, observability, redaction, AI tool approval, or retention.
  • Concrete validation commands, deployment evidence, success criteria, failure signals, stop conditions, and rollback procedure.

Authoring and Verification Order

  1. Identify affected contracts and update focused HTML documents and ADRs.
  2. Ship forward-compatible readers or consumers before writers/producers where the contract needs it.
  3. Apply migrations and provisioning through the deployment system, never an implicit HTTP startup action.
  4. Run unit, integration, provider, and recovery checks required for the claimed support level.
  5. Observe the defined rollout window, complete reconciliation, and retain owner-approved evidence.

Non-Goals

This guide does not promise automatic cross-version migration, provider replay, data backfill, schema downgrade, credential rotation, or topology rollback. Those operations need application and deployment ownership.
