Migration Guide

호환성 변경은 code diff가 아니라 운영 절차까지 설명합니다

Rustee는 첫 public baseline 이후 API, configuration, schema, provider lifecycle이 바뀌는 release마다 실행 순서와 rollback limit을 여기에 기록합니다. release note는 변경 목록이고, 이 문서는 사용자가 실제로 이동하는 방법입니다.

Initial baseline: v0.1.0

Status: Draft / Unreleased.

이전 Rustee release가 없으므로 v0.1.0에는 source version 간 migration path가 없습니다. 첫 tag와 publish record가 만들어진 뒤에만 이 항목은 public compatibility baseline이 됩니다. 현재 사용자는 unpublished workspace source를 stable API로 가정해서는 안 됩니다.

baseline의 supported scope, optional provider status와 initial limitations은 v0.1.0 release note draft 및 지원 현황 매트릭스를 따릅니다.

작성과 검증 순서

  1. release owner가 affected surface와 no-downtime 가능 여부를 먼저 분류합니다. 불가능하면 maintenance window 또는 explicit stop-the-world requirement를 적습니다.
  2. new reader/consumer 또는 compatibility code를 먼저 배포하고, data/config/producer를 다음에 바꾸며, old path 제거는 rollback window 뒤의 separate release로 둡니다.
  3. migration은 test fixture와 real backend/provider contract에서 verify합니다. credential, production tenant data, billable provider call이 필요한 step은 explicit approval을 받아 별도 qualification으로 기록합니다.
  4. rollback이 unsafe하거나 provider-side side effect를 되돌릴 수 없으면 그 사실을 숨기지 않고 reconciliation procedure와 operator owner를 적습니다.
  5. final guide link와 known limitation을 release note, support-level delta와 release checklist에 대조합니다.

비목표

framework는 application의 business-data backfill, credential issuance, cloud IAM/KMS update, CDN purge 또는 external side-effect rollback을 자동 실행하지 않습니다. migration guide는 이 책임을 감추는 convenience API 대신 required operator action과 검증 evidence를 공개합니다.
