Queue and Background Jobs

비동기 작업은 전달 보장을 숨기지 않고 실행합니다

Rustee의 queue 지원은 HTTP request에서 작업을 enqueue하고 별도 worker process에서 처리하는 durable job system입니다. 기본 보장은 at-least-once delivery이며, 성공 처리 후 ack, 실패 재시도, dead-letter queue, idempotent handler를 명시합니다.

결정 요약

Stage 9A에서 rustee-jobs를 typed job client와 worker runtime으로 제공하고, 첫 durable provider는 NATS JetStream 기반 rustee-jobs-nats로 구현합니다. 현재 NATS adapter는 acknowledged publish, job ID를 쓴 stream deduplication header, readiness, pre-provisioned durable pull worker, bounded concurrent drain, explicit ack/delayed NAK, acknowledged DLQ relay를 구현합니다. Stage 10의 Redis Streams adapter rustee-jobs-redis는 consumer group, durable delayed retry, ownership-checked ack/DLQ, pending reclaim과 Redis 7 CI contract를 구현했습니다. RabbitMQ 4.3 adapter rustee-jobs-rabbitmq는 quorum queue publisher confirm, manual ack/reject, native delayed-retry compatibility, direct DLQ와 CI contract를 구현했고, Amazon SQS adapter rustee-jobs-sqs는 25초 기본 요청 deadline, long polling, visibility lease heartbeat, direct DLQ/delete, Standard/FIFO route와 stopped LocalStack recovery를 포함한 CI contract를 구현했습니다. rustee-core에는 broker dependency를 넣지 않습니다.

현재 rustee-jobs는 versioned JSON envelope, job ID, idempotency key, bounded W3C JobTraceContext, typed publish/dispatch contract, bounded retry/Dead Letter decision, worker concurrency/drain configuration과 broker가 관찰한 delivery attempt의 handler context 주입을 구현합니다. 선택적 rustee-jobs-opentelemetry는 current span을 envelope carrier에 넣고 valid carrier를 job handler span의 parent로 연결하며, rustee-jobs-observability는 NATS/Redis Streams/RabbitMQ/SQS worker의 bounded delivery metric collector를 제공하고 rustee-jobs-observability-prometheus는 explicit no-store text response를 제공합니다. 실제 broker command를 일반화한 public Queue<T> API는 만들지 않습니다. 대신 application이 필요로 하는 공통 job lifecycle만 노출하고, provider-specific configuration과 delivery capability는 각각의 adapter에 남깁니다.

Worker observability

모든 durable worker는 선택적 with_delivery_observer builder로 같은 lifecycle contract를 사용합니다. 시작과 최종 정산을 분리해 acknowledged, retried, dead_lettered, unsettled outcome 및 처리 시간을 기록합니다. 정산 실패나 drain timeout으로 task가 취소되면 source delivery를 성공으로 보지 않고 unsettled로 끝납니다. 

let metrics = JobMetrics::new();
let worker = SqsWorker::new(sqs_client, config)
    .with_delivery_observer(Arc::new(metrics.clone()));

worker.run_registry_until(registry, RetryPolicy::default(), WorkerConfig::default(), shutdown).await?;
let snapshot = metrics.snapshot();
let response = rustee_jobs_observability_prometheus::metrics_response(&metrics);
  • rustee-jobs-observability::JobMetrics는 exporter-neutral collector입니다. rustee-jobs-observability-prometheus는 provider label을 escaped text 0.0.4로 인코드하는 optional metrics_response helper이며 registry, listener 또는 automatic route를 만들지 않습니다. Prometheus, OTLP 또는 application logger로 내보내는 정책은 application이 정합니다. 상세 결정은 ADR 0032를 따릅니다.
  • metrics에는 bounded provider identifier, settlement outcome, global duration histogram만 사용합니다. job ID, job type, idempotency key, payload, queue URL/name, receipt handle, trace carrier와 handler error text는 넣지 않습니다.
  • rustee-jobs-opentelemetry::TraceContextHandler span은 job ID, type, version, attempt를 correlation용 trace attribute로 기록합니다. exporter sampling과 retention은 application이 소유합니다.
  • observer는 synchronous/non-blocking contract이며 panic은 worker settlement path와 격리됩니다. observer implementation은 bounded exporter queue 또는 local aggregation을 사용해야 합니다.

Redis Streams worker 경로

RedisStreamsPublisher와 RedisStreamsWorker는 reconnecting ConnectionManager를 받습니다. source stream, consumer group, DLQ stream, ACL, retention은 deployment가 먼저 만들고 worker는 readiness에서 source/DLQ와 group 존재만 검사합니다. group을 만들거나 last-delivered ID를 바꾸지 않습니다.

publisher와 worker는 기본 5초의 설정 가능한 operation deadline으로 readiness, XADD, XREADGROUP, pending reclaim, ownership-checked settlement와 retry promotion을 제한합니다. worker deadline은 idle blocking read보다 길어야 합니다. reconnect policy는 injected ConnectionManager와 application이 소유하며, Rustee는 deadline 만료를 endpoint 없는 provider error로 정규화합니다. 

let publisher = RedisStreamsPublisher::new(redis.clone(), "jobs.email")?;
let worker_config = RedisStreamsWorkerConfig::new(
    "jobs.email",
    "email-workers",
    "email-worker-a",
    "jobs.email.dlq",
)?
.with_reclaim_idle(Duration::from_secs(90))?;
let worker = RedisStreamsWorker::new(redis, worker_config);

worker
    .run_registry_until(
        registry,
        WorkerConfig::default(),
        RetryPolicy::default(),
        shutdown_signal(),
    )
    .await?;
  • publisher는 envelope bytes와 base attempt를 XADD하고 Redis가 append를 승인한 뒤에만 성공을 반환합니다. publish deduplication은 제공하지 않으므로 outbox 재전달과 external side effect는 job ID/idempotency key로 처리합니다.
  • worker는 XREADGROUP으로 새 entry를 읽습니다. handler success는 현재 consumer가 PEL owner인 경우에만 XACK합니다.
  • handler failure는 Redis server clock 기준으로 provider-private retry zset/hash에 payload와 next attempt를 기록한 뒤 source를 같은 Lua operation에서 ack합니다. due retry는 다시 source stream에 원자적으로 append되므로 process restart 뒤에도 delay가 남습니다.
  • max delivery, malformed envelope, unknown registry job은 DLQ XADD를 source XACK과 한 operation으로 묶습니다. DLQ entry에는 payload, actual cumulative attempt, source entry ID가 남습니다.
  • terminated worker가 남긴 PEL entry만 XAUTOCLAIM으로 회수하고 XPENDING delivery count를 base attempt와 합산합니다. source entry가 retention/trim으로 사라졌다면 worker는 데이터 유실을 숨기지 않고 실패합니다.

현재 Redis worker는 processing 중 PEL heartbeat를 연장하지 않습니다. reclaim_idle은 deployment가 허용하는 최대 handler 실행 시간보다 길어야 하며, 더 긴 작업은 handler timeout/분할 또는 heartbeat가 있는 후속 provider capability가 필요합니다. source stream을 pending entry보다 짧게 trim하면 안 됩니다.

RabbitMQ 4.3 worker 경로

RabbitMqPublisher는 dedicated confirm channel에서 persistent publish와 mandatory route를 사용하고 broker Ack가 올 때만 enqueue 성공으로 처리합니다. RabbitMqWorker는 source quorum queue의 manual ack consumer channel과 DLQ confirm channel을 분리합니다. 성공은 source ack, poison/exhausted delivery는 DLQ publish confirm 뒤 source ack입니다.

RabbitMqConnectionConfig는 기본 5초의 bounded connect deadline을 사용하며 with_connect_timeout으로 deployment deadline을 명시할 수 있습니다. broker가 unavailable이면 RabbitMqError::Connect로만 실패하고 endpoint나 credential을 노출하지 않습니다. adapter는 자동 reconnect나 backoff loop를 시작하지 않으므로 restart, backoff, readiness 전환은 application supervisor의 책임입니다.

retry는 publish/ack 교환이 아니라 source delivery를 basic.reject(requeue=true)로 반환합니다. deployment가 만든 RabbitMQ 4.3 delayed-retry-type=failed policy가 이를 durable delayed state로 보관하며 x-acquired-count를 다음 handler attempt로 사용합니다. RabbitMqNativeRetryConfig은 deployment policy와 RetryPolicy의 exact compatibility를 startup에 확인합니다.

source quorum queue의 delivery-limit은 explicit dead-letter-exchange와 dead-letter-routing-key를 함께 가져야 합니다. 두 값은 poison/exhausted delivery의 confirmed direct-DLQ route와 같은 destination을 가리켜야 하며, exchange만 지정해 original routing key로 unroutable dead-letter를 만들면 안 됩니다. AMQP passive readiness는 이 effective policy를 읽지 못하므로 deployment artifact 또는 별도 management-plane audit에서 검증합니다.

optional rustee-jobs-rabbitmq-management의 RabbitMqTopologyAuditor는 worker AMQP connection과 별도의 read-only Management HTTP API account로 source queue snapshot을 읽습니다. CI는 provisioned quorum queue의 실제 Management API snapshot으로 quorum/durable/non-auto-delete와 effective delayed retry min/max/type, delivery limit, DLX exchange/routing key를 worker config와 비교합니다. auditor는 topology를 생성하거나 수정하지 않습니다. management URL과 credential은 debug output에서 제외합니다. adapter는 loopback test endpoint 외의 plain HTTP URL을 거부하므로, deployment는 HTTPS endpoint와 monitor-only ACL을 사용합니다.

Amazon SQS worker 경로

SqsPublisher와 SqsWorker는 application이 구성한 AWS SDK client를 받습니다. credential, region, endpoint와 SDK transport retry는 application이 소유하고 adapter는 queue URL을 credential로 취급하지 않습니다. source/DLQ, queue mode, redrive policy, IAM, encryption, retention은 deployment가 먼저 만들며 worker readiness는 이를 읽기 전용으로 검증합니다. 

let source = SqsQueueTarget::new(source_queue_url, SqsQueueKind::Standard)?;
let dlq = SqsQueueTarget::new(dead_letter_queue_url, SqsQueueKind::Standard)?;
let config = SqsWorkerConfig::new(source, dlq, 5)?
    .with_visibility_timeout(Duration::from_secs(120))?
    .with_heartbeat_interval(Duration::from_secs(30))?;
let worker = SqsWorker::new(sqs_client, config);

worker
    .run_registry_until(
        registry,
        RetryPolicy::default(),
        WorkerConfig::default(),
        shutdown_signal(),
    )
    .await?;
  • publisher는 SQS SendMessage 성공 response 뒤에만 enqueue 성공을 반환합니다. FIFO route는 명시한 message group과 job ID 기반 deduplication ID를 함께 보냅니다. FIFO deduplication window도 exactly-once side effect 보장이 아닙니다.
  • worker는 최대 20초 long polling으로 receive하고 ApproximateReceiveCount를 typed handler attempt로 주입합니다. Standard queue의 count와 delivery는 at-least-once/approximate이므로 idempotency key가 여전히 필요합니다.
  • handler가 실행되는 동안 heartbeat가 ChangeMessageVisibility로 lease를 갱신합니다. handler 성공은 DeleteMessage, handler failure는 core retry backoff와 같은 whole-second visibility 값으로 retry합니다. sub-second 또는 12시간 초과 retry는 startup에서 거부합니다.
  • malformed envelope, unknown registry job, retry budget 고갈은 explicit DLQ SendMessage 성공 뒤 source receipt를 delete합니다. 이 delete가 실패하면 direct DLQ duplicate가 가능하므로 DLQ consumer도 idempotent해야 합니다.
  • source redrive policy는 같은 DLQ ARN과 configured maxReceiveCount를 가져야 합니다. 이는 process crash나 lease loss로 adapter가 source receipt를 settle하지 못했을 때의 broker recovery path이며 adapter가 queue policy를 변경하지는 않습니다.

SQS visibility timeout은 message가 처음 receive된 뒤 최대 12시간까지만 연장할 수 있습니다. SqsWorkerConfig은 handler timeout을 이 한계보다 짧게 강제하며 heartbeat 실패 시 source receipt를 delete하지 않습니다. 긴 작업은 작은 idempotent job으로 분할하거나 durable step workflow를 사용합니다.

NATS worker 경로

JetStreamWorker는 application startup에 stream이나 consumer를 만들지 않습니다. 이미 provision된 durable pull consumer와 JetStream context를 받아 실행하며, consumer가 AckPolicy::Explicit이 아니거나 durable하지 않으면 시작을 거부합니다. worker concurrency보다 작은 MaxAckPending 또는 retry policy보다 작은 MaxDeliver도 실행 전에 거부합니다. 

let worker = JetStreamWorker::new(context, consumer, "jobs.email.dlq")?;

worker
    .run_until::<SendWelcomeEmail, _, _>(
        send_welcome_email,
        WorkerConfig::default(),
        RetryPolicy::default(),
        shutdown_signal(),
    )
    .await?;
  • 성공 handler는 source delivery를 ack합니다.
  • 실패 handler는 JetStream이 보고한 delivery attempt로 retry policy를 계산하고, 예산이 있으면 delayed NAK를 보냅니다.
  • 예산 소진 또는 잘못된 envelope는 DLQ subject에 publish하고 JetStream publish acknowledgement를 받은 뒤에만 source를 ack합니다. DLQ에는 job ID deduplication header와 실제 attempt header를 남깁니다.
  • shutdown 신호 뒤에는 새 delivery를 꺼내지 않고 active handler만 drain_timeout까지 기다립니다. 그 뒤 취소된 handler와 아직 ack되지 않은 delivery는 at-least-once 규칙에 따라 redelivery됩니다.

consumer의 AckWait은 handler의 최대 실행 시간보다 길어야 합니다. 현재 worker는 긴 handler를 위해 JetStream progress acknowledgement를 자동 연장하지 않으므로, 이 값이 짧으면 처리 중 redelivery가 발생할 수 있습니다.

전달 보장과 처리 규칙

규칙 Rustee 정책 애플리케이션 책임
전달 보장 기본은 at-least-once입니다. exactly-once 실행을 약속하지 않습니다. 중복 실행을 견디는 idempotent handler와 idempotency key를 구현합니다.
ack handler가 성공한 뒤에만 ack합니다. 외부 side effect가 성공으로 확정된 뒤 handler를 반환합니다.
retry retryable, permanent, discard 결과를 구분하고 max attempts, backoff, jitter를 설정합니다. 재시도 가능한 오류와 이미 처리된 job을 분류합니다.
DLQ max attempts 초과 또는 permanent failure를 dead-letter 경로로 보냅니다. 원인 수정, 조사, 안전한 replay 또는 discard 절차를 운영합니다.
worker 종료 새 fetch를 멈추고 grace period 동안 실행 중 job을 drain한 뒤, 남은 unacked job을 release합니다. handler timeout과 긴 작업 heartbeat를 service 특성에 맞게 설정합니다.

Job 계약

모든 job은 serialization 가능한 payload와 versioned type name을 가져야 합니다. Rust closure나 in-memory pointer를 enqueue하지 않습니다.

use rustee_jobs::{Job, JobClient, JobEnvelope, JobRegistry, RetryPolicy, WorkerConfig};

#[derive(Serialize, Deserialize)]
struct SendWelcomeEmail {
    user_id: UserId,
}

impl Job for SendWelcomeEmail {
    const NAME: &'static str = "email.welcome";
    const VERSION: u16 = 1;
}

let envelope = JobEnvelope::new(SendWelcomeEmail { user_id })
    .with_idempotency_key(format!("welcome-email:{user_id}"))?;
JobClient::new(publisher).enqueue(&envelope).await?;

let mut registry = JobRegistry::new();
registry.register::<SendWelcomeEmail, _>(send_welcome_email)?;

worker
    .run_registry_until(
        registry,
        WorkerConfig::default(),
        RetryPolicy::default(),
        shutdown_signal(),
    )
    .await?;

이는 현재 Stage 9A의 public API 형태입니다. envelope에는 job ID, type, version, payload, idempotency key, enqueue time, attempt를 기록합니다. strict decode가 기본이며 older version은 명시적 JobUpcaster를 등록한 handler만 처리합니다. credential, raw token, 불필요한 개인정보는 payload와 observability attribute에 넣지 않습니다.

Provider 전략

Provider 지원 단계 운영 의미
NATS JetStream Stage 9A 첫 공식 durable provider: rustee-jobs-nats durable pull consumer, explicit ack, AckWait/backoff, MaxDeliver, flow control을 사용합니다.
Redis Streams Stage 10 구현/Redis 7 CI gate: rustee-jobs-redis consumer group, ownership-checked XACK, durable delayed retry, DLQ, pending reclaim을 사용합니다. Redis Pub/Sub이나 List는 durable job 경로가 아닙니다.
RabbitMQ Stage 10 구현/RabbitMQ 4.3 CI gate: rustee-jobs-rabbitmq quorum queue, publisher confirm, manual ack/reject, bounded prefetch, direct DLQ를 사용합니다. retry는 RabbitMQ 4.3 native delayed-retry policy로만 처리하며 queue/exchange/DLX/policy는 배포 단계에서 만듭니다.
Amazon SQS Stage 10 구현/LocalStack CI gate: rustee-jobs-sqs long polling, visibility lease heartbeat, 처리 후 DeleteMessage, direct/redrive DLQ를 사용합니다. Standard와 FIFO 모두 business side effect는 at-least-once로 다룹니다.
Apache Kafka job provider가 아님: rustee-events-kafka, optional rustee-events-kafka-sqlx topic, partition key, consumer group, offset commit, retention/replay가 핵심인 event stream입니다. PostgreSQL delayed retry adapter는 source offset commit 전 retry intent를 stage하고 due row를 relay하지만, Kafka를 durable job lifecycle로 평준화하지 않습니다.

NATS stream/consumer, Redis stream/group/DLQ 같은 broker infrastructure는 production server startup에서 자동 생성하지 않습니다. 배포 provisioning 단계에서 versioned configuration으로 만들고, application은 readiness check로 필요한 consumer에 접근 가능한지 확인합니다.

RabbitMQ exchange/queue/DLX와 SQS queue/redrive policy/IAM도 같은 방식으로 provisioning합니다. Kafka topic/partition/retention은 event stream 문서의 별도 운영 경계에 따릅니다.

rustee-jobs-rabbitmq는 RabbitMQ 4.3 이상 quorum queue와 native delayed-retry-type=failed policy를 요구합니다. archived x-delayed-message plugin이나 per-message TTL/DLX 대기열을 retry 구현으로 사용하지 않습니다. native backoff는 linear이므로 RabbitMqNativeRetryConfig과 core RetryPolicy의 initial/max 값이 같고 max_backoff <= 3 * initial_backoff일 때만 worker가 시작됩니다. 이 조건 밖의 exponential retry는 NATS, Redis Streams 또는 PostgreSQL schedule 경로를 선택합니다.

Outbox와 지연 작업

database transaction을 commit한 뒤 broker publish가 실패하면 DB 변경은 남고 job은 유실될 수 있습니다. 반대로 먼저 publish하면 아직 commit되지 않은 데이터를 참조하는 job이 생길 수 있습니다. Rustee는 이 dual-write를 자동 transaction처럼 만들지 않습니다.

  • PostgreSQL은 rustee-outbox-sqlx로 event/job envelope을 같은 transaction에 stage합니다. migration은 deployment-owned이고, JobOutboxRelay는 destination별 FOR UPDATE SKIP LOCKED lease를 broker publish acknowledgement 뒤에만 confirm합니다. application은 one-pass relay_once 또는 explicit run_until(RelayLoopConfig, shutdown)을 선택합니다. 후자는 empty pass만 bounded idle delay로 poll하고 shutdown 뒤 새 lease를 잡지 않으며, completed pass의 bounded RelayLoopReport를 반환합니다. each pass는 OutboxRelayObserver lifecycle을 emit하며 optional OutboxRelayMetrics가 live count와 duration을 집계합니다.
  • outbox relay도 at-least-once입니다. broker success 뒤 DB confirmation이 실패하거나 lease를 잃으면 같은 job ID가 다시 publish될 수 있습니다. PostgresInbox는 consumer scope와 job ID receipt를 same-transaction database side effect에 기록하지만 external side effect는 provider idempotency key가 필요합니다.
  • one-time delayed job은 JobSchedule::after와 PostgresOutbox::stage_job_after로, one-time delayed event는 EventSchedule::after와 stage_event_after로 business write와 같은 PostgreSQL transaction에 stage합니다. existing application-owned JobOutboxRelay/EventOutboxRelay loop가 database available_at 이후에만 publish하므로 process restart에도 delay가 남습니다. 0 delay는 immediate stage를 쓰고, one-time schedule은 366일 이하입니다. event schedule은 Kafka retry header, source offset commit 또는 DLQ routing을 자동화하지 않습니다. OutboxPriority(0-255)는 opt-in PostgreSQL local relay ordering이며, same kind/destination에서 higher value를 먼저 claim하고 equal priority는 durable FIFO order를 유지합니다. 이는 broker priority, fairness, global rate limit이 아니므로 continuous high priority traffic의 starvation policy는 application이 정합니다. 상세 결정은 ADR 0028을 따릅니다.
  • rustee-jobs-cron-sqlx는 typed job payload, cron expression과 durable IANA RecurringJobTimeZone을 PostgreSQL에 등록합니다. RecurringJob::new는 UTC default이고 with_time_zone으로 business zone을 명시합니다. application-owned supervisor가 fire_due(RecurringJobFireLimit)를 호출하면 due row를 FOR UPDATE SKIP LOCKED로 잠그고, fresh job ID와 UTC occurrence idempotency key를 가진 envelope을 outbox에 stage한 뒤 next run을 같은 transaction에서 갱신합니다. shutdown 또는 transaction failure는 둘 다 rollback하므로 memory timer나 broker와의 dual write가 생기지 않습니다. forward DST gap은 skip하고 backward overlap은 earlier UTC occurrence만 한 번 stage합니다. late run은 모든 missed tick을 replay하지 않고 schedule당 한 번만 stage한 뒤 database clock 다음 occurrence로 이동합니다. RecurringJobRateLimit은 shared key의 PostgreSQL-clock fixed window를 같은 transaction에서 consume합니다. capacity가 없으면 outbox row를 만들지 않고 next window boundary로 defer하며, 같은 key의 capacity/window drift는 registration conflict입니다. time-zone drift도 definition conflict입니다. 이는 Redis HTTP rate-limit store와 별도 경계입니다. RecurringJobFireObserver와 optional rustee-jobs-cron-observability는 fixed terminal outcome, aggregate claimed/staged/rate-limited count와 global duration만 관측하며, Prometheus helper는 explicit no-store response만 만듭니다. 0003_rustee_recurring_job_time_zone.sql은 base migration 뒤 적용하고 governor deployment는 optional 0002 뒤 적용하며 existing row는 UTC로 보존합니다. bundled tzdb 갱신은 affected schedule inventory와 DST contract를 재검증하는 deployment gate입니다. holiday calendar, broker priority, tenant fairness, daily quota와 external-provider exactly-once quota는 이 crate 범위 밖입니다. 상세 결정은 ADR 0029, ADR 0030, ADR 0031과 ADR 0033을 따릅니다.
  • JobRegistry는 startup에 registered typed handler를 stable job name으로 고정합니다. duplicate/invalid name은 시작을 거부하고, provider-observed attempt와 optional JobTraceContext를 typed JobContext에 주입합니다. default register는 strict current-version decode를 쓰고, older job payload가 필요한 handler만 register_with_upcaster와 explicit JobUpcaster를 사용합니다. newer producer version은 거부합니다. JetStreamWorker::run_registry_until과 RedisStreamsWorker::run_registry_until은 unknown/malformed envelope을 retry 없이 durable DLQ route로 처리하고 registered handler failure만 retry policy로 처리합니다.
  • MongoDB와 PostgreSQL 이외 SQL backend의 outbox helper는 각 transaction 모델을 실제 backend contract로 검증한 뒤 별도 integration crate로 추가합니다.

Outbox relay metric export

rustee-outbox-observability-prometheus는 application-owned OutboxRelayMetrics snapshot을 Prometheus text 0.0.4와 Cache-Control: no-store로 인코드합니다. metrics_response(&metrics)는 convenience HTTP response일 뿐 global registry, listener 또는 automatic /metrics route를 만들지 않습니다. application은 protected 또는 network-isolated scrape route에 명시적으로 mount합니다.

exporter는 rustee_outbox_relay_passes_total, in-flight gauge, fixed event/job kind와 succeeded/failed/abandoned outcome, claimed/published/retry_scheduled/lease_lost row counter, global duration histogram만 냅니다. destination, message ID, payload, broker endpoint, tenant, credential와 raw error는 label이나 metric value가 아닙니다. alert owner는 sustained failure/abandon, retry-scheduled growth, claimed-published gap 또는 lease loss를 deployment의 broker/DLQ signal과 함께 판단하며 framework가 universal threshold나 automatic replay를 정하지 않습니다.

Worker 운영 규칙

  • worker는 HTTP server와 독립된 process로 실행할 수 있어야 합니다. 같은 binary라면 명시적인 worker mode를 사용합니다.
  • queue마다 local concurrency와 prefetch를 제한해 downstream database/API가 과부하되지 않게 합니다.
  • observer event는 provider, 안전하게 읽은 attempt, settlement outcome, duration을 전달합니다. JobMetrics는 provider/outcome과 global duration만 집계하고, job ID/type은 trace/log correlation에만 씁니다. queue route, payload, receipt handle, idempotency key, trace carrier와 raw broker/handler error는 기본 metric에 넣지 않습니다.
  • readiness는 broker 연결만이 아니라 configured stream/consumer와 worker registration 상태까지 확인합니다.
  • DLQ backlog, retry rate, oldest pending age, processing latency를 운영 지표로 노출합니다. outbox relay는 rustee-outbox-observability::OutboxRelayMetrics로 event/job kind와 succeeded/failed/abandoned outcome, claimed/published/retry_scheduled/lease_lost, in-flight/global duration을 live export하고 final RelayLoopReport로 drain 결과를 확인합니다. destination/message ID/payload/broker endpoint/raw error는 label로 쓰지 않습니다. Redis Streams에는 retry zset/hash cardinality와 XAUTOCLAIM missing-entry failure도 추가합니다.
  • RabbitMQ는 publisher confirm, consumer ack/reject, x-acquired-count, native delayed message count와 delivery limit/DLQ 상태를, SQS는 visibility timeout, receive count, redrive DLQ age를 추가로 관측합니다.

DLQ 조사와 replay runbook

Rustee는 DLQ 메시지를 자동으로 원래 queue에 복사하는 replay API를 제공하지 않습니다. broker deduplication ID를 재사용해 replay가 사라지거나, 이미 성공한 external side effect가 다시 실행되는 일을 막기 위해서입니다. replay는 application-owned approval 절차이며 새 delivery로만 발행합니다.

  1. worker를 멈추기 전에 대상 DLQ entry를 snapshot하고 provider, observed attempt, source/DLQ route, 발견 시각, envelope checksum과 incident ticket을 기록합니다. payload와 receipt handle은 일반 log나 metric에 복사하지 않습니다.
  2. unknown/malformed job이면 source payload를 변경하지 않고 격리합니다. 등록 handler, schema/upcaster, deployment configuration을 수정해 typed decode가 가능해진 뒤에만 재검토합니다.
  3. handler가 시작했을 수 있는 delivery는 application idempotency ledger 또는 external provider receipt로 side effect 완료 여부를 먼저 확인합니다. idempotency key가 없거나 완료 상태를 판정할 수 없으면 자동 replay하지 않고 보상 또는 명시적 operator approval을 사용합니다.
  4. approved replay는 typed payload를 현재 version으로 decode 또는 explicit upcast한 뒤 새 JobEnvelope와 새 JobId로 만듭니다. original idempotency key는 유지해 application/external deduplication이 계속 작동하게 하고, provider attempt는 1부터 다시 시작합니다. 이전 trace carrier와 broker delivery handle은 재사용하지 않습니다.
  5. application의 JobClient와 해당 provider publisher로 source route에 confirmed enqueue합니다. raw DLQ body를 broker API로 직접 copy하거나 DLQ consumer가 자기 자신을 자동 replay하게 만들지 않습니다.
  6. 새 job ID, original DLQ record, approval identity를 application audit store에 연결하고 acknowledged/retried/dead_lettered outcome, source/DLQ backlog, external idempotency receipt를 확인합니다. 결과가 확정된 뒤에만 DLQ retention/discard policy를 적용합니다.
ProviderDLQ에서 조사할 보존 정보승인된 replay 경로
NATS JetStreamoriginal envelope bytes, Rustee-Delivery-Attempt header와 가능한 job ID message IDtyped decode 후 JetStreamPublisher로 source subject에 acknowledged publish
Redis Streamspayload, cumulative attempt, source_entry_idtyped decode 후 RedisStreamsPublisher로 source stream에 XADD
RabbitMQoriginal envelope body와 direct-DLQ message IDtyped decode 후 RabbitMqPublisher의 confirm route로 source exchange/routing key에 publish
Amazon SQSdirect-DLQ message body와 operational receive/age metadatatyped decode 후 SqsPublisher로 source queue에 send; FIFO는 새 job ID deduplication ID를 사용

DLQ는 durable investigation queue이지 immutable audit ledger가 아닙니다. retention, encryption/KMS, access control, PII redaction, approval identity와 completed side-effect receipt는 application과 deployment audit store가 관리합니다.

의도적으로 제공하지 않는 것

  • 성공 side effect가 단 한 번만 일어난다는 exactly-once 실행 보장
  • provider 별 ordering, visibility timeout, partitioning을 숨기는 공통 raw queue API
  • HTTP request를 background task로 몰래 전환하는 middleware
  • unbounded retry, 자동 DLQ replay, 운영자의 승인 없는 poison-message discard
  • job payload에 HTTP request/response, database connection, authentication credential를 직렬화하는 편의 API
  • Kafka의 topic, partition, offset, consumer group, replay를 job queue로 가장하는 API
