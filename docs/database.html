Database Support

선택은 열어 두고, 운영 경로는 분명하게

Rustee는 데이터베이스를 필수 core 기능으로 만들지 않습니다. 대신 연결 풀을 안전하게 주입하고, SQLx를 첫 공식 통합 경로로 제공하며, ORM과 migration 도구는 팀의 요구에 맞게 선택할 수 있게 합니다.

첫 공식 경로: SQLx

Rustee는 async Tokio 기반과 잘 맞고 SQL을 숨기지 않는 SQLx를 첫 공식 integration 대상으로 삼습니다. SQLx는 PostgreSQL, MySQL/MariaDB, SQLite 풀과 타입 기반 row 변환을 제공하며, 선택하면 compile-time query 검증도 사용할 수 있습니다. Rustee는 Stage 5에서 선택적 rustee-sqlx crate를 제공합니다. 현재 공식 지원선은 PostgreSQL이며 SQLite는 opt-in candidate입니다. MySQL/MariaDB feature는 upstream RSA 의존성의 무패치 security advisory가 해소될 때까지 제공하지 않습니다. rustee-auth-sqlx는 이 pool 위에서 keyed API-key fingerprint record와 successful-auth audit을 제공하는 optional identity adapter입니다. PostgreSQL 16 CI contract는 bounded pool connect, readiness query, simple query와 pool close, tenant-scoped transaction과 row-level security의 read/write 격리, API-key active/revoked/expiry/rotation/audit transaction을 확인합니다. CI는 database 중단 중 500ms initial-pool deadline의 credential/endpoint-free failure를 확인하고 restart 뒤 SQLx, API-key store, outbox, AI audit/usage ledger, checkpoint suite를 다시 실행합니다.

rustee-sqlx는 rustee-core의 의존성이 아닙니다. backend는 PostgreSQL과 SQLite feature로 분리하고, SQLx의 pool과 error 타입을 불필요하게 감싸거나 대체하지 않습니다.

다른 toolkit과 ORM

선택지 권장 상황 Rustee와의 결합
SQLx SQL 제어권, async 처리, 단순하고 투명한 의존성을 원하는 서비스 첫 공식 integration. pool을 AppState에 넣어 사용합니다.
SeaORM entity, relation, CRUD 중심의 async ORM 생산성이 중요한 서비스 DatabaseConnection을 상태로 주입하는 공식 recipe를 제공합니다. core 변경은 없습니다.
Diesel / diesel-async 강한 schema/query DSL 검증 또는 기존 Diesel 자산을 활용하는 서비스 async pool/connection을 상태로 주입합니다. sync Diesel 연결을 async handler에서 직접 실행하는 API는 제공하지 않습니다.
MongoDB Rust driver 문서 모델, aggregation, replica set, change stream이 도메인 요구에 맞는 서비스 별도 MongoDB integration에서 driver Client를 상태로 주입합니다.

특정 ORM을 편하게 쓰게 하는 adapter는 사용 사례가 축적된 뒤 별도 crate로 추가합니다. 처음부터 Rustee 전용 repository trait를 만들면 ORM의 표현력과 데이터베이스 고유 기능을 잃기 쉽습니다.

권장 애플리케이션 구조

use rustee::{App, Json, Path, State};
use sqlx::{postgres::PgPoolOptions, PgPool};

#[derive(Clone)]
struct AppState {
    db: PgPool,
}

#[tokio::main]
async fn main() -> rustee::Result<()> {
    let db = PgPoolOptions::new()
        .max_connections(20)
        .connect(&std::env::var("DATABASE_URL")?)
        .await?;

    let app = App::new()
        .get("/users/:id", get_user)
        .with_state(AppState { db });

    rustee::serve("127.0.0.1:3000", app).await
}

async fn get_user(
    State(state): State<AppState>,
    Path(id): Path<i64>,
) -> Result<Json<User>, AppError> {
    let user = find_user(&state.db, id).await?;
    Ok(Json(user))
}

위 API는 Rustee가 Stage 4와 Stage 5를 완료했을 때의 목표 형태입니다. handler는 HTTP 경계를 맡고, 쿼리와 트랜잭션은 service 또는 repository 함수에 둡니다. AppState에는 pool, 설정, 외부 client를 함께 둘 수 있지만, 요청별 mutable 상태를 넣지 않습니다.

트랜잭션 정책

  • 트랜잭션은 use case 시작점에서 명시적으로 열고, 필요한 repository 함수에 mutable 참조로 전달합니다.
  • Rustee는 모든 요청을 자동으로 transaction으로 감싸지 않습니다. 읽기 전용 요청, streaming, 외부 API 호출과 충돌하기 쉽기 때문입니다.
  • Transaction extractor는 초기 API에 넣지 않습니다. lifetime과 commit 시점이 숨겨지지 않는 명시적 API를 먼저 검증합니다.
  • PostgreSQL tenant 격리는 begin_tenant_transaction과 application-owned RLS policy로 제공합니다. read/write 분리와 transaction retry는 별도 enterprise integration에서 확장합니다.

PostgreSQL transactional outbox

rustee-outbox-sqlx는 event와 durable job을 business row와 같은 PostgreSQL transaction에 stage하는 선택적 adapter입니다. 제공된 0001_rustee_outbox.sql migration과 forward-only priority upgrade 0003_rustee_outbox_priority.sql은 application의 배포 migration에 넣습니다. HTTP startup에서 schema를 만들지 않습니다. relay task, readiness, metric export, log와 supervisor는 application이 소유하며, 필요할 때만 explicit run_until helper에 shutdown future를 전달합니다. 

use rustee_events::EventEnvelope;
use rustee_outbox_sqlx::{OutboxDestination, OutboxMessage, PostgresOutbox};

let destination = OutboxDestination::new("orders.events")?;
let envelope = EventEnvelope::new(order_paid, order.account_id.to_string())?;
let message = OutboxMessage::event(destination.clone(), &envelope)?;

let mut transaction = pool.begin().await?;
save_order_state(&mut transaction, &order).await?;
PostgresOutbox.stage(&mut transaction, &message).await?;
transaction.commit().await?;

// A separately scheduled EventOutboxRelay publishes only `orders.events` rows.
// It confirms the row only after Kafka reports broker acknowledgement.
  • row는 kind + destination + source message ID unique constraint로 중복 stage를 억제합니다. request retry에서 같은 event/job ID를 재사용하는 정책은 application이 결정합니다.
  • JobSchedule::after/stage_job_after와 EventSchedule::after/stage_event_after는 각각 durable job/event를 PostgreSQL clock 기준으로 0보다 크고 366일 이하의 available_at에 stage합니다. existing JobOutboxRelay/EventOutboxRelay loop는 due row만 lease하므로 별도 memory scheduler가 필요하지 않습니다. duplicate stage는 기존 availability를 바꾸지 않습니다. event delay는 provider-specific retry header나 source offset commit을 포함하지 않습니다.
  • rustee-events-kafka-sqlx의 separate 0001_rustee_kafka_delayed_retries.sql migration은 Kafka source topic/partition/offset, next retry attempt, stored retry topic, sanitized failure kind, key/payload, database-clock availability와 relay lease/confirmation을 보관합니다. source tuple plus retry attempt unique constraint가 consumer commit 재시도 중 같은 delayed retry intent를 하나로 유지합니다. PostgresKafkaDelayedRetryRouter가 insert를 성공한 뒤에만 source offset commit이 진행되며, PostgresKafkaDelayedRetryRelay는 due row만 SKIP LOCKED로 claim해 Kafka broker acknowledgement 후 published_at을 기록합니다. readiness(KafkaDelayedRetryReadinessConfig)은 retry table select와 retry/DLQ topic metadata를 concurrent bounded check로 확인하고, run_until(KafkaDelayedRetryRelayLoopConfig, shutdown)은 one-pass relay를 application supervisor에서 반복하며 empty pass만 bounded하게 wait합니다. Kafka acknowledgement와 database confirmation은 atomic하지 않아 duplicate publish가 가능하며 event consumer idempotency는 필수입니다.
  • OutboxPriority는 stage 전 0-255 relay preference를 저장합니다. default 0은 ordinary row의 existing FIFO behavior를 유지하며, one kind/destination의 eligible row는 higher priority, then created_at, then row ID로 claim과 relay return order를 정합니다. priority는 broker delivery order, fairness, tenant policy나 global rate limit을 보장하지 않습니다.
  • rustee-jobs-cron-sqlx는 0001_rustee_recurring_jobs.sql migration으로 typed job payload, cron expression과 next run을 저장합니다. 0002_rustee_recurring_job_rate_governor.sql은 opt-in shared-key fixed-window columns와 one-row current-window state를 forward-only로 추가하고, 0003_rustee_recurring_job_time_zone.sql은 existing row를 UTC로 유지하며 durable IANA time_zone을 추가합니다. RecurringJob::new는 UTC default이고 with_time_zone(RecurringJobTimeZone)으로 business zone을 명시합니다. forward DST gap은 skip하고 backward overlap은 earlier UTC occurrence만 fire합니다. PostgresRecurringJobs::register는 application-owned key의 exact duplicate만 accept하고 time-zone drift를 포함한 definition drift를 거부하며, shared governor key의 capacity/window drift도 explicit conflict로 거부합니다. supervisor가 fire_due를 호출하면 due row lock, fresh job outbox stage와 next occurrence update를 같은 transaction에서 처리합니다. governor capacity가 없으면 outbox 없이 next window boundary로 defer합니다. optional RecurringJobFireObserver는 cancellation-safe이며 separate collector/exporter는 fixed outcome, aggregate count와 global duration만 노출합니다. holiday calendar, catch-up replay, tenant fairness, daily quota와 external-provider quota는 application이 정합니다.
  • relay는 destination과 kind별로 FOR UPDATE SKIP LOCKED lease를 잡고, broker 성공 뒤에만 publish confirmation을 기록합니다. process crash, lease loss 또는 confirmation failure 뒤에는 같은 message ID가 다시 publish될 수 있습니다.
  • EventOutboxRelay와 JobOutboxRelay의 relay_once는 한 번의 bounded pass만 실행합니다. explicit run_until(RelayLoopConfig, shutdown)은 empty pass 뒤에만 bounded idle delay를 기다리고, shutdown을 새 pass 전 또는 idle wait 중에 반영합니다. 이미 lease한 pass는 끝낸 뒤 멈추며, process task를 강제로 abort하면 lease expiry 뒤 duplicate publish가 가능하므로 graceful shutdown을 사용합니다.
  • run_until은 completed pass의 RelayLoopReport(pass, claimed, published, retry_scheduled, lease_lost)를 반환합니다. 각 relay_once pass는 cancellation-safe OutboxRelayObserver lifecycle을 emit하고, optional rustee-outbox-observability::OutboxRelayMetrics는 event/job kind, succeeded/failed/abandoned outcome, bounded row count와 global duration만 집계합니다. destination, message ID, payload, broker endpoint, raw error는 metric label에 넣지 않습니다. publisher/database 오류는 retry release 뒤 그대로 반환되므로 supervisor backoff와 incident policy는 숨겨지지 않습니다.
  • payload는 non-empty, 최대 1 MiB이며 destination, message ID/type, ordering key도 bounded합니다. 대형 payload는 object storage reference 등 application-owned pattern으로 분리합니다.
  • 이 adapter는 PostgreSQL outbox table을 tenant-facing data model로 만들지 않습니다. tenant RLS는 business table에 적용하고, relay service의 cross-tenant access, event key와 tenant authorization의 관계는 application이 명시적으로 설계합니다.
  • PostgresInbox::register는 InboxConsumer scope와 event/job ID receipt를 같은 database side-effect transaction에 기록합니다. commit된 duplicate는 side effect를 건너뛰고, rollback된 receipt는 다음 delivery가 다시 처리합니다.
  • broker transaction과 DB transaction을 하나로 합치거나 exactly-once business effect를 주장하지 않습니다. external HTTP/email side effect는 provider idempotency key 또는 별도 workflow가 필요하고 consumer scope/tenant policy는 application이 결정합니다.
use rustee_outbox_sqlx::{
    InboxConsumer, InboxDecision, InboxMessageId, PostgresInbox,
};

let mut transaction = pool.begin().await?;
match PostgresInbox.register(
    &mut transaction,
    &InboxConsumer::new("billing-projection.v1")?,
    &InboxMessageId::event(event_context.id()),
).await? {
    InboxDecision::FirstDelivery => apply_projection(&mut transaction).await?,
    InboxDecision::Duplicate => {}
}
transaction.commit().await?;
use std::time::Duration;
use rustee_jobs::JobEnvelope;
use rustee_outbox_sqlx::{
    JobSchedule, OutboxDestination, OutboxMessage, OutboxPriority, PostgresOutbox,
};

let destination = OutboxDestination::new("billing.jobs")?;
let message = OutboxMessage::job(destination, &JobEnvelope::new(send_reminder))?
    .with_priority(OutboxPriority::new(200));
let schedule = JobSchedule::after(Duration::from_secs(60 * 60))?;

let mut transaction = pool.begin().await?;
save_reminder_request(&mut transaction).await?;
PostgresOutbox.stage_job_after(&mut transaction, &message, schedule).await?;
transaction.commit().await?;

// The application-owned JobOutboxRelay loop leases this row after its database due time.
use std::sync::Arc;
use rustee_outbox_observability::OutboxRelayMetrics;
use rustee_outbox_sqlx::{JobOutboxRelay, RelayConfig, RelayLoopConfig};

let relay_metrics = OutboxRelayMetrics::new();
let relay = JobOutboxRelay::new(pool, job_publisher, destination, RelayConfig::default())
    .with_relay_observer(Arc::new(relay_metrics.clone()));
let report = relay
    .run_until(RelayLoopConfig::default(), shutdown_future)
    .await?;

// shutdown_future resolves during deployment drain. Export the live bounded metrics snapshot
// and the final RelayLoopReport counts.
// Task spawning, readiness, restart/backoff and alerting remain application-owned.

PostgreSQL tenant RLS

rustee-tenant::TenantContext는 verified identity 또는 trusted server-side resolver만 만든 scope입니다. begin_tenant_transaction은 이 값을 PostgreSQL의 transaction-local rustee.tenant_id setting으로 넣습니다. query가 범위를 잊어도 database policy가 read와 write를 막게 하려면 application migration이 RLS와 runtime role을 함께 정의해야 합니다. 

use rustee_sqlx::{begin_tenant_transaction, PgPool, TenantContext};

async fn list_projects(pool: &PgPool, tenant: &TenantContext) -> Result<Vec<Project>, sqlx::Error> {
    let mut transaction = begin_tenant_transaction(pool, tenant).await?;
    let projects = sqlx::query_as!(Project, "SELECT id, name FROM project ORDER BY name")
        .fetch_all(&mut *transaction)
        .await?;
    transaction.commit().await?;
    Ok(projects)
}
ALTER TABLE project ENABLE ROW LEVEL SECURITY;
ALTER TABLE project FORCE ROW LEVEL SECURITY;
CREATE POLICY project_tenant_scope ON project
  FOR ALL TO app_runtime
  USING (tenant_id = current_setting('rustee.tenant_id', true))
  WITH CHECK (tenant_id = current_setting('rustee.tenant_id', true));

superuser, BYPASSRLS role, policy owner configuration, direct raw transaction 또는 migration job은 이 경계를 우회할 수 있습니다. application은 tenant-facing query를 RLS가 적용되는 non-superuser runtime role로 실행하고, 모든 protected table에 같은 migration policy를 적용해야 합니다. Rustee는 schema migration을 자동 생성하거나 MongoDB에 PostgreSQL RLS와 동등한 보장을 주장하지 않습니다.

Migration과 운영

production 서버 시작 시 migration을 자동 실행하지 않습니다. 여러 인스턴스가 동시에 시작하거나 장시간 lock이 필요한 변경이 배포 가용성을 해칠 수 있습니다.

  1. migration은 SQLx CLI, SeaORM migration, Diesel migration 등 선택한 도구로 작성합니다.
  2. rustee-outbox-sqlx를 쓰면 crate의 0001_rustee_outbox.sql, 0002_rustee_inbox.sql과 priority upgrade 0003_rustee_outbox_priority.sql을 application migration set에 순서대로 포함하고, relay/consumer runtime보다 먼저 배포합니다. recurring job도 쓰면 뒤이어 rustee-jobs-cron-sqlx의 0001_rustee_recurring_jobs.sql을 적용합니다. scheduler governor를 쓰거나 scheduler crate를 governor-capable version으로 올리면 그 다음 0002_rustee_recurring_job_rate_governor.sql을 적용한 뒤 runtime을 배포합니다. Kafka delayed failure routing을 쓰면 rustee-events-kafka-sqlx의 0001_rustee_kafka_delayed_retries.sql을 consumer runtime보다 먼저 적용하고 application supervisor에 relay loop와 graceful shutdown을 명시합니다. 이미 적용한 migration을 수정하지 않고 모두 forward-only migration으로 추가합니다.
  3. CI에서 새 migration과 query metadata를 검증합니다. SQLx compile-time query를 쓰면 cargo sqlx prepare --check --workspace를 사용합니다.
  4. 배포 pipeline의 단일 migration job이 schema를 먼저 전진시킵니다.
  5. 새 서버 인스턴스는 pool 연결과 짧은 query를 포함한 readiness check를 통과한 뒤 트래픽을 받습니다.

하위 호환 schema 변경, backfill, 대용량 index 생성 같은 배포 규칙은 Stage 5의 운영 가이드에 포함합니다.

다음 구현 순서

  1. Stage 1-4에서 State, error 변환, extractor와 통합 테스트 경계를 안정화합니다.
  2. Stage 5와 Stage 9에서 PostgreSQL + SQLx와 rustee-outbox-sqlx를 구현했고, PostgreSQL 16 container에서 connection/readiness/basic query, tenant RLS read/write isolation, outbox transaction visibility/deduplication/retry lease, delayed-job invisibility/due release와 inbox rollback/commit duplicate-suppression contract를 실행합니다. stopped database에서 500ms initial pool failure가 credential/endpoint-free인지, restart 뒤 SQLx/outbox/AI audit/usage ledger/checkpoint suite가 회복되는지도 CI가 확인합니다.
  3. 동일한 상태 주입 방식으로 SQLite feature와 SeaORM/Diesel recipes를 검증합니다. MySQL/MariaDB는 upstream security advisory가 패치된 driver line, 실제 backend contract, 새 ADR이 함께 준비될 때만 다시 candidate로 검토합니다.
  4. Stage 10에서 MongoDB tenant isolation model, read/write split, retry 정책을 실제 workload와 함께 별도 release gate로 확장합니다.

Redis와의 구분

Redis는 이 문서의 관계형 database integration과 별도 경계로 관리합니다. Redis를 cache, session, rate limit, message 전달에 쓸 때의 client, TTL, 장애 정책은 Redis와 상태 저장소를 기준으로 합니다.

MongoDB와의 구분

MongoDB는 SQLx가 대상으로 삼는 관계형 database가 아니라 BSON 문서와 collection을 중심으로 한 별도 integration입니다. driver client, document model, transaction, change stream, durable checkpoint와 tenant BSON boundary 정책은 MongoDB 문서 저장소를 기준으로 합니다.
