Database Support

Keep the Choice Open, Make Operations Explicit

Database access is not a mandatory core feature. Rustee safely injects connection pools, uses SQLx as its first official relational integration path, and leaves ORM and migration-tool choices to the application.

Support Model

Area Rustee owns Application owns
Connections and pools State<AppState> injection and optional SQLx helpers Driver choice, URLs and secrets, pool sizing, and timeouts
Queries and models HTTP handler and error-conversion boundary SQLx, SeaORM, Diesel, or a repository design
Transactions Explicit transaction helpers and PostgreSQL tenant-RLS integration Use-case boundaries, commit/rollback policy, and RLS schema/runtime roles
API-key persistence Optional PostgreSQL fingerprint records, readiness, rotation, revocation, and success audit Migrations, peppers/KMS, retention, backup, and recovery policy
Transactional outbox PostgreSQL staging, leasing, relay helpers, delays, and recurring-job materialization Migrations, relay supervision, destination policy, and consumer idempotency
Migrations Deployment and readiness guidance Tool selection and CI/CD execution

Official Path: SQLx

rustee-sqlx is an optional integration, not a dependency of rustee-core. It preserves SQLx pool and driver error types for trusted handling while initial connection display and debug diagnostics expose only a safe category. PostgreSQL is the current official support line. SQLite is an opt-in candidate behind the sqlite feature with explicit pool connection and readiness helpers, exercised against an in-memory database in CI; it does not include PostgreSQL tenant-RLS or outbox behavior. MySQL/MariaDB is not exposed while an upstream RSA dependency has an unresolved unpatched security advisory. 

[dependencies]
rustee-sqlx = { version = "0.1", features = ["sqlite"] }

PostgreSQL 16 contract tests cover bounded pool connection, readiness with an application-supplied positive deadline, simple queries, pool close, tenant-scoped read/write isolation, API-key rotation and audit behavior, and recovery after an outage. Application code still owns pool settings, credentials, schema, and deployment topology. When using PoolConfig, set positive connection and timeout values and keep the minimum connection count at or below the maximum; invalid values fail before a connection is attempted. 

use rustee::{App, Json, Path, State};
use sqlx::{postgres::PgPoolOptions, PgPool};

#[derive(Clone)]
struct AppState { db: PgPool }

async fn get_user(
    State(state): State<AppState>,
    Path(id): Path<i64>,
) -> Result<Json<User>, AppError> {
    Ok(Json(find_user(&state.db, id).await?))
}

Handlers own the HTTP boundary. Queries and transactions belong in explicit service or repository functions. Shared application state may include pools, configuration, and external clients, but not request-scoped mutable state.

ORM Coexistence

  • SQLx: preferred when a service needs direct SQL control and transparent async dependencies.
  • SeaORM: inject DatabaseConnection into state when entity, relation, and CRUD productivity are the priority.
  • Diesel or diesel-async: inject an async pool or connection; do not run synchronous Diesel connections directly in async handlers.
  • MongoDB: use the separate MongoDB integration and inject the official driver's Client.

Rustee will add ORM-specific adapters only after repeated use cases justify them. A framework-owned repository trait would hide database-specific capability and reduce ORM expressiveness.

Transaction and Tenant Rules

  • Open a transaction explicitly at the use-case boundary and pass it to the repository functions that require it.
  • Rustee never wraps every request in a transaction; read-only requests, streaming, and external calls do not share one safe default.
  • A Transaction extractor is intentionally absent until lifetime and commit semantics can remain explicit.
  • begin_tenant_transaction places verified, NUL-free TenantContext in a transaction-local PostgreSQL setting. Application-owned RLS policies enforce the actual read/write boundary.
  • Read/write splitting and transaction retry require separate enterprise contracts rather than implicit behavior.

PostgreSQL Transactional Outbox

rustee-outbox-sqlx optionally stages an event or durable job in the same PostgreSQL transaction as business state. Deployment runs the supplied forward-only migrations; HTTP startup never creates schemas. An application-owned relay leases due rows and confirms them only after broker acknowledgement. Immediate and delayed staging, inbox receipt registration, storage, and relay errors expose content-free categories by default while retaining trusted database or publisher sources for application handling. Staged and leased-message debug output redacts identifiers, destinations, routing metadata, payloads, and lease capabilities.

  • Unique kind + destination + source message ID constraints suppress repeated staging. The application selects source IDs for request retries.
  • One-time jobs and events can be staged with an available_at time based on the PostgreSQL clock. Relays claim only due rows.
  • Outbox priority is a local relay preference, not a broker ordering, fairness, tenant-policy, or global-rate-limit guarantee.
  • PostgresInbox records a consumer receipt with a database side effect. Its durable inbox ledger is maintained separately from outbox staging and relay behavior while the root API remains stable. It protects database effects from committed duplicates, not arbitrary external effects.
  • Database and broker confirmation are not atomic. Crashes and confirmation failures can republish a message, so consumers must be idempotent.
  • Relay loops, readiness routes, metrics routes, supervision, backoff, alerts, and payload storage policy remain application-owned.

Migration and Release Boundary

Schema changes, indexes, RLS policy, migrations, credentials, backups, and database outage recovery are deployment responsibilities. Rustee documents and tests the integration contract but does not execute production migrations at startup.

Use testing guidance, the support matrix, and the qualification register before calling a provider or topology release-qualified.
