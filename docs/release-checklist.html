Release Checklist

재현 가능한 소스 증거와 승인된 배포를 분리합니다

이 체크리스트는 Rustee의 release owner가 tag와 publish 전에 실행하는 절차입니다. CI 통과, source package 생성, registry publish와 지원 등급 선언은 서로 다른 증거이므로 하나의 green check로 취급하지 않습니다.

현재 기준선

2026-08-04 현재 main의 첫 intentional source baseline commit은 존재하지만, release tag와 registry publish record는 없습니다. 아래 목록은 source baseline을 official release record로 승격하기 위한 절차입니다. v0.1.0 tag와 publish 전에는 semver diff, Supported 또는 framework v1 안정성 약속을 선언하지 않습니다.

release 범위와 지원 단계는 출하 계획과 지원 정책, publish 대상은 release inventory, 미해결 증거는 구현 계획 재검토를 우선합니다. 이 문서는 그 결정을 실제 출하 절차로 번역할 뿐입니다.

1. 범위와 변경 승인

  1. release version, tag 이름, 대상 crate와 명시적으로 제외한 crate를 확정하고 inventory의 package metadata와 대조합니다.
  2. 변경 범위, breaking change, migration 영향, MSRV 영향, 새 feature flag와 지원 등급 변경을 release note에 기록합니다.
  3. public facade와 publishable leaf crate의 API를 human review합니다. prior tag 또는 published version이 있을 때만 semver comparison을 release gate로 실행합니다.
  4. API, proxy trust, lifecycle, security, provider support 범위가 바뀌었다면 관련 HTML 문서와 ADR을 같은 변경에 갱신합니다.

2. 소스 preflight

release candidate는 clean worktree와 intended commit에서 다음 검증을 통과해야 합니다.

cargo +1.94.1 fmt --all --check
cargo +1.94.1 test --workspace --offline
cargo +1.94.1 clippy --workspace --all-targets --offline -- -D warnings
node scripts/check-html-links.mjs
node scripts/check-release-inventory.mjs
node scripts/check-workflow-action-pins.mjs
git diff --check
node scripts/package-release-candidates.mjs --offline

container-backed provider suite와 live provider suite는 credentials, billable cost, external topology를 요구할 수 있습니다. 이들은 skip을 green으로 해석하지 않고, target support level에 필요한 pinned CI evidence 또는 별도 승인된 qualification record로 확인합니다.

2026-08-04에 실행한 node scripts/package-release-candidates.mjs --offline --allow-dirty는 현재 75개 workspace package 중 72개 publish candidate와 3개 workspace-only package를 대조하고, 72개 inventory-approved source archive를 조립했습니다. 이 helper는 publish = false package를 제외하고 stale archive를 제거한 뒤 inventory와 정확히 같은 archive 집합인지 확인합니다. 이는 dirty worktree의 점검일 뿐 clean commit, tag, registry publish, provenance 또는 release approval의 증거가 아닙니다.

3. tag qualification

  1. preflight가 통과한 exact commit을 tag로 고정하고, tag가 가리키는 commit과 release note의 version을 다시 대조합니다.
  2. release qualification workflow에서 stable format/lint/test/doctest, HTML/inventory와 workflow action SHA pin 검증, native Kafka compile profile, publish-candidate source archive, checksum, CycloneDX SBOM과 가능한 provenance artifact를 생성합니다.
  3. 각 source package의 SHA-256, SBOM, workflow run, dependency advisory 결과와 허용된 exception 유무를 release record에 연결합니다.
  4. artifact attestation은 source artifact의 provenance를 보강하지만 crates.io upload identity나 publish 승인을 대신하지 않는다는 점을 기록합니다.

4. publish와 사후 확인

  1. registry credential owner가 승인한 순서로 publishable crate를 업로드합니다. workspace-only crate는 절대 publish하지 않습니다.
  2. registry에서 각 version, checksum, dependency metadata, docs/example visibility를 확인하고 생성한 source package와 대조합니다. 첫 release 전에는 local path dependency가 registry에 없으므로 tag 단계에서 cargo package의 unpack-and-compile verification을 주장하지 않습니다. dependency publish 뒤 node scripts/verify-published-release-candidates.mjs로 registry source consumer compile verification을 실행해 그 경계를 별도로 기록합니다.
  3. release note, migration guidance, known limitation과 support matrix를 publication 결과에 맞춰 갱신합니다.
  4. rollback이 registry unpublish로 가능하다고 가정하지 않습니다. post-publish defect는 corrected release, deprecation 또는 advisory 절차로 처리합니다.

중단 조건

  • clean preflight, required CI, package inventory, advisory/license policy 중 하나라도 실패하면 tag나 publish를 진행하지 않습니다.
  • 지원 등급을 올리려는데 real backend failure, recovery, security 또는 operator evidence가 비어 있으면 해당 adapter만 이전 등급으로 유지합니다.
  • provider credential, billing, production tenant data, TLS/IAM/ACL topology가 필요한 검증은 release owner의 명시적 승인 없이 실행하지 않습니다.
  • 실제 publish 결과나 checksum이 expected artifact와 다르면 배포를 멈추고 release record와 inventory를 먼저 바로잡습니다.
