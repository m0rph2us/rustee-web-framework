AI Operating Context

AI가 계속 참고하고 갱신해야 할 규칙

이 문서는 Rustee에서 AI 에이전트가 작업할 때 따라야 하는 운영 규칙입니다. 목표는 매 세션의 판단이 이전 설계와 이어지고, 중요한 변경이 코드에만 남지 않게 하는 것입니다.

작업 시작 체크리스트

  1. 먼저 이 문서를 읽습니다.
  2. 문서 인덱스, 출하 계획과 지원 정책, 공급망과 릴리스 증거, release inventory, 지원 현황 매트릭스, 구현 계획 재검토에서 현재 문서 맵, 지원 단계와 release blocker를 확인합니다.
  3. 새 facade나 provider를 제안하기 전, 계획 재검토의 P0→P4 순서를 확인합니다. P0/F1 뒤에는 owner가 고른 하나의 reference deployment의 qualification을 우선하며, Contract-verified code가 live-provider 또는 Supported 증거를 대신한다고 판단하지 않습니다.
  4. 작업 영역에 따라 디자인 철학, 구조, 운영과 배포, 정적 파일, 응답 압축, OpenAPI, 매크로 경계, 데이터베이스, Redis, MongoDB, 인증과 권한, Queue와 background job, Kafka event stream, event schema runbook, Kafka delayed retry runbook, AI application integration, 테스트와 검증 전략, 기능 로드맵, 관련 ADR을 읽습니다.
  5. 기존 파일과 git 상태를 확인하고, 사용자가 만든 변경을 되돌리지 않습니다.
  6. 코드를 바꾸기 전에 어떤 문서가 함께 갱신되어야 하는지 판단합니다.

문서 형식 규칙

  • 정식 문서는 HTML로 작성합니다.
  • 문서 파일은 docs/**/*.html 아래에 둡니다.
  • 문서 간 링크는 상대 경로를 사용합니다.
  • 각 문서 하단에 Last updated와 갱신 조건을 적습니다.
  • 새로운 문서가 생기면 docs/index.html에 링크를 추가합니다.

루트의 AGENTS.md는 일반 문서가 아니라 AI 에이전트가 HTML 문서를 찾기 위한 부트스트랩 파일입니다. 정식 설계 내용은 이 HTML 문서 세트를 기준으로 합니다.

MCP 구현 기준

rustee-ai-mcp은 MCP 2025-11-25 Streamable HTTP의 JSON/SSE POST-response와 local stdio client path를, rustee-mcp은 nested JSON server path를 제공합니다. AI는 endpoint trust, HTTPS/non-loopback rule, request/body/page/tool/context limit, local program/argument/inherited-environment trust, tool별 risk와 Rustee approval/audit 연결을 AI 문서, ADR 0015, ADR 0016, ADR 0017에 함께 기록해야 합니다. remote schema, description, annotation, argument와 result는 authorization이 아니며, remote call은 McpRemoteTool 또는 McpStdioRemoteTool이 ToolRegistry 승인 뒤에만 보냅니다. client SSE parser는 matching result 전 notification만 소모하며 unexpected request를 실행하지 않습니다. session-bearing request의 404는 stored session만 비우고 SessionExpired를 반환하며 tool을 자동 재실행하지 않습니다. opt-in HTTP session recovery는 bounded backoff로 replacement initialize/notification만 준비해 next explicit request에 쓰며 expired request를 replay하지 않습니다. valid event ID 뒤 opt-in SSE resumption은 bounded Last-Event-ID GET만 보내고 origin POST, tool call 또는 context request를 replay하지 않습니다. open_server_event_stream()은 initialized session에서 standalone GET notification을 명시적으로 읽고, server request/response를 거부하며 notification을 tool, context 또는 provider에 자동 전달하지 않습니다. close_session()은 session-bearing DELETE를 보내고 stateless 405도 local cleanup으로 처리합니다. stdio는 bounded newline JSON-RPC와 request/shutdown deadline을 적용하고 timeout, pipe failure, protocol/output violation 뒤 connection을 폐기합니다. 기본은 caller의 explicit restart()이고, opt-in automatic restart는 bounded backoff로 replacement handshake만 준비하며 prior tool call이나 context request를 replay하지 않습니다. Rust fixture integration test와 macOS/Windows CI matrix는 initialize/discovery/approved execution/close 공통 경로를 검증하도록 구성합니다. server는 Origin header가 있으면 explicit canonical allowlist가 없을 때 403으로 거부하고, access policy가 visible tool과 application-owned execution/idempotency context를 만들며 mandatory terminal audit을 거치게 합니다. optional McpContextProvider는 같은 authenticated request로 tenant/user/data authorization을 수행한 뒤 명시적 read-only resource/template/prompt 결과만 제공하며 model context로 자동 채택하지 않습니다. Origin allowlist는 DNS rebinding 방어이지 authentication/CORS가 아닙니다. client/server full session lifecycle, server-initiated request/sampling/elicitation, Windows advanced subprocess lifecycle와 context subscription/completion은 구현되지 않은 범위로 유지하고 완료된 것처럼 문서화하지 않습니다. optional rustee-mcp-oauth는 separate protected-resource metadata와 Bearer/scope layer를 제공하며 existing MCP tool/context policy에 verified principal만 전달합니다.

client HTTP MCP authorization은 optional rustee-ai-mcp-oauth만 담당합니다. application은 protected-resource discovery 뒤 authorization server와 scope를 선택하고, state/PKCE callback을 atomic short-TTL store에 보관한 다음 token set을 encrypted tenant/user store에 넣어야 합니다. rustee-ai-mcp-oauth-redis는 AES-256-GCM envelope, active/retired decrypt key rotation, TTL/GETDEL state consume와 token persistence를 제공하지만 tenant/user key/KMS/retention policy는 application이 소유합니다. authorization-code와 explicit refresh request는 canonical resource를 보내며 revoke는 locally resource-bound token을 선택합니다. expired tool/read/prompt request는 replay하지 않습니다. opposite-direction rustee-mcp-oauth는 canonical resource/metadata/issuer allowlist/scope configuration, public metadata GET과 Bearer challenge만 제공하고 token을 저장하지 않습니다. application verifier는 exact resource audience와 issuer/key source를 검증해 Principal만 layer에 전달해야 하며 existing MCP tool/context/tenant/approval policy가 최종 권한을 계속 소유합니다. 이 lifecycle은 MCP OAuth, ADR 0018, ADR 0019을 함께 갱신합니다.

AI evaluation/cache/batch 변경은 rustee-ai-eval, rustee-ai-cache, rustee-ai-cache-redis, rustee-ai-batch, rustee-ai-batch-jobs, rustee-ai-batch-sqlx, rustee-ai-openai과 ADR 0020, ADR 0021, ADR 0022, ADR 0023, ADR 0024, ADR 0025를 기준으로 합니다. evaluation suite 식별자와 report는 safe metadata만 담고 prompt, expected target, completion은 application-owned 실행·grader 경계를 벗어나지 않습니다. cache key는 application-generated tenant-scoped opaque fingerprint여야 하며 raw prompt를 framework가 hash하거나 pipeline에 automatic cache를 넣으면 안 됩니다. submission batch job은 tenant/policy scope, catalog ID, run key만 보관하고 ledger가 existing receipt/pending ambiguity를 보존하므로 provider submit을 automatic retry하면 안 됩니다. artifact job은 output/error role, opaque provider file ID, reconciliation key만 보관하고 loader/processor failure 뒤 Pending을 release하지 않습니다. rustee-ai-batch-sqlx은 scope/reconciliation-key reference를 restart-safe로 보존하고 same key의 다른 identity를 거부하지만, artifact authorization이나 row output을 보관하지 않습니다. application은 provider custom_id와 domain key로 row-level side effect를 멱등 처리한 뒤 검토할 수 있으며, 재처리가 안전할 때에만 새 reconciliation key를 가진 새 job을 명시적으로 schedule합니다. OpenAI adapter의 upload/download/delete는 caller가 명시적으로 고른 bounded, non-serializable input 또는 file ID에서만 수행합니다. output JSONL iterator는 safe ID/status/request ID/error code만 구조적으로 파싱하고 model body는 explicit consume 뒤에만 보입니다. built-in into_chat_response()/into_embeddings(expected_count) conversion 외의 raw JSONL/prompt와 output/error content를 automatic cache/evaluation에 주입하면 안 됩니다. tool interaction/stream은 cache 대상이 아니고, read bypass/fail-closed, write failure status, exact invalidation, key salt/version, tenant erase, encryption/TLS, retention과 stale-answer UX를 명시합니다. catalog authorization, external human 또는 LLM grader의 authorization·cost·redaction, semantic cache와 provider domain response semantics/partial result/billing reconciliation도 숨겨서 구현하면 안 됩니다. 이 범위는 AI 문서, 테스트, 로드맵, 출하 계획을 같은 변경에서 갱신합니다.

durable evaluation run은 rustee-ai-eval-jobs, rustee-ai-eval-sqlx와 ADR 0038을 추가로 따릅니다. AiEvaluationReference에는 validated scope, catalog ID, run key만 들어가고 raw suite, report, prompt, target, completion은 저장하거나 serialize하지 않습니다. worker는 authorized catalog loader 뒤에만 runner를 호출하며 ledger의 exact scope/run-key reservation이 completed result를 재사용하거나 failure를 Pending으로 남깁니다. catalog/report storage authorization, provider 또는 grader 비용, human/LLM grader governance, explicit fresh-run 승인과 reconciliation은 application이 소유합니다.

OpenAiBatchOutputExpiration은 caller가 선택한 output/error file의 provider-side whole-second expiration(1시간~30일)만 batch creation에 전달합니다. input file, artifact ledger, domain copy, billing, Pending 또는 live qualification approval을 자동 변경하지 않습니다. 실제 spend 호출은 protected openai-batch-qualification Environment의 manual workflow로만 수행하고, completed/failed/cancelled/expired artifact의 domain reconciliation은 계속 application evidence가 필요합니다.

client는 negotiated resources/prompts capability에서만 HTTP와 stdio에 동일한 bounded resources/list, resources/templates/list, resources/read, prompts/list, prompts/get API를 제공합니다. typed resource/prompt metadata, text/blob, image/audio, embedded resource와 resource link는 모두 untrusted data이며 ChatRequest, advisor, provider 또는 tool registry에 자동 전달하지 않습니다. application은 explicit URI/prompt selection, tenant authorization, user consent, classification, secret/PII redaction, modality compatibility와 tighter context/token budget을 거친 뒤에만 자체 renderer/advisor input으로 채택합니다. resource link도 자동 fetch하지 않습니다.

현재 설계 기준 요약

  • Core는 작고 안정적으로 유지합니다.
  • Tokio, Hyper, Tower와의 호환성을 기본 축으로 삼습니다.
  • 미들웨어는 Tower-compatible 구조를 우선합니다.
  • App::nest는 static non-root prefix에 Tower service를 mount하고 child URI에서 prefix를 제거합니다. child Rustee app의 RouteTemplate은 외부 full path로 유지하며 child fallback/405가 prefix 아래를 소유합니다. direct parent route가 우선하고, 여러 nest는 longest prefix가 우선합니다. parent/child StateStore는 자동 병합하지 않습니다.
  • 정적 파일은 선택적 rustee-static layer에서 explicit root와 URI prefix, weak ETag/Last-Modified conditional cache, normalized single/multipart byte-range response, opt-in precompressed Brotli/gzip variant와 bounded large-file streaming을 제공합니다. variant는 non-Range request에서만 quality negotiation으로 선택하고 Range는 identity representation으로 고정합니다. multipart input은 overlap/adjacent merge와 64 input/16 part limit를 적용합니다. streaming threshold는 maximum file admission limit를 대체하지 않으며 selected full/range representation에 적용합니다. cache policy, CDN/object storage 채택과 deployment exposure는 application 책임이며, raw filesystem path나 directory listing을 노출하지 않습니다.
  • response compression은 선택적 CompressionLayer에서 streaming gzip/Brotli negotiation으로 제공합니다. Vary: Accept-Encoding과 existing coding/no-transform/Range/HEAD bypass를 지키며, proxy/CDN가 compression을 소유하면 origin layer를 같이 켜지 않습니다.
  • rustee-test::TestApp은 opt-in with_cookie_jar()에서만 session-style valid cookie name/value를 보존합니다. Max-Age=0 deletion, fixed 64-entry/8 KiB bound, successful buffered response 뒤 atomic update와 explicit request Cookie override를 지키되, browser origin/path/secure/same-site/expiry/redirect 정책은 구현하지 않습니다. 이 경계를 넓힐 때에는 ADR 0042와 wire/browser evidence를 함께 갱신합니다.
  • rustee-openapi의 security component/requirement은 application-declared static metadata입니다. HTTP Basic/Bearer, API key, safe OpenID Connect discovery, Authorization Code/Client Credentials OAuth2 flow와 declared OAuth scope, static mutualTLS, document-wide default, anonymous alternative, explicit operation clear override를 render합니다. scheme은 requirement 전에 등록하고 header API-key name은 HTTP field-name grammar를 따라야 합니다. OAuth URL은 HTTPS 또는 loopback HTTP with no credential/query/fragment여야 하며 mutualTLS requirement는 scope를 받지 않습니다. route authentication, bearer/API-key parsing, OAuth token exchange/refresh/revocation, OIDC/session lifecycle, TLS termination, certificate validation/rotation/principal mapping 또는 tenant/scope authorization을 추론·생성하지 않습니다. runtime API-key authentication은 rustee-auth::ApiKeyLayer가 explicit header only boundary로 별도 제공하며, production store에는 HMAC-SHA-256 keyed fingerprint만 전달하고 provider persistence/rotation/audit policy를 추론하지 않습니다. legacy OAuth flow, runtime drift와 provider interoperability를 늘릴 때에는 ADR 0039, ADR 0043, ADR 0045, ADR 0046, ADR 0047, ADR 0048, ADR 0049을 함께 갱신합니다.
  • rustee-auth의 ApiKeyPepperRing/RotatingKeyedApiKeyAuthenticator는 active 뒤 최대 두 retained pepper를 rejection 때만 조회하고 provider outage에는 즉시 fail-closed 합니다. rustee-auth-sqlx는 keyed API-key fingerprint의 optional PostgreSQL record, bounded readiness, active/revoked/expiry lookup, no-overlap rotation와 successful-auth audit adapter를 제공합니다. stopped database CI는 500ms endpoint-free readiness failure와 restart requalification을 확인합니다. raw key/pepper를 저장하지 않고 KMS delivery, replacement fingerprint registration/backfill, retirement, retention, RLS와 database restore policy를 자동화하지 않습니다. 이 경계를 바꿀 때에는 ADR 0049, ADR 0050과 PostgreSQL container contract를 함께 갱신합니다.
  • 매크로는 선택 기능이며, non-macro API가 먼저 존재해야 합니다. 현재 rustee::routes!는 existing App method chain만 만들고, rustee-macros::FromHeader는 explicit header name의 one-field tuple newtype FromStr parsing만 생성합니다. handler/schema/authorization은 생성하지 않습니다. 확장 전에는 ADR 0040, ADR 0041과 compile-fail contract를 갱신합니다.
  • 엔터프라이즈 기능은 core에 밀어 넣기보다 별도 crate와 feature flag로 확장합니다.
  • 데이터베이스는 core 추상화가 아니며, SQLx는 첫 선택적 공식 통합입니다. 풀은 State<AppState>로 전달합니다. rustee-outbox-sqlx는 PostgreSQL에서 event/job envelope을 같은 transaction에 stage하고 destination별 SKIP LOCKED lease relay로 전달하며, PostgresInbox는 database side effect와 receipt를 같은 transaction에 commit합니다. cross-store exactly-once, external side-effect idempotency, tenant authorization은 추상화하지 않습니다.
  • Redis는 선택적 상태 저장소 통합이며, redis-rs ConnectionManager를 기본 client 경로로 삼습니다. rustee-rate-limit은 trusted application key resolver, fixed-window 429 response와 explicit failure policy를 제공하고 rustee-rate-limit-redis은 Lua atomic store를 제공합니다. 역할별 장애 정책은 명시합니다.
  • RedisConfig는 기본 5초의 bounded initial connect와 sanitized RedisConnectError::Connection만 제공합니다. URL과 credential은 Debug와 startup error에 노출하지 않으며, 이후 reconnect는 redis-rs ConnectionManager가 담당합니다. failover topology와 application-level retry supervisor는 deployment가 명시합니다.
  • MongoDB는 선택적 문서 database 통합이며, 공식 driver Client의 내장 pool을 사용합니다. BSON, schema evolution, change stream은 별도 운영 경계로 다룹니다. ChangeStreamCheckpointStore는 opaque resume token의 storage contract이고 rustee-mongodb-checkpoint-sqlx는 PostgreSQL BYTEA adapter, timeout-bound readiness와 opt-in database-clock writer lease를 제공합니다. durable handler success 뒤 save_while_leased로 저장하고 storage failure나 LeaseLost이면 worker를 종료합니다. owner identity, renewal scheduler, invalidation, restart/backoff와 outage policy는 자동화하지 않습니다. MongoTenantScope는 verified TenantContext를 outer-AND tenant_id filter, insert/replacement document, classic update validation과 target collection first-match aggregation pipeline에 연결합니다. 이는 MongoDB RLS가 아니므로 raw driver, aggregation의 $lookup/$unionWith, change-stream pipeline은 application의 explicit tenant condition과 access review가 필요합니다.
  • 인증과 권한은 선택적 security integration입니다. static JWT와 HTTPS JWKS bearer token은 verified scope/role/permission을 포함한 Principal로 정규화하며, JWKS는 strict algorithm/key-use filtering, bounded cache refresh, provider-unavailable 503을 유지합니다. OIDC browser login은 discovery, Code+PKCE, one-time state, nonce-bound ID token, session bridge와 Redis TTL/GETDEL transaction store까지 구현됐습니다. opaque access token은 HTTPS introspection의 active/issuer/audience/time 검증과 exp-bound SHA-256 fingerprint cache로 처리합니다. JWKS/opaque adapter의 real loopback transport outage는 credential/provider detail 없는 503으로 고정했습니다. rustee-tenant는 trusted tenant context를 security/storage에 공유하고 PostgreSQL은 transaction-local RLS read/write isolation을 확인합니다. direct permission, server-configured role-to-permission policy, tenant-match guard와 configured-host TenantResolutionLayer, MongoDB BSON read/update/delete tenant boundary는 구현됐고 external IdP revocation, MongoDB raw-query review와 outage/recovery contract는 별도 release gate로 검증합니다.
  • Queue와 background job은 선택적 worker integration입니다. at-least-once 전달, idempotent handler, retry/DLQ와 PostgreSQL outbox/inbox를 명시적으로 설계합니다. AWS SDK retry policy와 IAM/KMS/real AWS qualification은 application/deployment의 별도 release gate입니다. CI는 stopped LocalStack의 500ms failure와 restart 뒤 full recovery를 실행합니다.

rustee-jobs-redis의 publisher와 worker도 기본 5초의 command deadline을 사용하며, worker deadline은 Redis blocking read보다 길어야 합니다. readiness, publish, receive, reclaim, retry promotion, ack/retry/DLQ settlement가 모두 같은 sanitized RedisStreamsError로 종료됩니다. Redis 7 CI는 intentional CLIENT PAUSE로 500ms deadline과 endpoint redaction을 확인합니다. connection manager reconnect, retention/replay, Cluster/Sentinel failover는 application/deployment release gate입니다.

PostgreSQL 연결 경계

rustee-sqlx::connect는 PoolConfig의 기본 5초 initial-pool deadline을 적용합니다. SQLx의 low-level error model은 유지하지만, CI는 stopped PostgreSQL에서 500ms 연결 failure가 URL credential과 endpoint를 render하지 않는지 확인하고 restart 뒤 SQLx, outbox, AI audit/usage ledger, checkpoint contracts를 재실행합니다. application이 HTTP error mapping, migration, transaction retry, external side-effect idempotency와 database recovery supervisor를 명시적으로 소유합니다.

최근 운영 경계

rustee-outbox-observability-prometheus는 application-owned OutboxRelayMetrics를 bounded Prometheus text로 노출하는 optional adapter입니다. application이 protected scrape route와 alert owner/threshold를 정하며, destination, message ID, payload, endpoint, credential와 raw error는 metric label로 내보내지 않습니다. 상세 운영 규칙은 Queue 문서와 테스트 전략을 함께 확인합니다.

External qualification

release tag/publish, named edge topology, live AI provider spend/retention, real cloud/provider credential evidence는 code task와 다른 owner action입니다. AI agent는 이를 completed로 추측하지 않고 qualification register에서 owner와 required evidence를 확인합니다. approval 전에는 deterministic/local/container contract만 갱신하고 credential, tenant data, prompt/completion, endpoint와 billing detail을 문서나 test output에 기록하지 않습니다.

first release의 local path dependency는 publish 전 registry에서 해석할 수 없습니다. 따라서 package-release-candidates.mjs가 inventory-approved source archive 집합을 확인하는 것과, publish 뒤 verify-published-release-candidates.mjs가 registry source consumer compile을 확인하는 것은 서로 다른 gate입니다. AI agent는 archive assembly만으로 registry release를 완료로 기록하거나, 아직 publish되지 않은 상태에서 consumer verifier를 실행하지 않습니다.

작업 종료 체크리스트

  1. 관련 테스트나 검증 명령을 실행합니다. 실행하지 못했다면 이유를 기록합니다.
  2. 변경한 코드와 문서가 같은 방향을 말하는지 확인합니다.
  3. 새로운 설계 결정이 생겼다면 ADR을 추가하거나 기존 ADR에 후속 결정을 연결합니다.
  4. 최종 응답에서 변경한 HTML 문서와 검증 결과를 짧게 보고합니다.
