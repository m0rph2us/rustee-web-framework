AI Maintenance Rules

Rules AI Agents Must Read and Maintain

This is the durable working context for AI-assisted changes. It defines the documents to inspect, the boundaries that must remain explicit, and the records that must change with implementation.

Before Starting Work

  1. Read this page, the relevant focused document, the architecture, the testing strategy, the support matrix, enterprise deployment readiness, and related ADRs.
  2. Inspect the current workspace implementation and tests before proposing a new abstraction or changing a contract.
  3. Identify the owner boundary: core, optional adapter, application, deployment, provider, or operator.
  4. Check whether the request affects public APIs, configuration, feature flags, release evidence, security, privacy, or operational runbooks.
  5. Prefer the existing crate and test patterns. Do not widen scope through unrelated refactoring.

Documentation Update Rules

  • Official documentation is HTML, not Markdown. Keep it in English and update it in the same change as the relevant implementation. Internal module-boundary entries must resolve to declared Rust modules; CI verifies this.
  • Update architecture for crate or layer boundaries; update focused integration documents for contract and ownership changes; update the roadmap and release plan for scope or support changes.
  • Add or amend an HTML ADR for a durable decision, rejected alternative, or newly explicit trust boundary.
  • Update examples when a public API changes and add targeted verification for every changed observable behavior. Avoid fixed counts for CI checks or test suites unless a generated verifier owns the count; describe the enforced policy instead.
  • Do not claim a named deployment's production support, external provider qualification, or exactly-once behavior without recorded evidence in that deployment's qualification register. A generic framework is deployment-ready when it supplies the documented contracts, workflows, and runbooks without assuming an adopter's account or topology. Run the verifier after changing its HTML ledger.

Current Design Baseline

  • The core is small, typed, Tower-compatible, and based on Tokio/Hyper. Optional integrations live in focused crates.
  • Storage clients and pools are application state. SQLx, Redis, MongoDB, ORMs, migration tools, and database topology are not core contracts.
  • Direct outbound HTTP adapters disable automatic redirects so a trusted configured endpoint cannot silently move to a different transport target. Applications that inject an HTTP client own its redirect policy.
  • Authentication normalizes a verified Principal; authorization, tenant isolation, resource ownership, and deployment identity policy stay distinct. Principal identity fields and authorization sets have fixed bounds, and serde restoration revalidates them before persistence or request use. Principal and authorization-policy Debug output is limited to safe aggregate counts.
  • Jobs, outbox relays, Kafka events, MongoDB change streams, and AI provider actions are at least once where a crash boundary permits duplicates. Handlers need explicit idempotency.
  • Metrics use bounded labels and do not expose secrets, payloads, IDs, endpoints, or raw errors. Exporters, scrape routes, alerts, sampling, and retention are application or deployment-owned.
  • Framework tracing uses content-free error diagnostics. Do not format raw error, err, cause, source, or failure values into tracing fields; preserve only a fixed outcome, and add separately reviewed safe metadata when it is operationally necessary.
  • Public generic types implement Debug explicitly instead of deriving it. Their diagnostics expose only reviewed safe metadata and must not delegate unknown generic fields.
  • AI features enforce final-request policy, verified context, approval, audit, redaction, and no-replay boundaries. Models, prompts, vector stores, live credentials, and domain side effects are not framework defaults.

Implementation Rules

  • Use an explicit readiness, shutdown, timeout, and failure contract for every external dependency.

Redis Cache Boundary Update

rustee-redis::cache validates a positive explicit TTL before encoding or contacting Redis. A zero TTL is a local CacheError::ZeroTtl, not a transport failure. Its explicit create-only JSON helper issues one atomic Redis SET NX EX operation and reports CacheError::EntryExists without replacing a live value. The opt-in Redis contract races two writes to the same temporary key and requires exactly one retained winner. Higher-level adapters preserve those distinctions when their own TTL policy permits them.
