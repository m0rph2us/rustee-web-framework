AI Batch Operations

Batch artifact reconciliation runbook

OpenAI Batch output/error file을 안전하게 도메인 결과로 반영하고 보존 또는 삭제를 결정하기 위한 application-owned 운영 절차입니다.

적용 범위

Rustee는 batch 제출과 artifact reservation의 멱등 경계를 제공하지만, 모델 결과의 의미와 외부 side effect의 정확성은 애플리케이션이 소유합니다. 이 문서는 rustee-ai-batch, rustee-ai-batch-jobs, rustee-ai-batch-sqlx, rustee-ai-openai을 함께 쓸 때의 최소 운영 기준입니다.

  • durable job에는 prompt, raw JSONL, model body, provider error message를 넣지 않습니다.
  • artifact ledger에는 scope, catalog ID, run key, output/error role, opaque file ID, reconciliation key만 남습니다.
  • 결과 row의 도메인 저장은 provider custom_id와 application domain idempotency key를 함께 사용합니다.
  • Pending은 실패 상태가 아니라 불명확한 상태입니다. framework가 release, replay, delete, refund를 자동 수행하지 않습니다.

정상 흐름

  1. application이 모델별 request body를 검증해 JSONL을 만들고, 명시적으로 업로드한 뒤 input file ID와 run key를 catalog/receipt에 기록합니다. Rustee ChatRequest Responses row와 non-empty ordered EmbeddingInput Embeddings row는 typed builder를 선택할 수 있지만 provider-only fields는 explicit body로 남습니다.
  2. provider batch 상태를 application scheduler가 조회합니다. 완료·실패·취소의 판단은 provider snapshot과 서비스 정책을 함께 사용합니다.
  3. output file 또는 error file을 선택하면 application이 scope, catalog ID, run key, artifact kind, file ID, 새 reconciliation key로 reference-only job을 만듭니다.
  4. worker는 durable envelope key가 reconciliation key와 정확히 같은지 확인한 뒤 PostgresAiBatchArtifactLedger을 reserve합니다.
  5. 새 Reserved attempt만 tenant authorization 뒤 file을 bounded download하고 structural JSONL parser로 row를 읽습니다. parser가 만든 response body는 application이 명시적으로 소비할 때만 접근하며, Responses row는 explicit into_chat_response() validation을, Embeddings row는 catalog의 expected input count를 주는 into_embeddings(count) validation을 선택할 수 있습니다.
  6. application processor는 row마다 domain key와 custom_id를 사용해 validation, partial-result policy, transaction, external provider idempotency를 수행합니다.
  7. 모든 의도된 row effect를 확인한 뒤에만 exact artifact reference를 record_reconciled합니다. 중복 delivery는 Reconciled을 받고 artifact를 다시 열지 않습니다.
  8. application retention policy가 허용할 때만 input/output/error file을 명시적으로 delete하고 provider acknowledgement를 기록합니다.

Pending 처리

다운로드, parser, domain processor, 또는 final record 단계에서 실패하면 reference는 Pending으로 남습니다. 같은 key의 job을 다시 보내도 ledger는 processing을 시작하지 않습니다. 이 규칙은 이미 반영된 row 또는 확인되지 않은 external side effect가 중복되는 것을 막습니다.

pending reference
  -> authorize scope and catalog ownership
  -> inspect provider batch/file availability
  -> inspect domain records keyed by (domain_key, custom_id)
  -> classify every intended row: applied, absent, rejected, or unknown
  -> resolve billing/partial-result policy when relevant
  -> either retain for manual review, or issue a new reconciliation key
  -> schedule one new reference-only artifact job

새 attempt는 기존 scope, catalog ID, run key, artifact kind, file ID를 유지할 수 있지만 reconciliation key는 새 값이어야 합니다. 기존 pending row를 update, delete, release하거나 같은 key를 재사용하지 않습니다.

Partial Result Policy

  • completed with failed rows: output/error artifact를 각각 별도 reference로 처리하고, successful row와 failed row의 도메인 policy를 분리합니다.
  • cancelled or expired: provider가 만든 partial artifact를 결과로 가정하지 않습니다. snapshot count, artifact availability, billing, 그리고 domain ledger를 확인합니다.
  • malformed or oversize JSONL: parser failure로 pending을 남기고 raw artifact를 queue/log/cache에 복사하지 않습니다. provider support 또는 explicit application export 절차를 사용합니다.
  • unknown domain outcome: provider file 재처리보다 external provider lookup 또는 manual review를 우선합니다. domain idempotency가 증명될 때만 새 attempt를 발급합니다.

Retention And Deletion

Rustee의 upload, download, delete API는 모두 caller-selected operation입니다. artifact ledger의 Reconciled은 provider file이 삭제되었거나 billing이 확정되었다는 뜻이 아닙니다.

artifact최소 확인삭제 전 판단
input filebatch receipt와 provider result discovery가 보존됨재제출, audit, legal hold, prompt retention policy
output file모든 intended row의 domain ledger와 artifact reconciliation 상태partial result, downstream export, user erase request, billing dispute window
error filefailure classification과 retry/manual-review decisionsupport investigation, error-code aggregate, user-visible remediation policy

delete 응답은 exact provider acknowledgement여야 하며, delete 실패는 queue retry로 숨기지 않습니다. application은 retention deadline, retry ownership, alert, audit record를 명시합니다.

Release Gate

  • real PostgreSQL migration, simultaneous reserve, restart, pending query, and outage/recovery contract를 실행합니다.
  • first live lifecycle check는 ignored test와 protected manual workflow .github/workflows/openai-batch-live-qualification.yml로 제공합니다. workflow는 approved boolean input, unique run key, protected openai-batch-qualification Environment의 OPENAI_API_KEY/RUSTEE_OPENAI_BATCH_MODEL secret이 모두 있을 때만 upload/submit/retrieve/cancel을 실행합니다.
  • real provider의 completed/failed/cancelled/expired/partial output/error artifact를 opt-in spend-controlled environment에서 검증합니다.
  • application domain ledger가 duplicate job, worker crash after partial rows, crash after domain commit before record_reconciled, and explicit new-key retry를 통과함을 증명합니다.
  • tenant authorization, RLS, artifact retention/delete schedule, billing reconciliation, broker DLQ/replay authority, on-call alert와 manual review owner를 release evidence로 남깁니다.

Provider Expiration

OpenAiBatchRequest::with_output_expiration(OpenAiBatchOutputExpiration)은 generated output/error file에만 one-hour through 30-day provider expiration을 명시합니다. batch creation time이 anchor이고 input file, domain copy, billing 또는 Pending record는 바꾸지 않습니다. cancelled batch는 provider가 final partial artifact를 만든 뒤에만 application retention procedure로 검토합니다.

금지 사항

  • Pending record를 generic retry worker가 자동 release 또는 overwrite하는 것
  • model output/error message/raw JSONL을 job payload, application log, response cache, evaluation report에 기본 저장하는 것
  • provider custom_id만 보고 domain write의 멱등성을 주장하는 것
  • artifact ledger completion만 보고 file deletion, billing settlement, external side effect completion을 추정하는 것
  • provider file ID를 tenant authorization 없이 직접 download하는 것
