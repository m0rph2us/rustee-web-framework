Batch Artifact Reconciliation Runbook

This runbook governs application-owned reconciliation of OpenAI Batch output and error artifacts. Rustee supplies idempotent submission and reservation boundaries; the application owns result meaning and external side effects.

Scope and Preconditions

  • Durable jobs do not contain prompts, raw JSONL, provider request bodies, or provider error messages.
  • Batch job diagnostics retain only safe outcome categories while trusted runner sources remain available to application retry and DLQ handling.
  • The artifact ledger stores only scope, catalog ID, run key, artifact role, opaque file ID, and reconciliation key.
  • Each result row combines provider custom_id with an application domain idempotency key.
  • Deployment applies AI_BATCH_ARTIFACT_LEDGER_MIGRATION_SQL and then AI_BATCH_ARTIFACT_LEDGER_IDENTIFIER_BOUND_MIGRATION_SQL. The second migration rejects legacy rows outside the bounded ASCII identifier contract; explicitly repair or remove them before readiness is declared.
  • Deployment also verifies tenant authorization/RLS and restore policy, defines artifact owners/retention/deletion approval, and defines job retry/DLQ authority.
  • Pending is ambiguity, not an ordinary failure. Rustee never automatically releases, replays, deletes, or refunds it.

Normal Flow

  1. Validate the model-specific request body, create JSONL, upload explicitly, and record the input-file ID and run key in the application catalog or receipt.
  2. Poll provider batch state through an application scheduler. Completion, failure, or cancellation is a service-policy decision based on the provider snapshot.
  3. Create a reference-only reconciliation job for an output or error file with scope, catalog ID, run key, artifact kind, file ID, and a new reconciliation key.
  4. Verify the durable envelope key matches the reconciliation key and reserve it in PostgresAiBatchArtifactLedger.
  5. Only a new Reserved attempt may authorize and download the file under bounds, then structurally parse JSONL.
  6. Apply each row using its domain key and custom_id, including domain validation, transaction, partial-result policy, and external-provider idempotency.
  7. After all intended effects are verified, record the exact artifact as reconciled. A duplicate delivery observes Reconciled and does not reopen the artifact.
  8. Delete input, output, or error files only through an explicit retention policy and record the exact provider acknowledgement.

Pending and Partial Results

  • Download, parse, processor, or final-record failure leaves the reference Pending. Re-sending the same key does not begin processing again.
  • Process output and error artifacts separately. Do not infer domain success from a completed batch or an available artifact.
  • For cancelled or expired batches, inspect provider state, artifact availability, billing, and the domain ledger before selecting a manual action.
  • Malformed or oversized JSONL stays pending; never copy raw artifacts into a queue, log, cache, or ordinary report.
  • When a domain outcome is unknown, inspect the external provider or use manual review before a new reconciliation attempt.

Retention, Qualification, and Prohibitions

  • Reconciled means only that the reference was reconciled. It does not mean the provider file was deleted, billing settled, or external effects completed.
  • Live qualification is an opt-in, spend-controlled workflow with protected credentials and a unique run key. Retain only safe identifiers, status, and timestamps as evidence.
  • Before promotion, prove PostgreSQL migration, simultaneous reservation, restart, pending query, outage/recovery, domain-ledger idempotency, RLS, DLQ authority, and on-call ownership.
  • Never automatically overwrite or release a pending record, assume provider custom_id proves domain idempotency, or download a file ID without tenant authorization.
