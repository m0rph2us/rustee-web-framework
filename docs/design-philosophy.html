Design Philosophy

Start Small, Grow Without Breaking

A new user should be able to create a first route quickly, while an experienced team can grow the same service without abandoning the core model. Rustee designs durable extension boundaries before adding convenience features.

Core Beliefs

Small, Stable Core

The core contains only framework contracts: requests, responses, handlers, extractors, state, and error conversion. Convenience belongs in optional crates or features.

Ecosystem-Compatible Abstractions

Middleware and service composition remain compatible with Tower so applications can use established Rust web ecosystem tools.

Intent Visible in Types

Request extraction, response conversion, state access, and error handling are expressed in types. Compile-time failures are preferred over hidden runtime behavior.

Progressive Exposure

Start with APIs such as App::new().get(...), then expose lower-level Service, Layer, Body, and Extension APIs only when they are needed.

Storage Choice Stays with the Application

Databases matter to services, but they are not core framework contracts. Rustee passes typed relational pools and document-database clients while the application chooses its SQL toolkit, ORM, and document model.

Explicit External State

Redis is an implementation option for caching, sessions, and rate limits, never hidden global state. Namespaces, TTLs, failure policy, and consistency boundaries stay visible in configuration.

Identity Is Separate from Authorization

Authentication establishes a request subject; authorization decides what that subject may do. A Principal-centered model preserves this distinction across OIDC, JWT, and sessions.

Honest Asynchronous Delivery

Jobs acknowledge after success and retry or move to a DLQ on failure. Rustee makes at-least-once delivery and duplicates explicit, and treats idempotency and the outbox as service design concerns.

Jobs Are Not Event Logs

RabbitMQ and SQS job delivery are not Kafka's partitioned event log. Job acknowledgment and retry remain separate from Kafka keys, offsets, and replay semantics.

AI Policy Before Provider Calls

Model output, retrieved text, and tool requests are untrusted input. Chat, RAG, and tools are composed only after tenant authorization, human approval, budget, audit, and redaction policy.

Tests Specify Observable Contracts

Fast unit tests and real HTTP and backend contracts work together. The goal is observable behavior through cancellation, failure, and feature combinations, not just line coverage.

Conservative Operational Trust

Configuration and secrets must not leak. Proxy headers are accepted only from explicitly trusted hops, and TLS, health, shutdown, and observability are service contracts decided early.

User Experience Rules

  • The first example should run in ten minutes or less.
  • A handler signature should make its behavior predictable when read.
  • Error messages should tell an early-stage Rust user what to do next.
  • Macros are optional convenience; a macro-free API is always available.
  • Defaults are safe and operations-friendly, while advanced users retain explicit control.

Operations Philosophy

Rustee is more than a router: it is a foundation for operating a service. It does not place every operational capability in the core. Request IDs, tracing, timeouts, body limits, graceful shutdown, metrics, OpenTelemetry, authentication, and rate limits are placed in clear, composable layers.

Enterprise-ready does not mean a giant default package. In Rustee it means consistent support for observability, security, configurability, extensibility, and long-term maintainability.

Explicit Non-Goals

  • Do not implement an HTTP parser or async runtime in the first release.
  • Do not make the core own an ORM, database driver, migration runner, template engine, identity provider, or deployment tool.
  • Do not hide every database behind one repository trait or active-record API.
  • Do not expose MongoDB BSON documents as the HTTP response model or generic CRUD endpoints.
  • Do not make the core own user models, password databases, a specific identity provider, or a fixed RBAC scheme.
  • Do not treat the presence of JWT claims as completed authorization or trust tenant boundaries from request headers.
  • Do not disguise Redis as an automatic HTTP cache or general distributed lock that hides consistency and failure policy.
  • Do not claim a universal Queue<T> API or exactly-once execution across brokers.
  • Do not present Kafka topics, partitions, consumer groups, offsets, or replay as a background-job queue.
  • Do not put model-provider SDKs, API keys, prompts, or vector databases in the core, and never execute a tool call without approval.
  • Do not log prompts or completions by default or rely on prompt instructions for RAG data authorization.
  • Do not substitute real transport and backend contracts with mock-only tests or hide flaky tests behind retries.
  • Do not trust all forwarded headers automatically or lock the core to one configuration format, secret manager, or cloud deployment.
  • Do not isolate framework users from the Tower, Hyper, and Tokio ecosystems.
  • Do not make dynamic magic that weakens Rust's type safety the default path.

Success Criteria

Area Criterion
First use A new user can copy the documented hello-world example and run it immediately.
Extensibility Routes, middleware, extractors, and response conversion can grow without changing the core.
Operations Shutdown, tracing, timeouts, body limits, and metrics paths are clear for production services.
Maintenance Important design decisions and their rationale remain in HTML documents and ADRs.
