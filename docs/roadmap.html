Roadmap

From MVP to Enterprise Capabilities

The roadmap grows the framework through stable contracts and explicit verification. Completion means reusable behavior, deployment handoff, documentation, and source-release evidence are all present.

How to Read This Roadmap

  • A stage establishes a boundary before adding convenience on top of it.
  • Optional integrations are not automatically supported in production; their support level is defined by the release plan and qualification register.
  • Later stages may refine an earlier contract but may not silently weaken its safety or ownership rules.

Stages

Stage Scope Exit criterion
0 Charter and support policy Design philosophy, architecture, ADR process, documentation rules, MSRV, and release criteria are agreed.
1 Workspace and core contracts Facade, request/response, handlers, extractors, errors, router, and Tower compatibility have stable tests.
2 First server MVP Tokio/Hyper serving, routes, JSON, state, graceful shutdown, and a runnable hello-world example work.

4 Developer experience Test helpers, OpenAPI metadata, macros, static content, examples, and error ergonomics have focused contracts.
5 Relational databases Optional SQLx, PostgreSQL readiness, tenant transaction/RLS boundary, outbox/inbox, and migration guidance are verified.
6 Redis state stores Optional client, cache/session/rate-limit contracts, bounded failure behavior, and Redis integration evidence are available.
7 MongoDB documents Official driver injection, tenant BSON boundary, transactions, change-stream lifecycle, and checkpoint contract are defined.
8 Authentication and authorization Principal, JWT/JWKS/OIDC/session/API-key paths, permission policy, tenant match, and fail-closed contracts are implemented.
9A Durable background jobs Typed jobs, worker lifecycle, retry/DLQ, NATS provider, outbox, delays, schedules, and targeted observability work.
9B Kafka event streaming Versioned events, manual commits, retry/DLQ, delayed retry, schemas, real-broker contracts, and replay guidance work.
9C AI application integration Provider-neutral pipelines, policy, tools, RAG, streaming, MCP, audit, evaluation, cache, batch, and deterministic tests are bounded.
10 Expansion and stabilization Provider/topology matrices, external qualification, fuzzing, platform compatibility, benchmarks, migration/release guidance, and ecosystem governance mature.

Current Direction

Core framework layers and the optional integrations named in this workspace are implemented to their documented contract boundaries. Weekly parser/extractor fuzzing and a manual route-dispatch benchmark provide repeatable stabilization inputs. The framework provides a validated HTML qualification ledger and protected live-workflow paths for adopters. Its Pending external records are intentionally adopter-owned because Rustee does not choose or operate a user's providers, credentials, topology, data policy, or on-call process. See enterprise deployment readiness.

Use the implementation plan review, support matrix, release plan, and qualification register rather than this roadmap alone to decide readiness for a deployment.
