Operations and Deployment

Make Service Trust Boundaries Operable First

Rustee provides explicit configuration, lifecycle, health, observability, and middleware boundaries. Applications and deployments retain ownership of topology, credentials, alerting, and external infrastructure.

Configuration and Secrets

  • rustee-config supports typed configuration and redacted diagnostics. Builder diagnostics list configured source kinds without configuration keys or values. Environment loading requires a non-empty prefix and has fixed variable-count, name-length, path-depth, and value-length bounds; each nested path segment uses only ASCII letters, digits, underscores, or hyphens. Paths are normalized once, and empty, duplicate, malformed, or scalar/object-conflicting paths fail rather than depending on process enumeration order. Unrelated non-Unicode OS environment input does not poison collection; a matching non-Unicode name or value fails with a redacted configuration error. Configuration source, secret manager, validation policy, reload strategy, and deployment injection remain application-owned.
  • Secrets, credentials, tokens, connection URLs, raw request bodies, and provider responses must not be placed in panic messages, error responses, metric labels, or default traces.
  • Configuration that changes a security or delivery contract is explicit and documented, not inferred from an ambient environment.

Transport and Reverse Proxy Trust

Rustee accepts forwarded identity only from configured trusted peer CIDRs. The default uses a single normalized Forwarded hop; an explicit X-Forwarded-* path and bounded chain restoration are opt-in. Each selected forwarded-header value is capped at 2 KiB before Rustee retains it. Header families are never mixed. Client-supplied forwarded headers must be overwritten at ingress before trusted context is restored. Default diagnostics expose only safe configuration and presence summaries; direct peer addresses, forwarded client addresses and hosts, and configured CIDR addresses are never rendered through Debug or framework tracing fields.

TLS termination, HTTP/2, WebSocket or protocol-upgrade support, proxy topology, and ingress behavior are deployment contracts. They are not silently enabled framework features.

Lifecycle, Health, and Limits

  • Applications own socket binding, supervisor behavior, readiness route composition, restart/backoff, and deployment draining.
  • Readiness checks configured dependencies with bounded timeouts. A successful TCP connection alone is not a healthy application, broker, schema, worker, or downstream side effect.
  • Graceful shutdown stops new work, lets active handlers and explicitly managed relays/workers drain under a configured bound, then reports unfinished work according to application policy.
  • HTTP/1 header-read deadlines, a 100-field header cap, bounded per-connection buffers, handler timeouts, body limits, open-connection limits, and request concurrency are explicit layers. A declared Content-Length above the body limit is rejected before handler execution or payload upload; streaming or undeclared bodies remain limited when consumed. A connection arriving after its configured cap is closed before request execution, while a request arriving after handler capacity receives a content-free 503 without calling the application. Zero-valued or runtime-unsupported server limits and timeouts are rejected at startup; do not rely on implicit unbounded defaults.

Set transport capacity at the listener boundary so it can be reviewed with the deployment memory and latency budget. 

use std::time::Duration;
use rustee_server::ServerOptions;

let options = ServerOptions {
    header_read_timeout: Duration::from_secs(15),
    max_http1_buffer_bytes: 64 * 1024,
    max_connections: 4_096,
    max_in_flight_requests: 1_024,
    ..ServerOptions::default()
};

Panic, Compression, and Static Content

  • The optional PanicCatchLayer returns a fixed redacted 500 for handler panics without changing the process panic hook or restart policy. A panic after response-body commit remains an application concern.
  • CORS applies its response headers only to requests with exactly one configured matching Origin. Matching responses include Vary: Origin; unmatched or ambiguous Origin requests continue to the application unchanged.
  • Compression negotiates gzip and Brotli and separates cache representations with Vary: Accept-Encoding. Streaming, cache policy, CPU limits, and proxy/CDN ownership remain explicit.
  • Static-file delivery is prefix-bound and applies filesystem security, MIME handling, cache validators, range behavior, precompressed-variant opt-in, and bounded streaming. Edge caching is not inferred from origin delivery.

Observability and Privacy

  • rustee-observability provides request correlation, route-template or reserved-outcome metrics, and global latency histograms with bounded cardinality. Rustee metrics collectors are advisory: collector-state recovery after a metrics-only panic does not interrupt response, relay, worker, or scheduler traffic, and all cumulative counters saturate rather than overflow.
  • Prometheus helpers return explicit text responses and create no global registry or automatic scrape route. Exporter/provider, sampling, shutdown, scrape isolation, and alert policy remain application-owned.
  • Optional OpenTelemetry integration exports a server span through a subscriber layer. W3C propagation validates bounded inbound parents and injects explicit outbound children; it does not write response headers automatically. Parsed carriers and remote-parent diagnostics report presence only, never raw propagation headers or trace identifiers.
  • Never label metrics with user identity, tenant ID, request ID, path parameter, queue address, payload, token, raw error, or provider endpoint.

Workers, Relays, and Event Streams

  • Outbox and scheduler metrics expose bounded terminal outcome, aggregate counts, and global duration. Outbox relay retry may be explicitly immediate or use a whole PostgreSQL-millisecond delay of at least one millisecond; application supervisors own loops, retry/backoff, alerting, and shutdown.
  • Kafka readiness is a bounded metadata probe, while lag snapshots are diagnostics rather than coordination APIs. Observe retry/DLQ backlog and group delivery separately.
  • Delayed retry uses PostgreSQL state and Kafka acknowledgement but is still at least once. Follow the dedicated delayed-retry and schema runbooks for recovery, rollout, and approved replay.

Edge Delivery

Public TLS termination, CDN cache keys, purge, edge compression, and origin draining belong to deployment. Configure origin proxy trust only for the edge peer CIDRs and qualify the entire path before promotion.

See the edge delivery policy for deployment evidence and the support matrix for current qualification status.
