Kafka Delayed Retry Runbook

PostgreSQL provides durable, database-clock delayed retry staging before a Kafka source offset commits. The relay remains an at-least-once operation and requires idempotent consumers.

Operational Preconditions

  • Apply the retry-table migration through deployment, not HTTP startup.
  • Provision source, retry, and DLQ topics with ACLs for the consumer and relay identities.
  • Define retry budget, retry topic, DLQ route, delays, supervision, alert thresholds, and consumer idempotency before traffic begins.
  • Verify bounded readiness for both retry storage and Kafka metadata. Readiness does not create topics or determine lag/drain health.

Normal Operation

  1. On a retryable source failure, stage source topic/partition/offset, next attempt, retry destination, sanitized failure/origin metadata, key/payload, and database-clock availability in PostgreSQL.
  2. Commit the source offset only after the stage succeeds.
  3. Lease due rows with SKIP LOCKED, publish to Kafka, and record confirmation only after broker acknowledgement.
  4. Monitor aggregate unpublished/due/leased/oldest-due backlog, pass outcomes, consumer retry/DLQ backlog, and downstream behavior without sensitive labels.

Kafka or Database Failure

  • A source record whose stage failed is not committed. Return failure to the worker supervisor and preserve the source for redelivery.
  • A relay publish or confirmation failure can republish after recovery. Do not claim exactly once; maintain idempotent consumer effects.
  • On database or Kafka outage, fail bounded readiness, stop new unsafe work, supervise backoff outside the adapter, and resume with the normal lease and acknowledgment path after recovery.
  • Do not alter retry-table rows, source offsets, retry headers, or DLQ records manually without an approved incident record and reconciliation plan.

Restore and Approved Replay

  1. Capture source topic, consumer group, partition/offset range, retry/DLQ state, reason, expected count, approver, executor, and stop condition.
  2. Confirm schema compatibility and database/external idempotency before processing any historical record.
  3. Use a new, explicit replay consumer group and inspect admin-tool dry-run results before moving offsets.
  4. Monitor lag, failure, backlog, oldest age, rate limits, and duplicate evidence. Reconcile results before recording completion.
