ADR 0003

Redis 통합 경계

Status: Accepted. Date: 2026-08-01.

Context

Redis는 cache, session, rate limit, Pub/Sub, distributed coordination 등 서로 다른 성질의 기능에 사용된다. 웹 프레임워크가 Redis를 단순 cache로 취급하면 보안과 장애 시 동작이 숨겨지고, 반대로 client와 모든 고수준 기능을 core에 넣으면 의존성과 public API가 빠르게 커진다. Tokio 기반 Rustee에는 async, multiplexing, reconnect를 갖춘 기본 client 경로와 역할별 정책이 필요하다.

Decision

Redis는 core 의존성이 아닌 선택적 상태 저장소 integration으로 둔다. Stage 6에서 redis-rs의 Tokio용 redis::aio::ConnectionManager를 첫 공식 client 경로로 사용하는 rustee-redis crate를 만든다.

  • Redis client는 AppState에 보관하고 State<AppState>로 전달한다.
  • rustee-redis는 redis-rs command API를 대체하지 않으며, connection, configuration, middleware storage adapter에 집중한다.
  • cache는 key prefix와 TTL을 명시하고 원본 저장소와의 invalidation 책임을 application에 남긴다.
  • rustee-rate-limit은 trusted application key resolver와 explicit FailOpen/FailClosed policy를 가진 fixed-window Tower layer를 제공하고, rustee-rate-limit-redis은 INCR, first-window TTL, PTTL을 하나의 Lua execution으로 수행한다. session과 rate limit middleware는 Redis 장애 시 allow 또는 deny를 묵시적으로 선택하지 않는다.
  • Pub/Sub과 blocking command는 전용 connection/background task로 분리한다.
  • 분산 락과 DB-Redis cross-store atomicity는 초기 convenience API에서 제외한다. durable queue는 Stage 10에서 rustee-jobs-redis의 독립 provider release로 별도 지원한다.

Consequences

  • Redis를 쓰지 않는 Rustee 서비스는 core 의존성과 compile time을 늘리지 않는다.
  • 기본 client는 clone 가능한 multiplexed connection과 reconnect behavior를 제공해 일반 command 사용이 간결해진다.
  • 보안과 가용성 정책이 middleware configuration에 드러나므로 운영자가 의도를 검토할 수 있다.
  • 응답 cache와 lock의 보편적 API는 늦어지지만, 잘못된 기본값으로 서비스의 일관성을 훼손할 가능성이 줄어든다.
  • Cluster, Sentinel, Streams의 adapter는 실제 요구를 바탕으로 feature와 별도 ADR로 설계해야 한다.

Alternatives

대안 판단
Redis dependency를 core에 포함 대부분의 서비스가 필요로 하지 않으며 core 안정성 및 build cost를 해치므로 채택하지 않는다.
모든 Redis 사용에 connection pool 강제 multiplexed client로 충분한 요청이 많다. 전용 연결이나 pool은 application 또는 별도 feature가 선택한다.
deadpool-redis를 첫 공식 client로 채택 유효한 선택지지만 Rustee의 기본 경로는 redis-rs의 reconnecting multiplexed client로 단순하게 시작한다.
자동 response cache와 lock middleware 제공 권한, invalidation, fencing, failure semantics가 서비스마다 달라 초기 표준 API로 채택하지 않는다.
Redis 장애 시 모두 fail-open cache에는 맞을 수 있으나 session과 rate limit에는 보안상 맞지 않을 수 있어 채택하지 않는다.

Follow-up

  • Stage 6에서 rustee-redis의 최소 configuration과 ConnectionManager example을 구현한다.
  • cache miss, timeout, reconnect, Redis outage를 포함한 integration test를 작성한다.
  • Stage 8의 rustee-auth-session-redis은 session TTL과 versioned namespace를 보존하며 Redis 오류를 SessionLayer의 fail-closed 503으로 전달한다. rate-limit layer와 Redis Lua bounded-concurrency contract는 구현됐으며, token-bucket/GCRA와 Cluster/Sentinel은 별도 provider release로 검증한다.
  • Stage 10에서 Streams job provider의 consumer group, pending reclaim, retry/DLQ를 독립 provider release로 검증한다.
  • Cluster, Sentinel, distributed lock 요구가 발생하면 실제 workload와 함께 새로운 ADR로 결정한다.
