Architecture Decision Record

ADR 0040: FromHeader Derive Boundary

Status: Accepted

Context

Header extraction ergonomics can help applications but must not create hidden parsing, security, or HTTP failure semantics. A typed application header that silently chooses one of several values can disagree with upstream policy or conceal ambiguous request input.

Decision

Provide an optional FromHeader derive only for supported explicit shapes, generating the same extraction contract and diagnostics available without a macro. The typed Header<T> extractor requires exactly one occurrence of its declared field and rejects duplicates before invoking application parsing.

Consequences

Unsupported forms fail at compile time. Duplicate typed header values return the ordinary bad-request extraction response. Applications that intentionally interpret multi-value HTTP fields use HeaderMap or a focused parser. The derive does not infer authorization, API-key policy, route behavior, or OpenAPI security metadata.
