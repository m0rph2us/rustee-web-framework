ADR 0007

Kafka Event Stream 통합 경계

Status: Accepted. Date: 2026-08-01.

Context

Kafka는 topic의 partition에 append된 기록을 consumer group이 offset으로 읽는 event-stream system이다. 여러 consumer group이 독립적으로 같은 event를 읽을 수 있고, retention 안에서는 offset을 옮겨 replay할 수 있다. 이는 한 message를 처리하고 ack하는 background job의 lifecycle과 다르다. 두 모델을 같은 public queue abstraction으로 감싸면 ordering, offset commit, rebalance, replay, schema evolution의 중요 운영 의미가 사라진다.

Decision

Kafka는 Stage 9B의 선택적 rustee-events-kafka crate로 통합한다. 이 crate는 rdkafka를 사용하며, typed and versioned event envelope, explicit topic/key, consumer group, post-success offset commit, rebalance, replay와 observability 경계를 제공한다. Kafka를 rustee-jobs provider로 취급하지 않는다.

  • 순서는 partition 안에서만 보장되는 것으로 다루며, event producer가 domain partition key를 명시한다.
  • consumer는 business side effect가 성공한 뒤 offset을 commit한다. 첫 Kafka runtime은 partition-safe한 serial synchronous commit을 사용한다. provider-neutral handler는 stable event metadata만 받고, duplicate delivery를 전제로 idempotent하게 작성한다.
  • KafkaRetryConfig와 KafkaFailurePublisher는 decode/handler failure를 bounded immediate retry 또는 terminal DLQ로 routing한다. broker acknowledgement 뒤에만 current offset을 commit하므로 publish/commit 사이 장애는 retry/DLQ duplicate를 만들 수 있다. delayed retry와 DLQ replay는 deployment-owned scheduler와 approved runbook으로 분리한다.
  • PostgreSQL DB 변경과 event publish의 atomic handoff에는 rustee-outbox-sqlx transaction outbox를 사용한다. same-transaction stage와 destination별 lease relay, transaction-scoped PostgresInbox projection receipt는 제공하지만 external consumer idempotency와 cross-store exactly-once는 application 책임이다.
  • rustee-events의 normal decode는 exact version만 허용하고, older payload는 application이 explicit upcaster로 현재 type으로 변환한다. rustee-events-schema는 typed JSON Schema artifact, exact fingerprint와 subject/version catalog, application-owned registry acknowledgement exact-match를 제공한다. newer version, topic, partition, replication, retention, ACL, remote registry compatibility semantics/credential, schema ID wire format과 consumer-first rollout은 deployment provisioning에서 관리한다.
  • Kafka producer transaction은 provider capability일 뿐, 외부 side effect를 포함한 exactly-once business effect 약속이 아니다.

Consequences

  • job 처리와 event propagation의 목적과 failure model이 API와 운영 문서에서 분명해진다.
  • Kafka consumer group, lag, offset, rebalance, replay를 first-class 운영 대상으로 다룰 수 있다.
  • 서비스는 event handler의 idempotency, schema compatibility, partition key를 설계해야 한다.
  • Kafka를 쓰지 않는 HTTP service와 rustee-jobs 사용자는 Kafka dependency를 갖지 않는다.

Alternatives

대안 판단
Kafka를 rustee-jobs provider로 포함 work queue lifecycle이 partition/offset/replay model을 가리므로 채택하지 않는다.
모든 Kafka 사용을 raw rdkafka에 맡김 가능한 escape hatch는 유지하되 envelope, trace, shutdown, outbox와 document된 운영 contract를 제공할 가치가 있어 채택하지 않는다.
Kafka transaction으로 exactly-once side effect를 보장한다고 선언 database와 external API를 포함하는 일반적인 처리에는 성립하지 않으므로 채택하지 않는다.
application startup에서 topic을 자동 생성 partition, retention, replication, ACL은 운영 결정이므로 deployment provisioning으로 분리한다.

Follow-up

  • Stage 9B에서 producer/consumer와 post-success commit, bounded partition lag snapshot, provider-neutral bounded W3C carrier와 OpenTelemetry capture/handler-parent adapter, bounded immediate retry/DLQ route를 구현했고, 실제 Kafka CI contract로 successful handler record의 no-replay, failed handler record의 redelivery, active handler graceful drain/commit, quiescent member handoff, in-flight rebalance 뒤 commit failure/duplicate redelivery, committed lag-zero와 terminal DLQ arrival을 고정했다. PostgreSQL outbox stage/lease/release와 inbox rollback/committed-duplicate contract도 구현했다.
  • strict current-version decode와 explicit older-payload upcaster contract, production group offset을 자동으로 옮기지 않는 operator-owned replay procedure를 구현했다. optional rustee-events-kafka-sqlx가 Kafka source offset commit 전 PostgreSQL durable delayed-retry stage와 due relay를 제공하며, at-least-once duplicate boundary는 ADR 0034에서 관리한다. rustee-events-schema local catalog와 registry acknowledgement mismatch contract는 ADR 0036에서 관리한다. external side-effect idempotency guidance와 schema/replay qualification은 계속 검증한다.
  • real schema registry provider compatibility/credential, wire serialization과 consumer-first rollout evidence, Kafka transaction은 compatibility와 external side-effect 정책을 문서화한 뒤 선택 기능으로 검토한다.
