ADR 0025

AI Batch PostgreSQL artifact ledger

Status: Accepted. Date: 2026-08-03.

Context

AiBatchArtifactLedger requires an atomic, restart-safe reservation boundary. An in-memory implementation validates contracts locally but cannot preserve an interrupted result application or defend a retry worker after a process restart. The existing tool-audit and provider-usage schemas have different identifiers and retention semantics, so sharing their rows would hide artifact ownership.

Decision

Provide optional rustee-ai-batch-sqlx with an application-run PostgreSQL migration and PostgresAiBatchArtifactLedger.

  • The durable primary key is (scope, reconciliation_key). It binds a single opaque catalog ID, run key, output/error role, and provider file ID for one reconciliation attempt. Reusing the key with any other identity fails closed as a conflict.
  • A fresh insert yields Reserved; the same identity yields Pending or Reconciled. record_reconciled is idempotent for the exact identity and never changes a different record. A reviewed retry keeps the batch/file identity but uses a new reconciliation key rather than releasing the pending row.
  • The adapter exposes an oldest-first bounded pending query with only a content-free artifact reference. Its debug output redacts all identifiers. It does not download files, parse JSONL, persist row output, delete artifacts, or requeue jobs.
  • The schema migration is deployment-owned. Rustee does not run it at startup and does not define cross-application retention, database backup, RLS, encryption, disaster recovery, or row-level domain idempotency policy.

Consequences

  • Applications can build an operator reconciliation worker that receives safe pending references, authorizes scope, compares their custom_id domain ledger, then explicitly schedules a new durable job only when safe.
  • PostgreSQL CI verifies pending state, exact completion reuse, conflict rejection, bounded query metadata, and redacted debug output. The adapter remains Experimental until its outage/recovery, authorization, retention, and application side-effect evidence is qualified.
  • Tool audit and provider usage keep their existing separate migrations. Deployments may coordinate their retention policy but do not share a database key or claim one global transaction.

Alternatives

in-memory ledger를 production worker에서 사용restart와 multi-instance duplicate를 막지 못하므로 채택하지 않는다.
tool audit 또는 usage ledger table에 artifact 상태를 추가idempotency 주체와 보존 의미가 달라 migration 및 operator query를 불명확하게 하므로 채택하지 않는다.
pending row를 framework가 TTL로 삭제하거나 자동 release부분 side effect의 안전성을 framework가 판정할 수 없으므로 채택하지 않는다.

Follow-up

  • Row-level domain idempotency schema, tenant authorization/RLS, pending alerting and operator retry/DLQ runbook must be selected by each application.
  • Provider result semantics, partial-result/billing reconciliation, artifact retention/delete scheduling, PostgreSQL outage/restart qualification, and live OpenAI evidence remain release gates.
