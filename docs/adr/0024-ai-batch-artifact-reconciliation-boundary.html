ADR 0024

AI Batch artifact reconciliation boundary

Status: Accepted. Date: 2026-08-03.

Context

Provider batch completion is not a single reliable event. An output or error artifact can represent partial results; a worker can stop after downloading it, after applying some domain rows, or after application effects succeed but before completion is recorded. Retrying raw files or model rows from a generic queue would leak retained content and can duplicate business side effects.

Decision

rustee-ai-batch defines a content-free artifact reference, whole-artifact ledger, loader, and processor contract. rustee-ai-batch-jobs carries only that reference and binds its durable envelope idempotency key to the artifact reconciliation key.

  • AiBatchArtifactReference contains an existing tenant-scoped batch reference, an output/error role, a validated opaque provider file ID, and a stable reconciliation key for one delivery attempt. It cannot contain JSONL, prompts, model bodies, provider error text, or domain result values.
  • AiBatchArtifactLedger atomically returns Reserved, Reconciled, or Pending. The coordinator loads and processes only a fresh reservation; a recorded reconciliation is reused without artifact access, and an ambiguous attempt is never automatically replayed.
  • AiBatchArtifactLoader authorizes and obtains the artifact only after durable dispatch starts. AiBatchArtifactProcessor owns model-body decoding, partial-result policy, and domain writes. Each row effect must be idempotent with a domain key plus the provider custom_id.
  • Loader, processor, and final-record failures retain Pending. Rustee does not decide whether a retry is safe, does not release the reservation, and does not retry download, parsing, deletion, or side effects automatically. An application reconciliation procedure inspects its row ledger and, only when safe, explicitly schedules a new attempt with a new reconciliation key.

Consequences

  • OpenAI Batch files can be downloaded and structurally parsed through rustee-ai-openai, then passed to an application-owned loader/processor without storing their raw bytes in Rustee durable jobs or logs.
  • A production implementation needs a restart-safe whole-artifact ledger and an atomic or otherwise provably idempotent row-level domain ledger. The in-memory ledger exists only for tests and local development.
  • The framework explicitly covers duplicate delivery and ambiguous whole-artifact attempts, but does not claim exactly-once provider delivery, exactly-once external side effects, complete provider billing, or automatic cleanup.

Follow-up

  • OpenAI model-specific request validation and semantic result decoders remain provider/application adapters.
  • Production ledger/catalog authorization, row-level idempotency schema, broker retry/DLQ and operator reconciliation procedure, billing, artifact retention/erase schedule, and live provider/outage evidence remain release gates.
