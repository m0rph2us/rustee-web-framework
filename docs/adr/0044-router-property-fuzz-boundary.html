Route and OpenAPI parser property and fuzz boundary

작은 결정론적 property 계약은 pull request에서, route와 public OpenAPI parser의 sanitizer 기반 libFuzzer 탐색은 별도 nightly 작업에서 실행합니다.

Context

router route template, nested prefix, OpenAPI route conversion과 API-key header-name metadata는 외부 URI 또는 public application configuration을 만나는 경계입니다. 선택한 예제만으로는 segment count, parameter grammar, static-route precedence, HTTP field-name byte 조합을 충분히 탐색하기 어렵습니다. 반대로 libFuzzer는 nightly, LLVM sanitizer와 C++ toolchain을 요구하므로 모든 pull request의 기본 runner에 넣으면 feedback과 platform portability가 나빠집니다. 기존 문서에는 property/fuzz 전략이 있었지만 실제 target, seed corpus, 실행 lane은 없었습니다.

Decision

  • rustee-router는 proptest로 parser acceptance grammar, named parameter value preservation, static-route-over-parameter precedence를, rustee-openapi는 accepted Rustee template의 parameter set과 {parameter} rendering을 workspace test에서 검사합니다.
  • fuzz/는 root Cargo workspace와 분리된 unpublished workspace입니다. route_pattern target은 arbitrary UTF-8 bytes를 public App::try_route/App::try_nest construction parser에, openapi_route target은 OpenApiRoute::from_rustee에, openapi_security_scheme target은 OpenApiSecurityScheme::api_key(name, Header)에 전달합니다.
  • curated seed corpus는 fuzz/corpus/route_pattern, fuzz/corpus/openapi_route, fuzz/corpus/openapi_security_scheme에 version control하며, crash artifact와 fuzz build output은 version control하지 않습니다. 발견된 crash는 minimized input, focused regression test, 원인 수정 순서로 승격합니다.
  • Fuzz workflow는 pinned nightly와 cargo-fuzz로 Linux에서 매주와 manual dispatch 때 bounded sanitizer run을 수행합니다. 일반 pull request에는 property test만 남깁니다.
  • fuzz target은 authentication, database, network, credential, user data 또는 production service를 호출하지 않습니다. fuzz 결과가 coverage, security approval 또는 full protocol compatibility를 자동으로 증명하지 않습니다.

Consequences

  • 일상 CI는 stable/MSRV feedback을 유지하면서 parser regression을 randomized shrinking으로 재현할 수 있습니다.
  • sanitizer run에는 nightly와 C++ standard library headers가 필요합니다. 그 toolchain이 없는 local machine에서는 workspace property test를 실행하고 CI fuzz artifact를 확인합니다.
  • 현재 coverage는 router construction, OpenAPI route conversion과 API-key header-name metadata boundary입니다. request URI decode, query/cookie runtime parser, HTTP body/static range parser, extractor/state machine은 independent target과 targeted property contract를 추가한 뒤에만 이 lane에 포함됩니다.

Alternatives

대안판단
모든 fuzz를 pull request마다 실행nightly/sanitizer cost와 nondeterministic exploration time이 기본 feedback lane을 지배하므로 채택하지 않습니다.
fuzz target만 두고 seed 또는 artifact policy를 두지 않음실패 재현과 corpus provenance가 약해지므로 채택하지 않습니다.
hand-written random loop만 사용shrinking, persistent corpus, sanitizer instrumentation과 crash minimization을 잃으므로 채택하지 않습니다.
fuzz workspace를 publishable workspace member로 편입libFuzzer/nightly dependency가 public package and release graph에 섞이므로 채택하지 않습니다.

Follow-up

새 parser 또는 state machine fuzz target은 input ownership, resource bound, seed provenance, crash-to-regression procedure와 CI budget을 함께 결정해야 합니다. HTTP wire, backend driver, cryptographic verification, credentials 또는 external service fuzzing은 isolated fixture와 security review 없이는 이 target에 추가하지 않습니다.
