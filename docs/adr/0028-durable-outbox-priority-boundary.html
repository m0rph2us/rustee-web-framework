ADR 0028

Durable outbox priority의 경계

Status: Accepted. Date: 2026-08-03.

Context

one-time delayed job은 PostgreSQL clock 기반 available_at으로 이미 durable하게 stage할 수 있지만, eligible row 사이에는 중요도를 표현할 방법이 없었습니다. broker마다 priority semantics가 다르므로 provider-neutral job envelope에 priority를 넣으면 publish 뒤 delivery guarantees까지 잘못 약속할 수 있습니다.

Decision

rustee-outbox-sqlx는 message staging 전 선택하는 OutboxPriority(0-255)를 제공합니다. default NORMAL은 0이며 기존 ordinary row의 FIFO behavior를 유지합니다. PostgreSQL migration 0003_rustee_outbox_priority.sql은 priority column과 ready index를 추가하고, one kind/destination relay는 eligible row를 priority descending, then created_at, then row ID 순서로 FOR UPDATE SKIP LOCKED claim합니다.

priority는 source message deduplication key, delay, relay retry, broker message body를 바꾸지 않습니다. retry row도 같은 persisted priority를 유지합니다. existing deployment는 original 0001 migration을 수정하지 않고 0003을 forward-only migration으로 적용합니다.

Consequences

  • higher priority row는 동일 destination/kind의 next claim batch에서 먼저 선택되지만, 이미 leased 또는 broker-accepted message를 재정렬하지 않습니다.
  • continuous high-priority traffic은 lower-priority starvation을 만들 수 있습니다. fairness quota, traffic shaping, alert threshold와 worker concurrency는 application/deployment가 소유합니다.
  • 이 기능은 PostgreSQL transactional outbox의 local ordering만 정의합니다. NATS, Redis Streams, RabbitMQ, SQS와 Kafka의 broker-level priority는 별도 provider contract가 필요합니다.
  • cron/recurring schedule과 global rate-limited scheduling은 여전히 application-owned workflow이며, priority 구현만으로 완료되었다고 선언하지 않습니다.
  • PostgreSQL contract는 lower-priority row가 먼저 stage되어도 high-priority job lease가 먼저 반환되는지 확인합니다.

Alternatives

대안판단
generic JobEnvelope priorityprovider-specific queue semantics와 external delivery order를 framework가 보장하는 것처럼 보이므로 채택하지 않습니다.
in-memory priority queuerestart, transaction rollback, relay ownership 뒤 priority가 사라지므로 채택하지 않습니다.
priority와 cron/rate limit을 한 scheduler abstraction으로 제공recurrence, time zone, catch-up, fairness와 broker topology 정책을 한 API에 숨기므로 별도 contract로 유지합니다.
priority를 batch claim 순서만 바꾸고 returned relay order를 고정하지 않음SQL UPDATE return order는 보장되지 않으므로 priority/created time/row ID로 outer result order를 명시합니다.
