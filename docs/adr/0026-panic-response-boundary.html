ADR 0026

Panic response boundary

Status: Accepted. Date: 2026-08-03.

Context

Rustee Error는 명시적인 handler/extractor 실패를 safe HTTP response로 렌더하지만, unhandled panic은 handler future를 중단하고 panic payload 또는 process 상태를 application logging/runtime에 맡긴다. HTTP client에는 private panic detail을 보내지 않아야 하지만, framework가 모든 panic을 보이지 않게 처리하거나 application의 global panic policy를 대체해서도 안 된다.

Decision

rustee-middleware::PanicCatchLayer를 opt-in Tower layer로 제공한다.

  • layer는 inner Service::call future가 response를 만들기 전에 panic하면 fixed internal_error JSON 500으로 변환한다.
  • panic payload는 response 또는 tracing field에 넣지 않는다. layer는 payload 없는 error event만 남긴다.
  • layer는 기본 server stack에 자동 장착하지 않는다. application은 catch하려는 handler/middleware call future의 바깥에 명시적으로 놓는다.
  • response header가 이미 committed된 뒤 body stream에서 발생한 panic, panic = "abort", process-wide panic hook, poisoned/global state recovery는 이 layer의 범위 밖이다.

Consequences

  • HTTP client는 opt-in boundary 안의 handler panic에서 private panic message 대신 stable 500 body를 받는다.
  • application은 crash reporting, panic hook redaction, restart/supervisor, alerting과 state recovery policy를 별도로 소유한다.
  • in-process middleware test와 real TCP server test가 response code/body redaction을 고정한다. panic payload의 process log 미노출은 deployment logger/panic-hook contract가 필요하다.

Alternatives

대안판단
server가 모든 application에 자동으로 panic catch 적용layer order, panic handling과 restart policy를 숨기며 abort build나 body-stream panic까지 해결한 것처럼 보이므로 채택하지 않는다.
panic payload를 response 또는 structured trace에 기록secret, request body, provider detail이 섞일 수 있어 채택하지 않는다.
panic을 HTTP 500으로 바꾸지 않고 connection을 항상 종료명시적으로 opted-in한 application의 stable client error contract를 제공하지 못하므로 채택하지 않는다.

Follow-up

  • production deployment는 redacted global panic hook, supervisor restart, alert owner와 state-recovery policy를 운영 runbook에 기록한다.
  • streaming body, direct TLS/HTTP2, protocol upgrade의 post-commit failure semantics는 각각의 transport ADR에서 다룬다.
