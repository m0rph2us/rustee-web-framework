routes builder macro boundary

route macro는 handler를 등록하는 새 모델이 아니라, existing App builder chain을 읽기 쉽게 쓰는 선택적 문법입니다.

Context

application은 여러 App::get/post/route 호출을 순서대로 작성합니다. 이 형태는 explicit하지만 route table이 길어지면 method/path/handler의 시각적 구분이 약해집니다. 반대로 attribute macro가 function signature에서 route를 추론하거나 global registry에 등록하면 module initialization, route order, extractor, fallback, middleware와 authorization ownership이 숨겨집니다.

Decision

  • rustee::routes!는 facade macros feature의 function-like builder macro입니다.
  • input은 one App builder expression, semicolon, one or more METHOD path => handler entries입니다.
  • standard methods GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS, TRACE, CONNECT만 syntax로 지원하고 direct App::get/post 또는 App::route(Method::...) calls로 expand합니다.
  • path와 handler는 ordinary expressions입니다. route pattern validity, duplicate behavior, handler/extractor bounds, state, fallback, layer order, panic/error policy는 existing App implementation이 판단합니다.
  • custom method는 App::route를 explicit하게 사용합니다. macro는 at least one route와 supported method만 compile-time diagnostics로 확인합니다.
  • generated code resolves a renamed Rustee facade dependency and this is verified by the workspace-only consumer fixture.

Consequences

  • macro-free builder code remains canonical and any application can mix ordinary App calls before or after routes!.
  • route order exactly follows entry order because expansion is a consuming builder chain; the macro has no static registry or startup work.
  • unsupported method and empty entry list receive stable compile-fail fixtures. valid standard verbs, dynamic path dispatch and renamed facade use have runtime/consumer fixtures.
  • macro syntax and diagnostics are public developer-experience compatibility surface, but it does not make dynamic route configuration compile-time validated.

Alternatives

대안판단
attribute macro가 function을 global route registry에 자동 등록route order, mount/state/layer ownership과 test isolation을 숨기므로 채택하지 않습니다.
handler signature에서 extractor/OpenAPI/auth metadata 추론type만으로 application error/authorization/schema 의미를 완전하게 알 수 없으므로 채택하지 않습니다.
string literal만 받아 route pattern을 macro가 재구현해 검증router grammar duplication과 dynamic configuration 배제를 만들므로 existing App validation을 유지합니다.
custom HTTP method도 ad hoc token syntax로 허용method expression ownership을 흐리므로 explicit App::route로 남깁니다.

Follow-up

attribute route macro, compile-time route grammar, mounted route composition, OpenAPI/schema derive 또는 handler inference를 검토할 때에는 macro-free parity, error/authorization ownership, dynamic configuration, route order, diagnostics와 migration plan을 포함한 새 ADR이 필요합니다.
