ADR 0005

인증과 권한 경계

Status: Accepted. Date: 2026-08-01.

Context

인증은 framework adoption에서 빠지기 어려운 기능이지만 identity provider, login protocol, token format, session store, tenant model은 서비스마다 다르다. 이를 core에 넣거나 raw JWT claim을 handler에 직접 노출하면 framework dependency와 security surface가 커지고, 인증과 권한의 구분이 사라질 수 있다. 반대로 공식 경로가 없으면 OIDC callback, JWT 검증, CSRF, session rotation, 401/403 mapping이 서비스마다 달라진다.

Decision

인증과 권한은 Stage 8의 선택적 rustee-auth crate 세트로 제공한다. core는 authentication type이나 identity provider에 의존하지 않는다. 인증 결과는 provider-neutral Principal로 정규화하며, authorization policy는 이를 사용해 별도로 판단한다.

  • rustee-auth는 Principal, AuthUser extractor, RequireAuth, bearer layer, explicit header-only ApiKeyLayer, scope/direct-permission/server-configured role policy, tenant-match guard, configured host-map TenantResolutionLayer와 401/403/404/503 mapping을 제공한다.
  • rustee-auth-jwt는 static HMAC/RSA/EC/EdDSA verification key와 단일 algorithm allowlist로 JWT bearer token을 검증한다. signature, sub, issuer, audience, expiry, not-before를 모두 요구하고 verified roles/permissions claim을 정규화한다.
  • rustee-auth-oidc는 HTTPS remote JWKS bearer token 검증/key rotation과 OIDC discovery, Authorization Code + PKCE(S256), atomic one-time state, nonce-bound ID token, session bridge를 제공한다. 또한 configured HTTPS endpoint에만 opaque access token을 introspect하고 active, subject, issuer, audience, supplied time claim을 검증한다. verified roles/permissions claim을 정규화하며 cache는 raw token 대신 SHA-256 fingerprint를 key로 삼고 exp를 넘지 않는다. rustee-auth-oidc-redis는 versioned key/remaining TTL/Redis GETDEL로 durable transaction storage를 제공한다. one asymmetric algorithm, required kid, signature/issuer/audience/time claim, compatible JWK filtering, bounded refresh와 provider failure를 명시적으로 처리한다.
  • rustee-auth-session은 opaque server-side session, secure cookie, session rotation/logout, CSRF와 state-store trait를 제공한다. rustee-auth-session-redis은 rustee-redis 위에서 namespace와 session TTL을 보존하는 production adapter를 제공한다.
  • static-key verifier와 remote-JWKS verifier는 같은 BearerAuthenticator 경계 뒤에서 Principal만 반환한다. API-key provider도 ApiKeyAuthenticator 경계 뒤에서 same principal만 반환한다. raw token/key와 verification key를 handler에 노출하지 않는다.
  • tenant는 검증된 identity 또는 trusted server-side mapping에서 만들며, client-provided header를 tenant authority로 신뢰하지 않는다. TenantResolutionLayer는 configured exact host map 또는 custom trusted resolver의 TenantContext를 principal tenant와 다시 비교한 뒤 route에 넣는다.
  • implicit flow와 Resource Owner Password Credentials grant는 공식 login 경로에서 제외한다.

Consequences

  • OIDC, JWT, opaque token, cookie session을 바꾸더라도 handler는 안정된 Principal과 권한 API를 사용할 수 있다.
  • 인증되지 않은 요청, 권한 없는 요청, identity infrastructure 장애를 401, 403, 503 등 서로 다른 failure로 다룰 수 있다.
  • core dependency와 public API가 특정 provider, password database, cryptographic crate에 묶이지 않는다.
  • session store failure policy와 cookie/CSRF configuration이 application configuration에 명시되어 운영 검토가 가능하다.
  • 기본 API가 늘어나지만 policy engine, mTLS, DPoP, delegated authorization은 실제 요구 전까지 별도 extension으로 남는다.

Alternatives

대안 판단
identity provider와 user model을 core에 포함 provider 선택권과 core 안정성을 해치므로 채택하지 않는다.
handler가 raw JWT/cookie를 직접 처리 검증 누락과 authorization 혼동을 유발하므로 채택하지 않는다.
JWT claims만으로 자동 권한 부여 resource ownership, tenant 범위, domain policy를 표현하기 부족하므로 채택하지 않는다.
모든 app에 Redis session을 기본 강제 stateless API와 다른 state-store 요구가 있으므로 선택적 adapter로 둔다.
implicit flow 또는 password grant를 기본 login flow로 제공 현재 OAuth 보안 권고와 맞지 않아 채택하지 않는다.

Follow-up

  • Stage 4에서 request extension/extractor와 error mapping 계약을 구현한다.
  • Stage 6에서 Redis state-store failure policy를 구현했고, Stage 8에서 Redis session restoration Docker contract를 추가했다.
  • Stage 8에서 static-key JWT, JWKS verifier, OIDC Code + PKCE, opaque introspection, explicit header-only API-key authentication, direct permission/role policy/tenant-match guard와 configured host-map tenant resolution, Redis transaction-store security regression test를 유지한다. JWKS/opaque adapter의 real loopback transport-outage 503/redaction contract는 구현됐으며, API-key production provider rotation/audit, repository isolation과 external IdP revocation lifecycle end-to-end security integration test를 구현한다.
  • Stage 10에서 advanced client authentication, policy engine, mTLS/DPoP 요구를 별도 ADR 및 release gate로 검토한다.
