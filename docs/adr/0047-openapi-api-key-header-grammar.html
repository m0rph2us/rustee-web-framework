OpenAPI API-key header grammar boundary

header에 선언하는 API key 이름은 HTTP field-name으로 검증하되, document metadata를 runtime credential parser로 확장하지 않습니다.

Context

OpenAPI API key component의 name은 header, query, cookie 중 한 위치에 나타납니다. 기존 bounded text validation만으로는 header 위치에 공백이나 제어문자를 넣을 수 있어 generated client와 real HTTP request가 다른 contract가 될 수 있습니다. 반면 query/cookie key의 application semantics를 one framework grammar로 정하면 runtime parser와 cookie policy를 암묵적으로 약속하게 됩니다.

Decision

  • OpenApiSecurityScheme::api_key(name, Header)는 Rustee의 existing HTTP HeaderName parser로 name을 검증합니다.
  • blank, oversized, NUL을 포함한 name은 기존 bounded metadata error로 거부합니다. Header parser가 거부하는 공백, separator, control character도 InvalidMetadata { field: "API key header name" }으로 fail-closed 합니다.
  • valid header name의 application-provided spelling은 OpenAPI output에 유지합니다. Header field names의 runtime case-insensitive matching, duplicate header handling, actual API-key parsing과 secret redaction은 application middleware가 소유합니다.
  • query/cookie location은 bounded public metadata로 유지합니다. query encoding, duplicate handling, cookie-name/path/domain/same-site/secure semantics를 이 builder가 해석하거나 검증하지 않습니다.
  • 이 결정은 HTTP authentication middleware를 붙이지 않으며 API key value, credential, tenant/subject 또는 route runtime policy를 document에 넣지 않습니다.

Consequences

  • header API key를 사용하는 client generator는 invalid wire name이 없는 deterministic component를 받을 수 있습니다.
  • application은 custom query/cookie conventions를 문서화할 수 있지만 Rustee가 cross-framework cookie contract를 구현한다고 오해하지 않습니다.
  • unit과 facade contract는 valid mixed-case header name, invalid header name rejection, query metadata preservation을 고정합니다.

Alternatives

대안판단
모든 API-key name을 generic metadata로만 취급invalid header declaration이 OpenAPI output에 남으므로 채택하지 않습니다.
header/query/cookie에 하나의 strict token grammar 사용query/cookie wire semantics와 application conventions를 framework가 임의로 제한하므로 채택하지 않습니다.
OpenAPI API key 선언으로 parser와 authentication layer 자동 구성문서와 credential verification/tenant authorization ownership을 섞으므로 채택하지 않습니다.
header name을 lowercase로 정규화해 output에 저장HTTP matching에는 불필요하고 application의 public documentation spelling을 바꾸므로 채택하지 않습니다.

Follow-up

API-key runtime parser, duplicate/combined header policy, query encoding and duplicate policy, cookie serialization/browser scope, secret storage/rotation/redaction, runtime route-document drift와 external OpenAPI validator/client generation은 separate security owner와 integration evidence를 포함한 ADR에서 검토합니다.
