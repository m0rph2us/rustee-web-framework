ADR 0002

데이터베이스 통합 경계

Status: Accepted. Date: 2026-08-01.

Context

웹 서비스 대부분은 데이터베이스가 필요하지만, SQL 중심 개발, ORM 중심 개발, 관계형 DB와 다른 저장소의 요구는 크게 다르다. DB 모델을 core에 넣으면 Rustee의 최소 계약이 커지고, 특정 database와 ORM의 제약이 모든 사용자 API로 퍼질 위험이 있다. 반대로 아무런 공식 경로가 없으면 pool, 오류 처리, migration, readiness가 서비스마다 제각각이 된다.

Decision

rustee-core는 database driver, ORM, repository trait, migration runner에 의존하지 않는다. database client와 pool은 AppState에 두고 State<AppState> extractor로 전달한다.

  • 첫 공식 integration은 async SQL toolkit인 SQLx이며, Stage 5에서 선택적 rustee-sqlx crate로 제공한다.
  • rustee-sqlx는 PostgreSQL과 SQLite를 feature로 분리하고 SQLx 타입을 대체하지 않는다. MySQL/MariaDB는 무패치 upstream RSA security advisory가 해소되고 backend contract가 준비될 때까지 공식 feature로 노출하지 않는다.
  • SeaORM과 Diesel/diesel-async는 같은 상태 주입 모델로 지원하며, 처음에는 문서화된 recipe를 제공한다.
  • MongoDB는 SQL과 document model의 차이가 크므로 별도 rustee-mongodb integration과 ADR로 관리한다.
  • migration은 배포 pipeline의 명시적 단일 작업이다. production server startup에서 자동 실행하지 않는다.
  • 요청 단위 자동 transaction과 기본 Transaction extractor는 제공하지 않는다. transaction 경계는 use case에서 명시적으로 관리한다.
  • event/job과 PostgreSQL business write의 atomic handoff는 선택적 rustee-outbox-sqlx가 같은 transaction의 stage, job의 PostgreSQL-clock one-time delayed stage, destination별 SKIP LOCKED lease, broker acknowledgement 뒤 confirmation으로 지원한다. 같은 crate의 PostgresInbox는 consumer receipt와 database side effect를 같은 transaction에 기록한다. cross-store transaction이나 exactly-once business effect를 주장하지 않는다.

Consequences

  • Rustee는 저장소 선택권을 유지하면서도 SQLx 기반 서비스에 일관된 시작 경로를 제공한다.
  • core의 컴파일 시간, 의존성 수, public API surface가 database 선택에 의해 커지지 않는다.
  • application state가 DB 접근의 명확한 소유자가 되므로 테스트에서 pool 또는 fake client를 교체하기 쉽다.
  • 개발자가 transaction을 명시해야 하므로 초기 코드는 약간 길어지지만, commit과 rollback 시점이 숨겨지지 않는다.
  • outbox/inbox migration, relay schedule, tenant authorization, external consumer idempotency와 operational metric은 application이 계속 소유한다.
  • 운영 시 migration 실행 책임이 배포 환경에 있으므로 starter template과 CI 가이드를 제공해야 한다.

Alternatives

대안 판단
ORM을 core에 포함 진입 경험은 간단해질 수 있지만 core 안정성과 저장소 선택권을 해치므로 채택하지 않는다.
DB 중립 repository trait 제공 DB 고유 기능, SQL, ORM relation 모델을 지나치게 평준화하므로 채택하지 않는다.
SeaORM을 첫 공식 integration으로 선택 생산성은 높지만 Rustee는 먼저 SQL을 투명하게 유지하는 SQLx 경로를 표준화한다. SeaORM recipe는 지원한다.
서버 시작 시 자동 migration 개발 환경에서는 편리하지만 production 동시 기동과 schema lock 위험 때문에 기본 정책으로 채택하지 않는다.
모든 요청을 자동 transaction으로 감싸기 streaming, 외부 호출, read-only 요청, 긴 transaction을 올바르게 다루기 어려워 채택하지 않는다.

Follow-up

  • Stage 4에서 State와 application error 경계를 구현하고 테스트한다.
  • Stage 5에서 PostgreSQL + SQLx integration example, migration CI, readiness check를 만든다.
  • SQLx adapter API가 실제로 필요한 최소 helper만 갖는지 example과 integration test로 검증한다.
  • PostgreSQL outbox migration/stage/one-time delayed job availability/lease/confirmation/release와 inbox receipt contract를 구현했고, CI가 transaction visibility, source-message deduplication, delayed row invisibility와 due release, release 뒤 redelivery, rollback 뒤 receipt 재시도와 commit 뒤 duplicate suppression을 검증한다. external side-effect idempotency와 non-PostgreSQL outbox/inbox는 별도 release gate다.
  • tenant routing 요구는 ADR 0012: tenant persistence isolation에서 PostgreSQL RLS-scoped transaction으로 확장했다. read/write split과 transaction retry는 별도 ADR로 확장한다.

Last updated: 2026-08-02. Supersede this ADR if Rustee moves database abstractions into core or changes its official integration path.
