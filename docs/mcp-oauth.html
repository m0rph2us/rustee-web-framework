MCP OAuth

OAuth Boundaries for MCP Clients and Servers

MCP authorization is split between a client-side authorization flow and a server-side protected-resource boundary. Neither layer silently becomes a general token issuer, session store, or tool approval system.

OAuth Client

rustee-ai-mcp-oauth provides bounded protected-resource and authorization-server discovery, exact single JSON media-type admission, OIDC fallback, PKCE S256, an 8 KiB authorization redirect budget, atomic one-time state/verifier transactions, bounded authorization-code and explicit refresh exchange with canonical resource binding, redacted token sets, content-free OAuth diagnostics, and explicit local-store unavailability errors. All received WWW-Authenticate fields can be evaluated in order under one bounded challenge budget; protected-resource metadata is selected only through one unambiguous Bearer resource_metadata parameter, and repeated values fail closed. The optional Redis store encrypts token envelopes with AES-256-GCM, supports active/retired decryption-key rotation, uses exact whole-second token retention because Redis expiry is second based, and uses versioned length-delimited namespace/transaction-state and namespace/token-slot keys to avoid cross-store collisions. It exposes content-free transaction/token-store diagnostics while retaining trusted sources for application handling.

Application Flow

  1. Discover protected-resource metadata and the authorized server under bounded, redacted transport rules.
  2. Create and store a one-time state/verifier transaction outside ordinary browser sessions.
  3. Redirect the user through an application-controlled callback and validate state, PKCE, issuer, audience, and canonical resource binding.
  4. Store a redacted token set in the selected protected store and use it only for an authorized MCP request.
  5. On expiry or failure, return the explicit authorization outcome. Do not replay an MCP tool call while refreshing or recovering a session.

Security Boundary

  • Authorization state, codes, access tokens, and refresh tokens never belong in an ordinary session cookie, log, metric, trace, or error response.
  • A flow instance coalesces concurrent refreshes that observed the same token-store key and token set without blocking independent local keys; client registration, redirect URI policy, consent, KMS key delivery, revocation, cross-instance refresh coordination, and provider qualification remain deployment responsibilities.
  • A Redis transaction- or token-key format change is a protected-store migration. Restart uncompleted authorization flows and reauthorize affected token slots after the upgrade rather than automatically reading a legacy delimiter-only key whose namespace or record ownership could be ambiguous.
  • Refresh and recovery may prepare a new authenticated request path, but they do not repeat an original discovery, read, prompt, or tool call automatically.

OAuth Resource Server

rustee-mcp-oauth serves public protected-resource metadata, produces fail-closed 401/403 Bearer challenges bounded to the supported 8 KiB header budget, and hands a verified principal and scopes to the application. Token issuance, persistence, refresh, verifier configuration, audience trust, authorization-server trust, and deployment policy are intentionally outside this crate.

Server Mount and Verification

Mount the MCP server below an explicit application route. Combine protected-resource authentication with Origin validation, visible-tool policy, application-created execution context, approval, and mandatory terminal audit. Tests cover metadata, challenge, scope handoff, state single-use, PKCE, resource binding, redaction, and no-replay behavior. Production promotion requires live authorization-server, proxy URL, token-operation, revoke/rotation, and outage evidence.
