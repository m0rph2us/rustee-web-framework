Implementation Plan Review

The Framework Is Ready; Each Adopter Qualifies Its Own Backend

This review distinguishes completed reusable framework boundaries from the deployment-specific qualification that only a provider and topology owner can perform.

Review Criteria

  • Is the public boundary explicit, typed, documented, and tested at the right layer?
  • Does an optional adapter preserve provider semantics and declare application/deployment ownership?
  • Are redaction, bounded deadlines, shutdown, retry, duplicate delivery, and recovery behavior observable?
  • Does the claimed support level have matching automated and external evidence?

Current Assessment

The workspace implements the core framework, optional storage/security/delivery/AI contracts, focused examples, broad in-process/container verification, protected live-provider workflow paths, and a CI-validated HTML documentation and quality-gate ledger. The framework does not need to choose a shared provider account or topology to be deployment-ready. Each adopter owns the Pending record applicable to its credentials, ACLs, outages, duplicate matrices, tenant policy, external side effects, edge path, and recovery process.

Maintainability Snapshot

On 2026-08-25, follow-up structural audits again found no need for a broad refactor. The recurring-job scheduler keeps stable public values and errors at the crate root while schedule calculation, durable row reconstruction, rate governance, fire observation, and transactional execution have focused ownership. MCP OAuth token handling keeps token model and lifecycle contracts together while exchange HTTP and token-store persistence remain separate. Event and job envelopes retain compatibility and trace carriers as focused child modules, and the principal model remains one bounded, validated identity value object. Splitting those cohesive public models further would add navigation cost without removing a real dependency or failure boundary.

Recent narrow refactors moved only facade-level Kafka and MCP OAuth Redis integration regressions into dedicated test modules; their public and runtime contracts did not change. Scheduler row identifiers now follow the existing durable-ID diagnostic policy, so default debug output redacts them while an application may record an identifier explicitly. Configuration errors now admit only crate-defined fixed categories, preventing an arbitrary runtime value from becoming framework error text while retaining the documented identifying configuration key.

The recurring-job scheduler uses the workspace bounded JSON primitive when registering a schedule and materializing a fresh job envelope. Oversized registration input returns InvalidPayload; an oversized or otherwise invalid stored row returns StoredSchedule. The common 1 MiB job-envelope limit applies while each new JSON value is serialized, and regression coverage includes raw payload admission and envelope expansion.

A durable-store audit aligned runtime admission, stored-row restoration, and forward PostgreSQL migrations for API-key principals, MongoDB resume tokens, and AI batch artifact identifiers. Initial migrations remain immutable. Deployments apply the later bound migration in order and explicitly repair incompatible legacy rows before readiness is declared. Runtime restoration still validates the durable contract, and API-key authentication fails closed before it reads or uses an oversized persisted principal.

Kafka delivery now applies the same boundary discipline before a native client is reached, while a retry record is created, and when a delayed retry is restored from PostgreSQL. Topic names are bounded to the broker-compatible 249-byte limit and reject whitespace or NUL bytes. A retry preserves origin metadata only when the complete topic, partition, and offset tuple appears exactly once and validates; partial, duplicate, or malformed headers fail closed. The delayed-retry relay revalidates its stored routing and origin fields before it publishes. The all-feature native Kafka and SQLx unit suites, workspace Clippy, Rustdoc, doctests, and ordinary workspace tests pass; real Kafka and PostgreSQL contracts remain explicit environment qualification evidence rather than a local unit-test claim.

Stable event types share one 255-byte, NUL-free contract at the core envelope boundary. Envelope construction, recovered provider messages, and schema declarations reuse that contract, while a schema registry may add its stricter identifier grammar. This prevents an event that cannot enter a durable provider path from being accepted first and rejected only when a selected outbox adapter stages it.

Public crate roots preserve stable facades while distinct policy, wire-format, storage, provider, and HTTP responsibilities live in focused modules. The PostgreSQL outbox is intentionally an exception to the root-as-facade convention: transactional staging, lease acquisition, lease settlement, and stored-message reconstruction form one storage state machine, while message models, timing policy, relay execution, observation, and inbox receipt handling remain separate.

A workspace production-target audit found no production unwrap(). The complete all-feature workspace and test-target compile, all-feature library test suite, and CI-level workspace Clippy pass after the current audit. CI and release qualification deny clippy::unwrap_used across every all-feature library and first-party binary target. The remaining production expect() calls are closed invariants only: validated and bounded configuration, fixed non-zero constants, generated numeric or ASCII HTTP values, bounded integer conversions, or writes to owned strings. User input, provider data, persistence, and network failures remain explicit sanitized errors rather than panic paths.

PostgreSQL contract packages reset shared durable tables, so their full container lanes run one test thread per package. Outage-only tests are explicit opt-ins: ordinary provider runs skip them, while the stopped-backend workflow enables the required environment marker. The outbox package's dependency-free unit suite, strict Clippy, Rustdoc, AI module-boundary, and documentation gates pass locally; its database contract tests require PostgreSQL and CI provisions that service explicitly.

Priority Order

  1. Maintain the core API and regression suite without widening its dependency surface.
  2. Keep documented recovery, redaction, and real-backend contracts aligned with the adapters claimed as Supported.
  3. Give adopters clear qualification workflows and runbooks for identity, MongoDB, brokers, Kafka/registry, edge, and live AI providers.
  4. Expand fuzz/property coverage, repeatable benchmark baselines, and platform compatibility while keeping minimized deterministic regressions. Route/OpenAPI grammar plus public query, JSON, test-cookie, and static byte-range paths are now covered by the weekly fuzz matrix; route dispatch has a manual baseline harness.
  5. Keep framework release claims separate from a deployment-specific Enterprise-qualified claim.

Conclusion

Continue to prefer focused integration crates and operational contracts over a monolithic enterprise package. A new provider or feature is valuable only when its lifecycle, failure behavior, documentation, verification, and release ownership are as clear as its happy path.
