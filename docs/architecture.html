Architecture

Rustee Layers and Crate Boundaries

Rustee is a workspace of a stable core and optional, composable integrations rather than one large crate. The public API stays approachable while internal boundaries are designed for enterprise growth.

Current MSRV: Rust 1.94.1.

Core Abstractions

Handler

The common representation of an async function that extracts request values and converts its result into a response.

IntoResponse

The contract that converts strings, JSON, status tuples, and custom errors into HTTP responses. Bodyless HTTP statuses discard payload bytes and conflicting payload-length metadata.

FromRequest

The basis for extractors such as Path, Query, Json, Header, and State. Json requires exactly one Content-Type value, then accepts standard application/json and application/*+json media types with optional parameters.

App and Router

Application-facing types for routes, nesting, fallback, and middleware composition.

Layer

The standard composition path for cross-cutting concerns such as timeouts, tracing, authentication, and rate limits.

State

Safely injects shared typed application state, including database pools and Redis or MongoDB clients.

Nested Service Contract

let api = App::new()
    .get("/users/:id", get_user)
    .layer(AuthLayer::bearer(verifier));

let app = App::new()
    .get("/health", health)
    .nest("/api", api);

App::nest mounts a Rustee App or Tower-compatible service under a static, non-root prefix. The child receives a URI without the prefix while retaining the original query and request extensions, making service-scoped authentication, policy, and rate-limit layers natural to compose.

  • A prefix must contain at least one static segment such as /api; root mounts and parameterized prefixes are rejected at construction time.
  • Configured route templates and nest prefixes cannot contain repeated / separators. Requests with repeated separators do not match a Rustee route.
  • Unless a direct parent route path matches, the child owns 404, fallback, and method 405/Allow responses under its prefix. Only requests outside the prefix proceed to the parent fallback.
  • A direct parent route path, including its method-mismatch 405, wins over a nested route; the longest matching nested prefix wins among children.
  • Nested Rustee handlers record the externally visible full RouteTemplate; /users/:id under /api is classified as /api/users/:id.
  • Parent and child StateStore values are not merged. Shared state must be injected into both applications or passed through an outer Tower layer or request extension.
  • A poisoned nested-service clone state returns a sanitized 500 and does not resume by using recovered lock contents.
  • Use try_route and try_nest for runtime-supplied configuration. A route cannot duplicate another route's HTTP method and complete path-matching set; convenience-builder validation panics name the rule that failed without echoing the supplied route or prefix.

Extension Rules

  • The core does not own an ORM, database driver, broker client, model-provider SDK, or cloud deployment implementation.
  • The dependency direction of the foundational HTTP chain is checked in CI: rustee-json and rustee-observability-core have no local workspace dependency; rustee-core may depend only on rustee-json; router, server, middleware, and the compact facade have an explicit reviewed local dependency set. Optional provider crates remain outside this rule.
  • Optional integrations are feature-specific crates with explicit configuration, readiness, lifecycle, and failure behavior.
  • Observability collectors use bounded labels and do not create global registries, routes, listeners, or alert policies automatically.
  • Framework integrations expose contracts; application deployment owns credentials, topology, alerting, retention, external side-effect idempotency, and provider qualification.
  • Every optional adapter needs documentation, targeted tests, operational evidence, and a support classification before release promotion.

Implementation Direction

The currently implemented workspace covers the core HTTP path, routing and nesting, selected middleware, typed configuration and observability, optional SQLx/Redis/MongoDB/authentication integrations, durable job and event contracts with provider adapters, and an AI integration boundary. Each integration remains opt-in and has a separate support and qualification status. Read the focused documents before treating an adapter as production-ready: testing, support matrix, release plan, and qualification register.
