Event Schema Rollout

Schema artifacts and registry acknowledgement are explicit deployment contracts. They never replace consumer compatibility, replay policy, or producer/consumer operational ownership.

Operational Preconditions

  • Maintain typed JSON Schema artifacts, exact fingerprints, stable subject/version catalog entries, owners, compatibility policy, and retention/replay policy in source control.
  • Determine the producer, every consumer, consumer group, topic, partition key, rollout window, rollback owner, and external side-effect idempotency before publication.
  • Use bounded HTTPS or loopback registry operations with redacted endpoint and credential diagnostics. The registry deadline remains enforced even when an application supplies an mTLS or proxy HTTP client. The registry must not receive raw production payloads as a verification shortcut.

Deployment Order

  1. Review the artifact, fingerprint, subject/version, declared compatibility policy, and consumer impact.
  2. Deploy or validate consumers that can read the intended version. Add explicit upcasters where older payloads remain supported.
  3. Run exact registry lookup, compare effective policy, register only an absent exact artifact, and relookup the resulting identity.
  4. Deploy producers after consumer readiness is proven. Observe decode failures, lag, retry/DLQ backlog, and external effects.
  5. Record version, fingerprint, registry identity, rollout time, owner, verification evidence, and rollback decision.

Rollback and Replay

  • Stop or roll back the producer before assuming a registry change fixes consumer behavior.
  • Use a compatible consumer version or an explicit upcaster; do not guess semantic compatibility from two JSON Schema documents.
  • Replay follows the event-stream approval procedure with a new consumer group, bounded scope, idempotency evidence, stop condition, and reconciliation record.
  • Registry publication does not create topics, publish records, change offsets, or perform replay.

Confluent Live Qualification

The Confluent adapter is verified through local bounded transport contracts. The confluent-schema-live-qualification.yml workflow runs one retained generated-subject contract only after the registry_write_approved input is true and the protected confluent-schema-registry-qualification environment supplies credentials. Its required authentication choice injects exactly one Basic pair or Bearer token. Promotion beyond Experimental still requires owner-approved live endpoint, compatible provider version, TLS and credential handling, ACL evidence, outage/recovery exercise, consumer-first rehearsal, and rollback evidence without sensitive artifacts in reports.
