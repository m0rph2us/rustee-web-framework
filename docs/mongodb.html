MongoDB Document Store

Use the Official Driver, Keep HTTP and BSON Separate

Rustee integrates the official MongoDB Rust driver as an optional application-state dependency. BSON documents remain persistence models; HTTP request and response contracts remain explicit DTOs.

Application Shape

use mongodb::{bson::{doc, oid::ObjectId}, Client, Collection};
use rustee::{Json, Path, State};

#[derive(Clone)]
struct AppState { mongo: Client }

async fn get_user(
    State(state): State<AppState>,
    Path(id): Path<String>,
) -> Result<Json<UserResponse>, AppError> {
    let users: Collection<UserDocument> = state.mongo.database("app").collection("users");
    let document = users.find_one(doc! { "_id": ObjectId::parse_str(id)? }).await?
        .ok_or(AppError::not_found("user"))?;
    Ok(Json(UserResponse::from(document)))
}

UserDocument owns BSON serialization and collection layout. UserResponse owns the HTTP contract. Do not automatically expose ObjectId, internal fields, or schema versions through an API.

Tenant BSON Boundary

MongoTenantScope is created only from a verified TenantContext. It outer-ANDs tenant_id with caller filters, adds the trusted tenant ID to inserts and replacements, rejects tenant-field mutation, and can create bounded direct foreign-collection lookup and union stages. Its internal tenant_scope module is separate from client lifecycle, transactions, and change-stream helpers; the crate root preserves the stable public API.

  • Never build TenantContext from a request header, JSON body, or query parameter.
  • Use the scope for find, update, delete, and supported aggregation paths. Raw driver access, nested lookup/union, and change-stream pipelines require separate review.
  • Production indexes for tenant-owned collections normally begin with tenant_id; actual key order must follow query and shard-key analysis.
  • This helper is not server-enforced MongoDB RLS. Use least-privilege database identities and test tenant A/B isolation for every new query shape.

Transactions and Change Streams

  • begin_transaction starts an explicit session and transaction. The application attaches operations to that session and commits or aborts it; Rustee never creates a transaction per request.
  • Transactions and change streams require a replica set or sharded deployment. Avoid parallel operations within one MongoDB transaction.
  • Change streams run in supervisor-owned workers, not infinite HTTP handlers. Handlers must be idempotent because restart and duplicate delivery are possible.
  • next_change_until returns event, end, or shutdown with the opaque driver resume token observed at that point. Its debug summary reports only the outcome variant and token presence, never event content or token data. Persist a token only after durable event handling succeeds.
  • Invalid tokens, history loss, collection changes, and incompatible pipelines are operator-visible failures. Rustee never automatically falls back to earliest or latest history.

Durable Checkpoints

rustee-mongodb-checkpoint-sqlx can store opaque BSON resume tokens bounded to 1 MiB in PostgreSQL and optionally acquire a database-clock writer lease. Deployment applies the initial checkpoint migration and its forward-only byte-bound migration; application startup does not. Its default diagnostics are content-free while trusted storage sources remain available to application handling.

  • A stable consumer name identifies the collection, pipeline, decoder, and handler contract. Change it when any of those meanings change.
  • Save a checkpoint after the durable, idempotent effect succeeds. Storage failure or lost lease stops the worker and returns control to its supervisor.
  • Each restart uses a new deployment-instance owner ID. Lease durations use positive whole milliseconds; renew before expiry and do not reuse stale leases.
  • A checkpoint is not message-queue settlement and does not establish exactly-once behavior for external side effects.

Deployment Rules

Collection validators, indexes, backfills, shard-key changes, credentials, and topology are deployment work. They must not run automatically at production server startup.

Create one long-lived Client per process and clone it into state. Configure positive connection and server-selection deadlines, pool size, TLS, and application name explicitly; Rustee rejects a zero timeout before the driver is configured. Client configuration and readiness return content-free error categories while retaining the driver source for trusted diagnostics. Configuration debug output retains only redacted connection and routing values plus timeout and presence state. URI, credentials, database names, application names, command bodies, resume tokens, and event bodies must stay out of logs, metrics labels, traces, and HTTP errors.
