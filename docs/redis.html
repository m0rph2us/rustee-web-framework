Redis and State Stores

Explicit State, Explicit Failure Policy

Redis is an optional external state store for caching, sessions, rate limiting, and streams. Rustee never turns it into hidden global state or an automatic cache.

Integration Boundary

rustee-redis injects an application-created client. It does not expose a universal cache, distributed lock, or session as a hidden framework singleton. Namespaces and TTLs must be visible and bounded, while secrets and endpoint details are redacted from diagnostics. Cache writes reject a zero or Redis-unrepresentable TTL as a local configuration error before contacting Redis. Bounded JSON reads and bounded atomic cache consumption each inspect the Redis byte length before returning a value in one server execution, so a cache miss, size rejection, and invalid stored JSON remain distinct outcomes. Redis configuration, connection, readiness, JSON cache helpers, and higher-level cache adapters expose content-free failure categories by default while preserving trusted source errors where an adapter retains one for application handling. 

#[derive(Clone)]
struct AppState { redis: redis::Client }

let app = App::new()
    .get("/profile", profile)
    .with_state(AppState { redis });

One long-lived client is normally created per process and cloned into state. Call readiness(&manager, deadline) with a short, positive deadline; its timeout and diagnostics are content-free while trusted driver sources remain available for application handling. Request retry, stale fallback, and degraded-service behavior remain explicit application policy.

Create-Only Records

set_json_if_absent and set_json_bounded_if_absent write a JSON value with one atomic Redis SET NX EX command. The bounded form rejects an oversized serialized value before the command. Both return CacheError::EntryExists when the exact key is already live and never replace that value. Use them for one-time state such as OAuth authorization transactions; use the ordinary explicit cache write helpers when replacement is part of the application cache policy.

The optional MCP OAuth Redis adapter derives its transaction record key from a versioned, length-delimited configured namespace and opaque state. The record key remains authenticated-encryption data, so a format upgrade invalidates unfinished transactions rather than attempting an ambiguous legacy-key lookup.

The Redis provider contract races two create-only writes for one temporary key and verifies that exactly one value is retained. It is opt-in locally because it needs Redis, and runs in the Redis CI qualification stage.

Sessions and Rate Limits

  • rustee-auth-session-redis stores opaque server-side sessions with a namespace and TTL. It reads at most 512 KiB per persisted session, rejects a Redis-unrepresentable remaining TTL before persistence, validates the restored CSRF capability, session-key binding, and expiry before restoration, exposes content-free persistence diagnostics while preserving trusted sources, and remains fail-closed at the HTTP boundary. Cookie attributes, session rotation, CSRF policy, user logout, and retention are application decisions.
  • rustee-rate-limit-redis implements a keyed fixed-window decision with Lua. Fixed windows use positive whole milliseconds, and connection and namespace values remain redacted from diagnostics. Its versioned, length-delimited storage key keeps an opaque identity containing delimiters from colliding with another namespace. It does not decide whether the key is an IP address, account, tenant, credential, or route.
  • A Redis outage must not silently become an authorization bypass or unlimited request path. Configure the intended failure behavior and test it.
  • Do not place raw session content, credential material, or unbounded user input in keys, metric labels, logs, or traces.

Redis Streams Jobs

rustee-jobs-redis is an optional durable-job provider. It uses pre-provisioned consumer groups and DLQs, ownership-checked acknowledgement, Redis-clock delayed retry, pending reclaim, and bounded readiness. Delivery is at least once; duplicate handling belongs to the job handler.

  • Worker operation deadlines must exceed blocking reads.
  • Retry, block, and reclaim settings use positive whole milliseconds; unknown-job handling is an explicit delivery outcome with a DLQ path.
  • Internal retry storage keys use a versioned, length-delimited stream and consumer-group namespace, so delimiters in deployment identifiers cannot make two worker routes share retry state. These provider-private keys are not an application namespace API. Reconcile legacy scheduled retries before a worker upgrade that changes this durable key format; do not run old and new worker versions for the same route concurrently.
  • Redis Cluster, Sentinel, retention, operator replay, heartbeat behavior, and production outage qualification are separate release gates.

Operational Rules

  • Use namespaced keys that include the owning subsystem and, where needed, a verified tenant boundary.
  • Set bounded TTLs and document who invalidates a value. A TTL is not a substitute for consistency design.
  • Use TLS and least-privilege credentials in production. Never include Redis URLs or credentials in HTTP errors, logs, traces, or metrics labels.
  • Restart behavior, backoff, readiness routing, alerting, and failover drills are deployment responsibilities.
