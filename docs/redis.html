Redis and State Stores

외부 상태는 명시적으로, 장애 정책은 역할별로

Redis는 빠른 cache 이상의 역할을 합니다. Rustee는 Redis를 cache, session, OIDC authorization transaction, rate limit, Pub/Sub을 위한 선택적 상태 저장소로 지원하되, 데이터 일관성이나 장애 시 동작을 숨기는 전역 기능으로 만들지 않습니다.

결정 요약

첫 공식 client 경로는 redis-rs의 Tokio용 redis::aio::ConnectionManager입니다. RedisConfig는 기본 5초의 bounded initial connect와 endpoint/credential 없는 failure를 제공하고, 이 client는 clone 가능한 multiplexed connection을 사용해 이후 끊긴 연결을 재연결합니다. Rustee는 Stage 6에서 선택적 rustee-redis crate를 제공하며, keyed HTTP policy는 provider-neutral rustee-rate-limit, Redis Lua adapter는 rustee-rate-limit-redis로 분리합니다. rustee-core에는 Redis 의존성을 추가하지 않습니다.

애플리케이션은 Redis client를 AppState에 보관하고 State<AppState>로 꺼냅니다. Rustee는 redis-rs command API를 새 trait로 감싸지 않으며, 필요한 경우 원래 client API에 바로 접근할 수 있습니다.

권장 애플리케이션 구조

use redis::{aio::ConnectionManager, AsyncCommands};
use rustee::{App, Json, Path, State};

#[derive(Clone)]
struct AppState {
    cache: ConnectionManager,
}

async fn get_user(
    State(state): State<AppState>,
    Path(id): Path<i64>,
) -> Result<Json<User>, AppError> {
    let key = format!("rustee:users:v1:{id}");
    let mut cache = state.cache.clone();

    if let Some(json) = cache.get::<_, Option<String>>(&key).await? {
        return Ok(Json(serde_json::from_str(&json)?));
    }

    let user = users::find(id).await?;
    let json = serde_json::to_string(&user)?;
    cache.set_ex::<_, _, ()>(&key, json, 300).await?;
    Ok(Json(user))
}

이는 Rustee Stage 4와 Stage 6이 완료됐을 때의 목표 형태입니다. 실제 서비스에서는 cache read와 write의 Redis 오류를 같은 방식으로 처리하지 않습니다. cache는 원본 DB로 우회할 수 있지만, session이나 rate limit은 보안 요구에 따라 다른 정책을 가져야 합니다.

연결과 격리 규칙

  • 일반 command는 ConnectionManager를 clone해 concurrent하게 사용합니다.
  • Pub/Sub, blocking command, 장시간 stream 소비는 일반 request client와 분리한 전용 client 또는 background task를 사용합니다.
  • 연결 pool이 실제로 필요한 경우 애플리케이션이 deadpool-redis 같은 도구를 선택합니다. Rustee 초기 core와 adapter는 pool을 강제하지 않습니다.
  • Redis Cluster, Sentinel, TLS, RESP3은 별도 feature와 configuration으로 제공하며, 단일 Redis 기본 경로의 의존성을 늘리지 않습니다.
  • Redis URL과 credential은 configuration/secret provider에서 공급하고, rustee_redis::connect의 sanitized startup failure와 함께 로그나 오류 응답에 포함하지 않습니다.

장애와 일관성 정책

사용 사례 기본 태도 Rustee 요구
읽기 cache 원본 저장소로 우회할 수 있음 우회 여부, timeout, metric을 configuration으로 드러냅니다.
쓰기 cache 원본 저장소의 성공을 Redis 쓰기와 혼동하지 않음 write-through, invalidate, retry 중 하나를 application이 선택합니다.
Session과 authorization 보안을 우선해 대개 fail-closed가 필요 SessionLayer는 Redis store failure를 fail-closed 503으로 정규화합니다.
Rate limit 보안과 가용성의 trade-off가 서비스마다 다름 Redis 장애 시 allow 또는 deny를 필수 설정으로 둡니다.

Rustee는 Redis 장애를 조용히 무시하는 기본값을 제공하지 않습니다. RedisSessionStore는 Redis 오류를 store failure로 전달하고 SessionLayer는 503으로 차단합니다. RateLimitLayer는 allow/deny를 기본값으로 숨기지 않고 constructor에서 failure policy를 받습니다.

Rate limit

RateLimitLayer는 key를 추측하지 않습니다. application은 verified principal, API key fingerprint 또는 trusted proxy가 정규화한 client address처럼 이미 trust boundary를 지난 값으로 resolver를 만듭니다. raw bearer token, 임의 forwarding header, cookie value를 Redis key로 직접 쓰지 않습니다. 

use rustee_rate_limit::{FixedWindow, RateLimitKey, RateLimitLayer, StoreFailurePolicy};
use rustee_rate_limit_redis::RedisFixedWindowStore;

let store = RedisFixedWindowStore::new(state.redis.clone(), "app:rate-limit:v1")?;
let policy = FixedWindow::new(120, Duration::from_secs(60))?;
let api_limit = RateLimitLayer::new(
    store,
    policy,
    |request: &Request| request
        .extensions()
        .get::<Principal>()
        .and_then(|principal| RateLimitKey::new(format!("principal:{}", principal.subject())).ok()),
    StoreFailurePolicy::FailClosed,
);

let app = api_limit.layer(app);
  • allowed response에는 RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset을 넣습니다. denied request는 application에 도달하지 않고 429, Retry-After, 같은 rate-limit metadata를 반환합니다.
  • resolver가 trusted key를 만들 수 없으면 layer는 400으로 차단합니다. rate-limit를 적용하지 않을 route는 layer 바깥에 둡니다.
  • store failure는 constructor에서 반드시 선택한 FailClosed 503 또는 FailOpen pass-through로 처리합니다. security-sensitive login, password reset, expensive API에는 대체로 FailClosed를 사용합니다.
  • Redis adapter는 INCR, 첫 TTL 설정, PTTL 조회를 하나의 Lua execution으로 수행합니다. fixed-window는 window 경계 양쪽에서 burst를 허용할 수 있으므로 더 엄격한 smooth rate 요구에는 token-bucket 또는 GCRA provider를 별도 contract로 추가합니다.

의도적으로 제공하지 않는 것

  • 모든 GET response를 자동으로 Redis에 저장하는 middleware. cache key, authorization, invalidation이 서비스마다 다릅니다.
  • 일반적인 lock() helper. 분산 락은 fencing과 lease 만료에 관한 서비스 수준의 정확성 요구가 필요합니다.
  • Redis Pub/Sub을 durable queue로 보이게 하는 API. 전달 보장이 필요하면 Redis Streams 또는 전용 queue adapter를 명시적으로 선택합니다.
  • DB transaction과 Redis write를 하나의 atomic transaction처럼 묶는 API. outbox 또는 보상 작업은 application architecture에서 결정합니다.

구현 순서

  1. Stage 4의 State와 middleware configuration contract를 안정화합니다.
  2. Stage 6에서 rustee-redis, ConnectionManager example과 Redis 7 container의 PING/JSON cache/atomic GETDEL/delete contract를 구현했습니다. rustee-rate-limit의 fixed-window HTTP 429/503/fail-open contract와 rustee-rate-limit-redis의 Lua atomic bounded-concurrency Redis 7 contract도 구현했습니다.
  3. Stage 8에서 rustee-auth-session-redis Redis adapter와 Docker-backed session restoration contract, rustee-auth-oidc-redis의 transaction TTL/atomic GETDEL contract를 구현했습니다.
  4. Stage 10에서 rustee-jobs-redis가 pre-provisioned Streams consumer group/DLQ, ownership-checked ack, Redis-clock durable delayed retry, pending reclaim을 구현했고 Redis 7 CI가 success ack, retry-DLQ, reclaim attempt, unknown registry job DLQ를 검증합니다. rustee-ai-cache-redis은 tenant-scoped opaque exact key로 선택한 AI response만 versioned namespace와 serialized-entry bound, Redis-second TTL, exact delete로 보관합니다. raw prompt fingerprint, encryption/TLS, tenant erase, retention, Redis outage/restart, Cluster/Sentinel와 cache stampede는 application/deployment release gate입니다. handler heartbeat, job retention/replay runbook도 별도 release gate입니다.
  5. Cluster, Sentinel, distributed lock은 실제 요구와 함께 별도 ADR로 확장합니다.
