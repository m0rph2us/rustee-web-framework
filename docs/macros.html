Macro Boundaries

Macros Implement Existing HTTP Contracts

Macros are optional ergonomics around explicit Rustee APIs. They do not create a parallel routing, extraction, or schema system.

Route Builder

routes! builds routes through the same App APIs used without macros. It validates supported macro methods at compile time and relies on the shared App validator for route grammar, including repeated-separator rejection, so macro and macro-free routes retain one contract.

Header Derive

FromHeader derives explicit header extraction for supported shapes. A typed Header<T> requires exactly one value for its declared field and rejects duplicates before user parsing. It preserves normal extraction failure and HTTP response behavior instead of inventing an implicit authentication or authorization rule.

Intentional Limits

  • Macro-free APIs remain first-class and documented.
  • Macros do not infer application state, error policy, OpenAPI semantics, security requirements, or provider configuration.
  • Unsupported input produces a compile diagnostic rather than a best-effort runtime interpretation.
  • Generated code follows the same public contracts, feature gates, and MSRV as its non-macro equivalent.

Implementation Boundaries

  • rustee-macros::route_builder owns the routes! grammar and builder expansion.
  • rustee-macros::from_header owns derive validation and FromHeader implementation generation.
  • rustee-macros::crate_path resolves renamed rustee dependencies for generated code; the crate root only exposes compiler-required macro entry points.

Verification and Evolution

  • Compile tests cover accepted input, rejected input, diagnostics, and generated API compatibility.
  • New syntax requires a documented public use case, a non-macro equivalent, regression tests, and an ADR when it alters a boundary.
  • See ADR 0040 and ADR 0041.
