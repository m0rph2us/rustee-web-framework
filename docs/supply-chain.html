Supply Chain and Release Evidence

Rustee Supply Chain and Release Evidence

Release artifacts must establish what was built, from which source, with which dependency policy, and under which approval. Evidence is auditable without exposing credentials or private data.

Current Controls

  • Source, lockfile, package inventory, MSRV, and dependency review are part of the release preflight.
  • CI and release dependency-resolving Cargo checks use the tracked lockfile and reject dependency resolution changes.
  • Candidate source archives are assembled with versioned manifests, then Cargo verifies each reassembled source package; command-scoped local patches only support pre-publication resolution and are never emitted as archive path dependencies.
  • Every publish candidate declares the repository's SPDX dual-license expression, while the repository source retains the concrete MIT and Apache license texts.
  • GitHub Actions use full commit SHAs, and Docker images used by CI contract environments use immutable manifest digests.
  • Release artifacts include package checksums, CycloneDX SBOM scope, provenance/attestation where configured, and tag-to-source association.
  • After publication, a manual tag-based workflow resolves every candidate through the public registry and compiles a neutral consumer at the supported MSRV. Registry indexing or consumer resolution failure remains a release-evidence failure.
  • Critical and policy-relevant dependency advisories block or receive documented owner-approved treatment before promotion.

Policy Boundary

  • Rustee records package and release evidence; registry credentials, signing keys, secret storage, and organizational approval systems remain deployment-owned.
  • Do not put tokens, signing material, private source URLs, raw build logs with secrets, or customer data in an SBOM, attestation, or public release note.
  • Third-party provider qualification and runtime security posture are not replaced by a dependency inventory.

Release Artifacts and Order

  1. Review the approved package inventory and clean source snapshot.
  2. Run the required test, documentation, inventory, and security checks.
  3. Generate package checksums, SBOM, provenance, and release metadata from the exact candidate source.
  4. Review artifacts and attach them to the approved tag and release record.
  5. Publish approved foundational dependencies before their dependents, waiting for registry indexing at each required boundary.
  6. Verify registry content and archive the safe evidence.

AI Maintenance Rule

When dependencies, artifact scripts, package metadata, or release evidence change, update this document, the release checklist, the inventory, and the qualification register in the same change.
