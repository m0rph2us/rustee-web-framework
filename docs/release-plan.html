Delivery Plan

작은 core를 먼저 출하하고, 통합은 증명된 만큼 지원합니다

Rustee는 모든 데이터베이스, broker, AI provider, enterprise topology를 한 번에 완성해야 v1이 되는 프로젝트가 아닙니다. framework baseline과 선택적 adapter의 지원 약속을 분리하고, 각 약속에는 같은 수준의 검증과 운영 책임을 요구합니다.

계획의 기준

이 문서는 출시 순서와 지원 선언의 단일 기준입니다. 기능 로드맵은 구현 항목과 완료 상태를, 구현 계획 재검토는 현재 공백과 다음 작업을, release checklist는 clean source부터 tag, publish까지의 실행 절차를 기록합니다. 문서가 다르면 이 문서의 출하 게이트를 우선하고 같은 변경에서 정정합니다.

  • v1은 framework baseline의 안정성 약속입니다. 선택적 adapter나 enterprise deployment를 모두 포함한다는 뜻이 아닙니다.
  • 공통 facade를 억지로 만들지 않습니다. database, queue, event, AI provider의 서로 다른 acknowledgement, transaction, retry 의미는 provider별 crate와 contract에 남깁니다.
  • 기능은 코드가 아니라 증거로 승격합니다. real backend contract, failure policy, lifecycle, observability, runbook, version matrix가 있어야 지원 상태가 올라갑니다.
  • enterprise는 edition이 아니라 qualification입니다. cluster, multi-tenant, cloud, regulated environment는 workload별 ADR과 deployment evidence가 있을 때만 선언합니다.

v1 경계

Rustee v1은 F1의 public surface를 안정화하는 release입니다. PostgreSQL, Redis, MongoDB, OIDC, queue, Kafka, AI crate는 독립적으로 Contract-verified에서 Supported로 올라갈 수 있으며, 하나가 미완성이라는 이유로 core HTTP framework의 v1을 끝없이 미루지 않습니다.

  • v1 hard gate: Rust 1.94.1과 stable에서 Linux CI, core/facade의 public API compatibility baseline, format/lint/unit/wire/doctest/example/link 검증, documented proxy trust/cleartext origin boundary, shutdown/redaction regression입니다.
  • v1 release gate: canonical reverse-proxy deployment contract, public migration guide/release notes, dependency advisory triage와 reproducible source artifact입니다.
  • v1 비목표: built-in TLS/ACME, HTTP/2, WebSocket upgrade, generic ORM, universal queue facade, automatic schema migration, automatic AI tool loop, cluster control plane입니다. 필요하면 별도 ADR과 feature track으로 진입합니다.
  • macOS/Windows는 F0에서 compile compatibility를 확인하는 candidate platform입니다. runtime and container-backed support를 약속하려면 별도 CI evidence와 support policy가 필요합니다.

첫 release 기준선

2026-08-04 현재 workspace의 첫 intentional source baseline commit은 존재하지만, release tag와 registry publish record는 없습니다. 따라서 public API diff를 이전 release와 비교하는 automated semver gate는 아직 실행할 baseline이 없습니다. 이 상태에서는 cargo-semver-checks를 억지로 green check로 추가하지 않습니다. clean preflight와 tag/publish의 구체적 실행 순서는 release checklist를 따릅니다.

  1. 첫 source baseline commit은 release inventory로 publish 후보 crate와 publish = false인 workspace-only crate, public facade와 직접 사용 가능한 leaf crate를 확정합니다. CI는 이 HTML의 structured inventory와 cargo metadata, candidate-only source archive assembly를 대조합니다.
  2. 첫 v0.1.0 source tag와 publish record가 public API baseline이 됩니다. 이전 crate version이 없다면 initial release는 human API review와 required CI evidence로 검토합니다.
  3. 그 다음 minor/patch release부터 prior tag 또는 prior published version을 baseline으로 cargo-semver-checks를 release gate에 추가합니다. pre-1.0 변경도 release note와 migration guidance 없이 숨기지 않습니다.
  4. baseline을 만들기 전에는 official Supported 선언이나 v1 stability promise를 하지 않습니다.

Dependency Advisory Policy

  • .github/workflows/security-audit.yml은 RustSec advisory database로 current lockfile을 검사합니다. 모든 checked-in workflow의 직접 uses: reference는 full commit SHA와 version comment로 고정하고, Fast PR/release lane의 check-workflow-action-pins.mjs가 mutable tag/branch가 다시 들어오는 것을 차단합니다. 이 검사는 third-party composite action 내부의 transitive reference를 검증하지 않습니다.
  • deny.toml과 dedicated CI lane은 all-feature graph의 SPDX license, yanked dependency, wildcard dependency와 unknown registry/git source를 검사합니다. dev/build dependency도 포함합니다. 현재 허용 목록 밖의 license, advisory 또는 source는 CI를 통과할 수 없습니다.
  • CI failure는 publish 전에 해결합니다. deny.toml은 빈 exception 목록을 version-control 하며, advisory 또는 license exception을 허용하지 않습니다. 이 원칙을 바꾸려면 새 ADR, 영향 분석, compensating control, owner와 만료일을 포함한 별도 변경과 release note가 필요합니다.
  • release qualification workflow는 v* tag 또는 manual dispatch에서 stable format/lint/test/doctest, HTML/inventory, native Kafka compile profile과 inventory-approved candidate source archive assembly를 실행하고 모든 publish-candidate .crate source package, SHA256SUMS, all-feature/all-target CycloneDX 1.5 JSON SBOM archive를 각각 90일 보관합니다. first publish 전 local path dependency가 registry에 없으므로 archive assembly는 --no-verify이며, dependency publish 뒤 verify-published-release-candidates.mjs가 registry source consumer compile verification을 수행하는 별도 publish gate입니다.
  • GitHub artifact attestation이 가능한 repository에서는 같은 workflow가 source package checksum subject와 SBOM JSON subject에 keyless provenance를 발행합니다. 이는 crates.io publish를 자동 실행하거나 registry upload identity를 증명하지 않으므로 publish credential owner, release approval, published package checksum 검토는 첫 release gate로 남습니다. 상세 범위는 공급망과 릴리스 증거를 따릅니다.

첫 네 개 milestone

  1. F0.1 - release evidence를 CI에 고정: Rust 1.94.1/stable matrix의 format, lint, workspace test/doctest, HTML link, release inventory, direct workflow action SHA pin, candidate-only source archive assembly과 native Kafka compile profile은 required CI job으로 고정했습니다. tag qualification도 같은 stable preflight를 재실행하고 CycloneDX SBOM, checksum archive와 keyless provenance를 생성합니다. pre-publication local path dependency는 registry에서 아직 해석되지 않으므로 source archive assembly와 post-publication registry consumer compile verification을 분리합니다. 첫 source baseline commit은 존재하지만 source tag와 registry publish approval은 다음 release owner gate입니다.
  2. F1.1 - framework baseline 닫기: canonical Nginx proxy의 spoofed Forwarded overwrite, proxy_cache gzip/identity representation separation, shutdown 중 active request drain과 config parse/schema error redaction contract는 CI에 고정했습니다. opt-in PanicCatchLayer는 pre-response handler panic을 fixed 500으로 redaction하는 in-process/real TCP contract를 추가했습니다. observability는 framework global exporter configuration을 추가하지 않으며 endpoint/credential/sampling/shutdown을 application-owned tracer provider에 둡니다. edge delivery policy는 vendor-neutral TLS/cache/purge/compression ownership과 qualification evidence를 정했습니다. 다음은 application panic hook/restart와 chosen CDN deployment contract를 실제 topology에서 확인하는 일입니다.
  3. I1.1 - 보안과 저장소의 실패 경계: external IdP revocation, MongoDB recovery policy, outbox alert/export policy, restore/rotation procedure를 provider별로 닫습니다. MongoDB transaction commit/abort, change-stream checkpoint/shutdown, trusted-context BSON tenant read/update/delete/first-match aggregation boundary와 tenant-field mutation rejection은 replica-set CI에 고정했고, PostgreSQL checkpoint adapter는 opaque token load/upsert/corruption-rejection, database-clock writer-lease contention/renewal/expiry/stale-write rejection과 new-client resume-to-next-event combined contract를 고정했습니다. CI는 stopped replica set 및 stopped checkpoint store의 bounded readiness failure와 restart 뒤 recovery도 확인합니다. raw driver, aggregation $lookup/$unionWith, change-stream tenant access review는 아직 release gate이며, lease owner identity와 renewal scheduler는 application deployment가 소유합니다.
  4. I2.1 - delivery reliability: RabbitMQ broker outage and management TLS/ACL, SQS IAM/KMS and real AWS opt-in, Redis Streams reclaim/retention, Kafka consumer delivery collector의 protected scrape/alert ownership과 source-settlement interpretation, retained-subject를 남기는 explicit Confluent Schema Registry live qualification의 provider/version/credential/ACL/outage와 consumer-first rollout/replay/external idempotency, PostgreSQL delayed-retry relay migration, alert/backoff, restore operator procedure를 각자의 contract로 검증합니다.

AI live provider/vector qualification과 enterprise topology는 I1/I2의 evidence를 소모하지 않는 독립 track으로 유지합니다. provider 수를 추가하거나 추상화를 넓히는 일은 위 gate가 통과된 뒤에만 우선순위를 얻습니다.

Outbox 운영 신호

rustee-outbox-observability-prometheus는 bounded relay collector의 pass/outcome/row-count/duration을 explicit Prometheus text response로 노출합니다. 이는 I1의 exporter 경계를 제공하지만 alert threshold, scrape authorization, migration/restore, external side-effect idempotency와 broader outage evidence를 자동으로 Supported로 올리지는 않습니다.

2026-08-04 출하 순서 확인

이번 재검토에서 F0/P0가 가장 앞선다는 점을 다시 확인했습니다. workspace의 main에는 첫 source baseline commit이 있지만 release inventory와 CI만으로 public API semver comparison이나 publish approval이 시작되지는 않았습니다. F1은 optional database, broker, AI adapter의 완료를 기다리지 않고 진행합니다. F1 뒤 I1/I2는 모든 adapter를 한 번에 Supported로 올리지 않고 owner가 선택한 하나의 reference deployment부터 provider evidence를 쌓습니다. Kafka의 delayed retry, schema boundary, delivery observer와 consumer readiness는 Contract-verified code evidence이며 Confluent/provider outage, rollout, replay와 external side-effect evidence를 대체하지 않습니다. AI Batch의 typed row/result conversion과 artifact runbook은 I3의 Experimental 근거이며 provider 비용, tenant authorization, partial-result/billing reconciliation을 자동 승인하는 근거가 아닙니다.

변경 통제

  • 새 crate나 provider는 먼저 Experimental로 문서화하고, “누가 어떤 인프라를 운영하는가”를 명시합니다.
  • Supported/Enterprise-qualified 승격, v1 public API freeze, 지원 platform 변경은 ADR와 이 문서를 함께 갱신합니다.
  • release blocker는 구현 계획 재검토와 지원 현황 매트릭스의 표에 반영합니다. 해결되지 않은 위험을 status 문구로 감추지 않습니다.
  • AI 에이전트는 작업 시작 시 이 문서, 구현 재검토, 영향 영역 문서를 읽고 완료 시 status와 evidence를 갱신합니다.
